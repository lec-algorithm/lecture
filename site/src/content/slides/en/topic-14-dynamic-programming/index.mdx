## Topic 01's promise
::sub[Why was recursive Fibonacci slow?]

- The culprit was not recursion but **computing the same value over and over**.
- Just writing each answer down once turns exponential time into linear time.

<br/>

We apply that idea in turn to coin change, the longest increasing subsequence,  
grid paths, shortest paths, and the 0/1 knapsack.  
Then we walk the table backwards to recover **the choices that built the answer**.

#### Two conditions and two methods
::sub[The "dynamic" in the name does not mean "changes at run time"]

- **Overlapping subproblems**
  - The same small problem shows up many times.
- **Optimal substructure**
  - The optimal solution to a large problem is built from optimal solutions to smaller ones (for optimization problems).
- **There are two ways to store answers.**
  - Memoization: keep the recursion and write the answers down.
  - Tabulation: fill a table upward from the smallest problems.

</Slide>

<Slide>

#### What optimal substructure means
::sub[If the whole is optimal, the parts it is made of are optimal too]

- **Example**: the fastest way from Seoul through Daejeon to Busan
  - Its Seoul → Daejeon leg is also the fastest way from Seoul to Daejeon.
- **Why**: try swapping the part.
  - If Seoul → Daejeon could be done faster, swapping it in would make the whole trip faster.
  - That contradicts the whole being fastest, so there is no such way.
- **The reverse does not come for free.** Optimal parts do not make an optimal whole.
  - Go through Gangneung and even two fastest legs make a detour.
  - That is why dynamic programming compares **all** the places to split.

</Slide>

#### Recursive Fibonacci
::sub[Topic 01's code as is]

```plaintext
ALGORITHM FibRecursive(n)
    if n <= 1 then
        return n
    return FibRecursive(n-1) + FibRecursive(n-2)
```

- **Time** $$O(2^n)$$: grows exponentially; exactly $$\Theta(\varphi^n)$$ with $$\varphi \approx 1.618$$
- **Space** $$O(n)$$: the recursion stack
- **The problem**: it repeats the same computations.

</Slide>

<Slide>

#### How much Fibonacci computes
::sub[Calls C(n) = C(n-1) + C(n-2) + 1]

| Term | Calls | of which $$F(3)$$ | of which $$F(2)$$ |
| --- | --- | --- | --- |
| $$F(0)$$, $$F(1)$$ | 1 | | |
| $$F(2)$$ | 3 | | 1 |
| $$F(3)$$ | 5 | 1 | 1 |
| $$F(4)$$ | 9 | 1 | 2 |
| $$F(5)$$ | 15 | 2 | 3 |

15 calls for $$F(5)$$ alone, yet only 6 distinct values.  
$$C(n) = 2F(n+1) - 1$$, growing about 1.6 times for each step of $$n$$.

<Slide>

#### What changed
::sub[The way down is the same; the way back up differs]

- $$F(2) = 1$$ is computed and written into `memo[2]`.
- When $$F(4)$$ calls $$F(2)$$ again, it comes out of `memo[2]`.
  - **No more branching.**
- $$F(5)$$'s right child $$F(3)$$ also comes out of `memo[3]`.
  - The four calls below it vanish.

<br/>

Calls drop **from 15 to 9**, and $$2n - 1$$ for any $$n \ge 1$$.  
`memo[0]` and `memo[1]` stay -1 because the base case returns them directly.

</Slide>

<Slide class="compact">

#### Write the answer down
::sub[`01_fibonacci/fibonacci.c` · all we added is the if that checks and the assignment that stores]

```c
long long fibMemo(int n) {
    if (n <= 1) {
        return n;                       // 1. the base definition
    }
    if (memo[n] != -1) {
        return memo[n];                 // 2. already written down: return at once
    }
    memo[n] = fibMemo(n - 1) + fibMemo(n - 2);  // 3. compute recursively
    return memo[n];                     // 4. write it down and return
}
```

- **Time** $$O(n)$$: each value is computed once.
- **Space** $$O(n)$$: memo array + recursion stack

</Slide>

## Tabulation

<Slide>

#### From the bottom up
::sub[One loop and one array]

```plaintext
ALGORITHM FibTabulation(n)
    if n <= 1 then
        return n
    dp[0] <- 0
    dp[1] <- 1
    for i <- 2 to n do
        dp[i] <- dp[i-1] + dp[i-2]    // the two cells before are already filled
    return dp[n]
```

- **Time** $$O(n)$$: once per cell
- **Space** $$O(n)$$: one table, and no stack is used.
- Keep only the last two cells and space drops to $$O(1)$$.

</Slide>

<Slide>

#### Isn't this just a loop?
::sub[Yes. Topic 01's loop is exactly tabulation]

- **What differs is not the result but the starting point.**
  - Topic 01: we wrote the loop **knowing** that adding the two previous terms works.
  - Tabulation: we **derive** it from the recursive definition (the recurrence).
- **How it is derived**
  1. Make each subproblem the recursion solves one cell of a table. (`dp[i]` = $$F(i)$$)
  2. Order the cells so that the cells referred to are filled first. (small $$i$$ first)
- For Fibonacci the cells form a line and the order is obvious, so it just looks like a loop.
  - For coin change, LIS, and the knapsack, the same method produces loops you have not seen before.

</Slide>

#### Iterative Fibonacci
::sub[Topic 01's code · tabulation with less space]

```plaintext
ALGORITHM FibIterative(n)
    if n <= 1 then return n
    prev <- 0, curr <- 1
    for i <- 2 to n do
        next <- prev + curr
        prev <- curr
        curr <- next
    return curr
```

- **Time** $$O(n)$$ · **Space** $$O(1)$$

</Slide>

#### Memoization vs. tabulation
::sub[Same recurrence, opposite directions]

| | Memoization | Tabulation |
| --- | --- | --- |
| Computation | **lazy** (only what is needed) | **eager** (everything) |
| Starting point | top → bottom, big → small | bottom → top, small → big |
| Implementation | recursion + cache | loop + table |
| Intuitiveness | transcribe the recurrence | the fill order must be worked out |
| Robustness | risk of stack overflow | uses no stack |
| Space optimization | hard | easy |

</Slide>

<Slide>

#### The character of each
::sub[Top-down and bottom-up]

- **Memoization**
  - Stores results while recursing and so avoids recomputation.
  - Descends from the big problem, like $$F(4)$$, $$F(3)$$, computing **only what is needed**.
  - Recursive calls add overhead.
- **Tabulation**
  - Fills the table in order from the small problems.
  - Solves **every subproblem** from the smallest up, like $$F(2)$$, $$F(3)$$.
  - Uses only a loop, so it is efficient.

</Slide>

#### Python generators
::sub[A lazy list]

```python
def squares_eager(n):          # keep every value in memory
    result = []
    for i in range(n):
        result.append(i * i)
    return result

def squares_lazy(n):           # compute one at a time, only when needed
    for i in range(n):
        yield i * i

numbers = squares_eager(1000000)   # a list of a million elements is created
numbers = squares_lazy(1000000)    # nothing has been computed yet
```

</Slide>

<Slide class="compact">

#### Lazy evaluation in functional programming
::sub[Define an infinite Fibonacci sequence and take only what you need]

```python
def fibonacci_infinite():      # "define" infinitely many Fibonacci numbers
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b

fib = fibonacci_infinite()
first_10 = [next(fib) for _ in range(10)]   # only 10 are actually computed
```

Languages such as Haskell do this at the language level.  
A generator **only postpones; it does not store.** Memoization is postponing plus storing.

</Slide>

#### When lazy is better
::sub[The memoization side]

- **When the answer needs only some of the cells**
  - For 80 won the table fills 80 cells, the memo **8**
  - $$F(50)$$ does not count: it needs everything from $$F(0)$$ up.
- **When it is hard to know in advance which cells matter**
  - Problems that branch on conditions, or use cells sparsely
- **When the filling order is hard to find**
  - The recursion descends in the order it needs.
- **Quick prototyping**
  - Copy the recurrence and attach a table.

</Slide>

<Slide>

#### When eager is better
::sub[The tabulation side]

- **When the whole result is needed anyway**
  - Problems that pass through every cell, like Fibonacci
- **When robustness matters**
  - For 100 won with `{1, 5, 10}` the memo's recursion is **101 deep**.
- **When tuning performance**
  - There is no overhead of recursive calls.
- **When saving memory**
  - Keep only a few earlier cells (Fibonacci $$O(1)$$, knapsack $$O(W)$$)

</Slide>

#### The last coin paid
::sub[The fewest coins of 2, 3, 5 won that make 6 won? 2 coins (3 + 3)]

- Greedy pays 5 won first and gets stuck, because the remaining 1 won cannot be made.
- Dynamic programming splits on **the last coin paid**, $$c$$.
  - The remaining $$a - c$$ won is the same problem again.

$$
C(a) = \begin{cases}
0 & a = 0 \\
\min\limits_{c \,\in\, \text{coins},\ c \le a} \bigl( C(a - c) + 1 \bigr) & a > 0
\end{cases}
$$

An amount that cannot be made is $$\infty$$ (`INF` in the code)

</Slide>

#### Memoization
::sub[`02_coin_change/` · the same four steps as Fibonacci]

```plaintext
ALGORITHM CoinChangeMemo(amount, coins, m, memo)
    if amount = 0 then return 0          // 1. base: 0 won takes 0 coins
    if amount < 0 then return INF        //    a negative amount cannot be made
    if memo[amount] != -1 then           // 2. already computed: return at once
        return memo[amount]
    best <- INF                          // 3. pay each coin once, recurse on the rest
    for i <- 0 to m-1 do
        r <- CoinChangeMemo(amount - coins[i], coins, m, memo)
        if r != INF and r + 1 < best then
            best <- r + 1
    memo[amount] <- best                 // 4. write it down and return
    return best
```

#### Tabulation
::sub[`02_coin_change/` · whenever the minimum changes, write that coin into choice]

```plaintext
ALGORITHM CoinChangeTab(amount, coins, m)
    dp[0] <- 0                           // 1. initialize
    for a <- 1 to amount do dp[a] <- INF
    for a <- 1 to amount do              // 2. every amount, smallest first
        for i <- 0 to m-1 do
            c <- coins[i]
            if c <= a and dp[a - c] != INF and dp[a - c] + 1 < dp[a] then
                dp[a] <- dp[a - c] + 1
                choice[a] <- c           //    the last coin paid for this amount
    if dp[amount] = INF then return INF  // 3. an amount that cannot be made
    a <- amount                          // 4. follow choice backwards
    while a > 0 do
        print choice[a]
        a <- a - choice[a]
    return dp[amount]
```

#### Memoization: take it or leave it
::sub[The remaining work is fixed by (the element i to look at, the last element taken prev)]

```plaintext
ALGORITHM LisHelper(arr, n, i, prev)
    if i = n then return 0                       // 1. base: no elements left
    if memo[i][prev+1] != -1 then                // 2. (i, prev) already solved
        return memo[i][prev+1]
    exclude <- LisHelper(arr, n, i+1, prev)      // 3. leave arr[i]
    include <- 0
    if prev = -1 or arr[i] > arr[prev] then      //    if arr[i] can be taken
        include <- 1 + LisHelper(arr, n, i+1, i) //    take it
    memo[i][prev+1] <- max(include, exclude)     // 4. write down the larger
    return memo[i][prev+1]
```

- $$O(2^n)$$ without a memo, $$O(n^2)$$ with one
- `prev + 1` puts `prev = -1` (nothing taken) into column 0

</Slide>

<Slide>

#### Tabulation: the longest that ends here
::sub[One dp cell = the longest increasing subsequence ending at that element]

$$
dp[i] = 1 + \max \{\, dp[j] : j < i,\ arr[j] < arr[i] \,\}
$$

- If there is no such $$j$$, `dp[i] = 1`
- Filling one cell looks at **several** earlier cells.
- The answer is not `dp[n-1]` but **the maximum of `dp`**.
- Recording the chosen $$j$$ in `prev[i]` lets us restore the sequence.
- Time $$O(n^2)$$ · space $$O(n)$$

</Slide>

#### [Aside] The smallest end for each length
::sub[`08_lis_nlogn/lisNlogn.pseudo`]

```plaintext
ALGORITHM LisTails(arr, n)
    len <- 0
    for i <- 0 to n-1 do
        x <- arr[i]
        pos <- LowerBound(tails, len, x)   // first cell >= x, or len
        tails[pos] <- x                    // replace, or append
        if pos = len then len <- len + 1
    return len
```

- One binary search per element, time $$O(n \log n)$$ · space $$O(n)$$
- `tails` is always strictly increasing, so binary search works.
- **Only the length** is right: for `[3, 4, 1]`, `tails` is `[1, 4]`, which is not a subsequence.

#### The recurrence
::sub[S(u, v, k): the minimum cost from u to v using k edges]

$$
S(u, v, k) = \begin{cases}
0 & k = 0,\ u = v \\
\infty & k = 0,\ u \ne v \\
\min\limits_{u \to x} \bigl( w(u, x) + S(x, v, k-1) \bigr) & k > 0
\end{cases}
$$

<br/>

- **Implementation 1**: this, directly as a recursion
- **Implementation 2**: memoization with a `memo[k][u][v]` table
  - Along with each value, record **the cheapest first step** `next[k][u][v]`.

</Slide>

#### Implementation 2: memoization
::sub[`05_shortest_path/shortestPath.pseudo`]

```plaintext
ALGORITHM ShortestMemo(u, v, k, memo, next)
    if k = 0 then
        if u = v then return 0 else return INF
    if memo[k][u][v] != -1 then return memo[k][u][v]
    best <- INF
    for each edge u -> x do
        r <- ShortestMemo(x, v, k-1, memo, next)
        if r != INF and w(u, x) + r < best then
            best <- w(u, x) + r
            next[k][u][v] <- x        // record the cheapest first step
    memo[k][u][v] <- best
    return best
```

</Slide>

#### Path restoration
::sub[Record what you chose when settling a value, and follow it from the start]

```plaintext
ALGORITHM RestorePath(u, v, k, next)
    path <- [u]
    while k > 0 do
        u <- next[k][u][v]            // follow the recorded first step
        append u to path
        k <- k - 1
    return path
```

- Following it

```plaintext
next[3][0][3] = 2    0 → 2   (cost 2)
next[2][2][3] = 4    2 → 4   (cost 3)
next[1][4][3] = 3    4 → 3   (cost 1)
```

#### Implementation 3: tabulation
::sub[`10_shortest_path_tab/shortestPathTab.pseudo`]

```plaintext
ALGORITHM ShortestTab(dst, K)
    for each vertex u do S[0][u] <- INF
    S[0][dst] <- 0
    for k <- 1 to K do                      // layers with fewer edges left first
        for each vertex u do
            S[k][u] <- INF
            for each edge u -> x do
                if S[k-1][x] != INF and w(u, x) + S[k-1][x] < S[k][u] then
                    S[k][u] <- w(u, x) + S[k-1][x]
                    next[k][u] <- x
    return S, next
```

- Every edge once per layer, time $$O(K(V+E))$$ · space $$O(KV)$$
- Without restoration two layers suffice, $$O(V)$$

#### One extra line that records the choice
::sub[choice, prev, next]

- Coin change's `choice`, LIS's `prev`, and `next` here all do the same job.
  - When asked not for "the minimum" but for **how to achieve it**, this line comes along.
- **The direction to follow differs.**
  - `choice` and `prev` hold the **last** choice, so go backwards from the end.
  - `next` holds the **first** step, so go forwards from the start.
- This differs from Dijkstra in Topic 12.
  - Exactly 3 edges are required, so 0 → 2 → 3 (2 edges) is not an answer.

</Slide>

#### A knapsack that cannot be split
::sub[Capacity 50, items (10, 60) (20, 100) (30, 120)]

- Greedy (by value per unit weight) took items 1 and 2 and stopped at **160**.
- Taking items 2 and 3 gives **220**.

$$
dp[i][c] = \begin{cases}
dp[i-1][c] & w_i > c \\
\max\bigl(dp[i-1][c],\ dp[i-1][c - w_i] + v_i\bigr) & w_i \le c
\end{cases}
$$

- Base `dp[0][c] = 0`: no items, value 0
- The cell above: leave item $$i$$
- The cell $$w_i$$ to the left in the row above + $$v_i$$: take item $$i$$

</Slide>

#### One row makes it O(W) space
::sub[Only the row above is needed, so rewrite a single row]

```plaintext
ALGORITHM Knapsack1D(w, v, n, W)
    for c <- 0 to W do dp[c] <- 0
    for i <- 1 to n do
        for c <- W downto w[i] do            // large capacities first
            dp[c] <- max(dp[c], dp[c - w[i]] + v[i])
    return dp[W]
```

- Filling **large capacities first**, `dp[c - w]` is still the value from before item $$i$$.
- Filling **small capacities first**, it refers to a cell that already holds item $$i$$.
  - That answers the **unbounded knapsack**, which reuses items.
- Time stays $$O(nW)$$, but without the table the items **cannot be restored.**

</Slide>

#### When it applies
::sub[When small problems overlap and small answers build the large one]

- **Split like divide and conquer, but the subproblems overlap**
  - Solve the small ones first, store them, and reuse them later.
- **For optimization problems, when there is optimal substructure**
  - Coin change, LIS, path finding, and the knapsack are like this.
  - Greedy follows one candidate; dynamic programming compares **all** of them.
- **Counting problems work too.**
  - Fibonacci and grid paths ask for **a value or a count**, not an optimum.
  - Subproblem answers are simply added, so optimal substructure does not come up.

</Slide>

#### The principle of optimality
::sub[The principle of optimality]

- An optimal solution to an instance of the problem
  - is also optimal for each subinstance it is built from.
- **Example: shortest paths**
  - If $$v_k$$ lies on an optimal path from $$v_i$$ to $$v_j$$,
  - the subpaths from $$v_i$$ to $$v_k$$ and from $$v_k$$ to $$v_j$$ are optimal too.
- **Counterexample: the longest simple path**
  - Making each subpath as long as possible can reuse vertices.

</Slide>

#### Divide and conquer vs. dynamic programming

| | Divide and conquer | Dynamic programming |
| --- | --- | --- |
| Direction | top-down: split going down | bottom-up (tabulation) or top-down (memoization) |
| Subproblems | do not overlap | overlap |
| Efficiency | efficient when subproblems are independent | stores overlapping answers, no recomputation |
| Examples | merge sort, quicksort, binary search | memoized and tabulated Fibonacci, coin change, LIS, knapsack |

<br/>

Recursive Fibonacci has the shape of divide and conquer, but its subproblems overlap, so it is a case for dynamic programming.

</Slide>

#### Order of design
::sub[Start from what one cell of the table means]

1. **Define the subproblem.**
   - In one sentence, like "`dp[a]` is the fewest coins that make `a` won"
2. **Set up the recursive property (the recurrence).**
   - Usually split on one last choice.
3. **Fix the base cases.**
4. **Choose the direction of computation.**
   - For memoization, a table on the recursion; for tabulation, the fill order
5. **If needed, record the choices and restore them.**
   - `choice`, `prev`, `next`, or compare cells again as in the knapsack

</Slide>

#### [Aside] Edit distance
::sub[The fewest edits that turn one word into another]

- Three edits: **delete, insert, replace**
- Split on how the last letters were handled.

$$
dp[i][j] = \begin{cases}
\max(i,\ j) & i = 0 \text{ or } j = 0 \\
dp[i-1][j-1] & a_i = b_j \\
1 + \min\bigl(dp[i-1][j],\ dp[i][j-1],\ dp[i-1][j-1]\bigr) & a_i \ne b_j
\end{cases}
$$

- `dp[i][j]` is the number of edits from the first $$i$$ letters to the first $$j$$, time $$O(nm)$$
- Spell checking and DNA sequence comparison start from this table.

</Slide>

## What to keep

1. **Dynamic programming solves each overlapping subproblem once.**
   - For optimization problems there must be optimal substructure.
2. **Memoization is top-down (lazy); tabulation is bottom-up (eager).**
   - Fibonacci's 15 calls become 9, $$O(2^n)$$ becomes $$O(n)$$
3. **It finds the answers greedy missed.**
   - 80 won is 40 + 40; the 0/1 knapsack is 220
4. **Path restoration: record the choices and follow them.**
   - `choice` and `prev` backwards, `next` forwards; the knapsack compares cells again.
5. **Design starts with defining what one cell of the table is.**
