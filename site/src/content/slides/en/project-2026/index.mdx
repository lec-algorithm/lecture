# Individual project

Compare anything

*Advanced Algorithms*

</Slide>

<Slide>

## There is only one task
::sub[The topic is free; what you do with it is fixed]

- Pick one problem you find interesting.
- Find **three or more existing approaches** that already solve it.
- Run all three under the **same conditions**.
- Explain what is fast where, what breaks down where, and why.
- Write up the trade-offs and where you would take it next.

</Slide>

## Three conditions on the topic
::sub[Meet these three and anything goes]

| Condition | Meaning |
| --- | --- |
| It runs as code | It produces a result and lets you measure time or counts |
| Several approaches exist | Three or more known ways of solving it already exist |
| It can be made public | No data that cannot go into a public repository |

## Decide the criteria first
::sub["Which one is better" cannot be answered without them]

- **Speed**: wall-clock time, or counted comparisons and operations
- **Memory**: the extra space an approach uses
- **Quality of the result**: accuracy, compression ratio, hit rate
- **Behaviour as the input changes**: larger sizes, skewed inputs
- **Implementation cost**: lines of code, hours spent

<br/>

Fix **two or more** of them.  
Anything else you can put a number on works just as well.

</Slide>

<Slide>

### Check the order against the numbers
::sub[The gap between them is where the report lives]

- An approach labelled $$O(n \log n)$$ being slower on small inputs is common.
- Constants, cache behaviour and implementation details show up there.
- Do not let [[time-complexity]] sit in a table and stop there.
  - Check it against what you measured.
  - When they disagree, explain **why** they disagree.

</Slide>

<Slide class="compact">

### Interim submission (October 18)
::sub[About 10 slides, as a PDF]

| Slide | Contents |
| --- | --- |
| 1 | Title, student ID, name |
| 2 | The topic and why you picked it |
| 3 | The problem you are solving, in one sentence |
| 4\~6 | The three approaches, one slide each |
| 7 | Criteria and how you will measure them |
| 8 | Experiment design (input data, sizes, repetitions) |

Those eight must be there; the remaining slides are yours to use.

</Slide>

<Slide>

### Final submission ① the report
::sub[December 13, as a PDF]

1. Topic and motivation
2. The three approaches, explained
3. Criteria and experiment design
4. Results (tables · graphs · screenshots)
5. Interpretation: why the numbers came out this way
6. Trade-offs
7. Where to take it next
8. References and a record of how you used AI

<br/>

At least 5 pages, at most 20.  
Markdown, Word or Hangul, whichever you like. **You submit a PDF.**

</Slide>

<Slide>

### Final submission ② the code
::sub[A reader must be able to run it as written]

- Submitting the GitHub repository **URL is required**. Put it on the first page.
- Also submit the zip from **Code > Download ZIP**.
- Put the run instructions in `README.md`.
- Upload the input data you measured with.
  - If it is large, upload the script that generates it.

</Slide>

## Five things are looked at

- **Code that runs**: all three execute and are compared under the same conditions
- **Measurement**: the criteria are clear and the numbers can be obtained again
- **Interpretation**: the results are tied back to the theory
- **Conclusions**: the trade-offs and next steps are your own judgement
- **Documentation**: someone else can read it and run it

<br/>

How hard the topic is does not count toward the grade.  
An easy topic followed all the way through scores higher.

</Slide>

<Slide>

## Rules

- **You may use AI.**
  - Using it to understand an approach you do not know is encouraged.
  - Record what you asked and what you got back in the report.
- **You may use other people's code.**
  - Cite the source and say what you changed.
  - Code copied without a source receives no credit.
- Write the report and the code in **Korean or English**.
- The repository is public. Do not use data containing personal information.

</Slide>
