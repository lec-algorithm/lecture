### I decide
::sub[Read the draft and edit it yourself]

- **Hash table**: collisions? hash function? when does it grow?
- **Shortener**: the same URL twice? an unknown code?
- **Bad input**: `ftp://`, spaces, very long addresses?
- **Web page**: only an API, or a page to use in the browser?
- **Edge cases**: they become the step 4 tests. Add what is missing.

<br/>

This step is about finding where the AI filled in blanks on its own.  
Leave what you changed as a comment on issue #2.

</Slide>

<Slide class="compact">

### Commit after editing

```text
Step 2, continued (issue #2).
I have edited SPEC.md.
Commit it, merge into develop and push.
```

- Every example request starts with **the step and issue number** and ends with **the commit line**.

</Slide>

<Slide>

### Fixed for this assignment
::sub[You build the hash table yourself]

- Collisions by **separate chaining** (linked lists), hashing by the **Horner method** from Topic 08
- **Linear probing** comes in the homework, built and compared.
- No Python `dict`, `set` or built-in `hash()`.
- The built-in `hash()` gives strings a different value on every run.
  - Rerunning the step 6 experiment would give different numbers.

</Slide>

## Step 3

A plan before code

</Slide>

<Slide class="compact">

### Ask for the plan only

```text
This is step 3, issue #3.
Read SPEC.md, write a step-by-step implementation plan and save it to PLAN.md.
Do not write any code yet.
When done, commit, merge into develop and push.
```

- You may switch the agent mode to **Plan** for this, then back to Autopilot.
- Fixing the plan is much cheaper than fixing the code.

</Slide>

<Slide>

### What you often catch in the plan

- It plans to store URL→code in a **`dict`**.
  - That breaks the specification.
- It plans to make the code **a hash of the URL**.
  - Two different URLs can then get the same code.
  - A serial number in base62 never collides.
- It plans to write the tests **last**.
  - Change the order.

</Slide>

<Slide class="center">

```text

When done, commit, merge into develop and push.
```

### A rules file
::sub[Write it yourself]

### Passing tests do not make a good table
::sub[Measure how the nodes compared change with the load factor]

```text
This is step 6, issue #6.
Create experiments/probe_experiment.py.
Fill a HashTable(max_load=None) with 4093 slots with random URLs.
For load factors from 0.25 to 4,
measure the average number of nodes compared for successful and unsuccessful searches.
Compare them in a table with the theory from Topic 08.
hit ≈ 1 + α/2, miss ≈ α
Save experiments/results.csv and an SVG chart.
Do not use external libraries.
When done, commit, merge into develop and push.
```

</Slide>

### Measured in the sample repository
::sub[M = 4093, random URLs, 2000 unsuccessful searches]

| Load factor | Hit (measured) | Hit (theory) | Miss (measured) | Miss (theory) |
| --- | --- | --- | --- | --- |
| 0.5 | 1.24 | 1.25 | 0.47 | 0.50 |

| 2 | 2.01 | 2.00 | 1.98 | 2.00 |
| 4 | 3.00 | 3.00 | 3.99 | 4.00 |

- It matches the theory well even at load factor 4.
- Linear probing cannot go past load factor 1. The homework measures how it differs.

</Slide>

<Slide>

### Judge the numbers yourself

- At load factor 1, are hits near 1.5 and misses near 1?
- If they are far off, find out why.
  - Was a search in an empty slot counted as 1?
  - Does the hash function differ from the specification?
- Can you read the axis labels and the legend?

### Same shortener, different collisions
::sub[Separate chaining in class, linear probing in the homework]

1. **Linear probing table**: the same interface as `HashTable`
2. **Tests**: wrapping from the last slot to slot 0, a full table
3. **Swap it in**: the shortener tests pass with both tables
4. **Comparison**: same keys, same size, load factors 0.1 to 0.9

### What to compare
::sub[Nodes compared for chaining, slots probed for linear probing]

| Method | Hit | Miss |
| --- | --- | --- |
| Separate chaining | about 1 + α/2 | about α |
| Linear probing | about (1 + 1/(1-α))/2 | about (1 + 1/(1-α)²)/2 |

- Plot measurements and theory in one chart.
- See how the two methods part as the load factor approaches 1.
