## Step 2

I write the specification

</Slide>

<Slide>

### Whatever you leave out, the AI decides
::sub[No requests in this step]

Delete the `TEMPLATE:` line at the top of `SPEC.md` and write it yourself.

- **Hash table**: collisions? hash function? when does it grow?
- **Shortener**: the same URL twice? an unknown code?
- **Bad input**: `ftp://`, spaces, very long addresses?
- **Edge cases**: write them as a list. They become the step 4 tests.

</Slide>

<Slide>

### Fixed for this assignment
::sub[You build the hash table yourself]

- Collisions by **linear probing**, hashing by the **Horner method** from Topic 08
- No Python `dict`, `set` or built-in `hash()`.
- The built-in `hash()` gives strings a different value on every run.
  - Rerunning the step 6 experiment would give different numbers.

</Slide>

## Step 3

A plan before code

</Slide>

<Slide class="compact">

### Ask for the plan only

```text
Read SPEC.md, write a step-by-step implementation plan and save it to PLAN.md.
Do not write any code yet.
```

- You may switch the agent mode to **Plan** for this, then back to Autopilot.
- Fixing the plan is much cheaper than fixing the code.

</Slide>

<Slide>

### What you often catch in the plan

- It plans to store URL→code in a **`dict`**.
  - That breaks the specification.
- It plans to make the code **a hash of the URL**.
  - Two different URLs can then get the same code.
  - A serial number in base62 never collides.
- It plans to write the tests **last**.
  - Change the order.

</Slide>

<Slide class="center">

## Step 4

Tests first, implementation by the agent

</Slide>

<Slide class="compact">

### Tests only, first

```text
Turn the edge cases in section 6 of SPEC.md into unittest tests.
Put them in tests/test_hash_table.py and tests/test_shortener.py.
Do not implement anything yet.
```

- **Read** the tests. Is every edge case there?
- Add what is missing yourself and commit.
- `make test` failing right now is expected.

</Slide>

<Slide class="compact">

### Then the implementation

```text
Implement src/hash_table.py and src/shortener.py in the order of PLAN.md,
and keep fixing them until make test passes.
Do not change the tests.
```

- **"Do not change the tests" matters.**
  - Without it the agent sometimes quietly edits a test it cannot pass.
- When it finishes, read the diff and commit.

</Slide>

::sub[.github/copilot-instructions.md]

| File | When the agent reads it |
| --- | --- |
| `SPEC.md` | When it looks relevant, or when told to |
| `.github/copilot-instructions.md` | **With every request** |

<br/>

Keep the repository's rules in the rules file.  
Put one in your project repository too.

</Slide>

<Slide class="compact">

### A rules file
::sub[Write it yourself]

```md
# To the agent working in this repository

- Read SPEC.md before writing code.
- Do not use dict, set or the built-in hash() inside src/. Use the hash table we built.
- After changing code, run make test and show the result.
- If a test fails, fix the code, not the test.
- For each step, work on a feature branch off develop; when done, commit, merge into develop and push.
- I am a first-year student. Summarize what you changed in at most three lines.
```

- Move the git rule from the first chat here too. A new chat does not know the earlier conversation.

</Slide>

<Slide class="compact">

### Check in a new chat

```text
Check whether the code in src/ follows this repository's rules,
and fix anything that breaks them.
```

- A new chat still reads the rules file.
- Write in `AGENT_LOG.md` which rules had an effect.

</Slide>

## Step 6

Verify the result yourself

</Slide>

<Slide class="compact">

### Passing tests do not make a good table
::sub[Measure how probes change with the load factor]

```text
Create experiments/probe_experiment.py.
Fill a HashTable(max_load=None) of fixed size 4093 with random URLs.
For load factors from 0.1 to 0.9,
measure the average number of slots probed for successful and unsuccessful searches.
Compare them in a table with Knuth's approximations from Topic 08.
hit ≈ (1 + 1/(1-α))/2, miss ≈ (1 + 1/(1-α)²)/2
Save experiments/results.csv and an SVG chart.
Do not use external libraries.
```

</Slide>

<Slide>

### The theory
::sub[Topic 08 · it gets sharply worse near 1]

<LoadCostDemo slide />

</Slide>

<Slide class="compact">

### Measured in the sample repository
::sub[M = 4093, random URLs, 2000 unsuccessful searches]

| Load factor | Hit (measured) | Hit (theory) | Miss (measured) | Miss (theory) |
| --- | --- | --- | --- | --- |
| 0.5 | 1.55 | 1.50 | 2.62 | 2.50 |
| 0.7 | 2.19 | 2.17 | 5.63 | 6.06 |
| 0.8 | 3.07 | 3.00 | 13.11 | 13.00 |
| 0.9 | 5.14 | 5.50 | 64.44 | 50.50 |

- Up to 0.8 it matches the theory well.
- At 0.9 the miss cost swings a lot. Why?

</Slide>

<Slide>

### Judge the numbers yourself

- At load factor 1/2, are hits near 1.5 and misses near 2.5?
- If they are far off, find out why.
  - Was the first slot counted as 0?
  - Does the hash function differ from the specification?
- Can you read the axis labels and the legend?

</Slide>

## Habits to take home

1. Decide what to build **in a specification** first.
2. Get **a plan** before code.
3. Speak **in tests**, and say not to change them.
4. Keep rules **in a rules file**.
5. Check results **by running them**, and **commit** every step.
