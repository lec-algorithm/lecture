# Hash Tables

Topic 08

*Advanced Algorithms*

## Finding without comparing
::sub[The binary search tree of Topic 07 searched by comparing]

- **Binary search tree**: goes down comparing keys. Even balanced, $$O(\log n)$$
- **Hash table**: **computes the slot straight** from the key. $$O(1)$$ on average

<br/>

That computation is the hash function.  
Everything else is how to resolve collisions, where different keys point to the same slot.

</Slide>

<Slide class="center">

## Keys as array indices
::sub[Key as an Index]

</Slide>

<Slide class="compact">

#### If the key were the address
::sub[The item with key i goes in slot i of the array]

```plaintext
slot  1   2   3   4   5   6   7   8
     [ ] [ ] [3] [ ] [5] [ ] [ ] [8]

find 3?  -> look at A[3]. It is there.
find 5?  -> look at A[5]. It is there.
find 7?  -> look at A[7]. Empty, so it is not there.
```

Not a single comparison.  
Any key takes one memory access: $$O(1)$$.

</Slide>

<Slide>

#### Hashing
::sub[This method extended to keys that are not small integers]

- We want to do the same with **keys that are large or not integers**: ID numbers, names, student IDs, strings.
- That takes two things.
  - **Hash function**: a computation that turns a key into an array index
  - **Collision resolution**: what to do when different keys turn into the same index

</Slide>

<Slide>

#### Between time and memory
::sub[Hashing finds a balance point between two extremes]

| If memory is | What you can do | The price |
| --- | --- | --- |
| unlimited | give every key its own slot | memory ($$10^{13}$$ slots) |
| very scarce | gather everything in one array and search sequentially | time ($$O(n)$$) |
| moderate | **hashing**: scatter, then handle only the overlaps | a little of both |

</Slide>

<Slide>

#### The café stamp-card rack
::sub[There is a slot for each first letter of a customer's name]

- To find a card, you go through **one slot**, not the whole box.
- **Picking the first letter** is the hash function.
- **Several cards in one slot** is a collision.

<br/>

There are far fewer slots than customers, so it uses little memory,  
and you only go through one slot, so it takes little time.

</Slide>

## Hash functions
::sub[Hash Function]

</Slide>

<Slide>

#### A good hash function
::sub[It turns a key into an array index]

1. **The result is always an integer in $$[0, M-1]$$.**
2. **It is easy to compute.**
3. **It spreads the keys evenly over the whole array.**

<br/>

- **ID numbers**: if it is a number, use the number as it is.
- **Names**: if it is a string, turn it into a number.
- **Your own data types**: you have to write the hash function yourself.

</Slide>

<Slide>

#### Modular hashing
::sub[The most common way to hash integers]

<div class="aas-split">
<div>

$$
h(k) = k \bmod M
$$

- The **remainder** of the key divided by the array size $$M$$
- The remainder is always in $$[0, M-1]$$
- A single division, so it is easy to compute.

</div>
<div>

| Key | Code | Hash ($$M = 8$$) |
| --- | --- | --- |
| A | 65 | 1 |
| B | 66 | 2 |
| C | 67 | 3 |
| K | 75 | 3 |

</div>
</div>

#### Why a prime
::sub[It helps spread the resulting indices evenly]

- With $$M = 8$$, only **2 of the eight slots** are used.
  - The keys and $$M$$ share the common factor 4.
- With $$M = 7$$, the keys spread over **all 7 slots**.
  - A prime shares no common factor with any key that is not its multiple.
- It is not a cure-all, though.
  - Had every key been a multiple of 7, $$M = 7$$ would also use just one slot.

</Slide>

<Slide>

#### Hashing strings
::sub[A string is turned into a number first]

- **Adding up the character codes**
  - `stop`, `pots`, `tops`, `spot`, `opts`, and `post` all get the same value.
  - It ignores the order of the characters.
- **Horner's method**
  - Multiply the value so far by $$R$$ (usually 31) and add the next character.
  - Taking the remainder mod $$M$$ each time keeps the value from growing.

$$
h \leftarrow (R \cdot h + \text{code}(c)) \bmod M
$$

</Slide>

<Slide class="compact">

#### Adding vs. Horner's method
::sub[`01_hash_function/` · M = 97]

<div class="aas-split">
<div>

```c
int hornerHash(const char *s, int m) {
    const int R = 31;
    int h = 0;
    for (int i = 0; s[i] != '\0'; i++) {
        h = (R * h + (unsigned char)s[i]) % m;
    }
    return h;
}
```

</div>
<div>

```console
string keys, M = 97
  key   sum  horner
  stop   66       9
  pots   66      79
  tops   66       3
  spot   66      49
  opts   66      58
  post   66      49
```

</div>
</div>

Adding puts the six words in **one slot**; Horner's method uses **five slots**.  
`spot` and `post` still meet. A good hash function only **reduces** collisions.

</Slide>

## Collisions are unavoidable
::sub[Collisions Are Unavoidable]

</Slide>

<Slide>

#### Two reasons they cannot be avoided

- **The pigeonhole principle**
  - With more keys than slots ($$N > M$$), some slot gets two or more.
  - The values a key could take always far outnumber the array size.
- **The birthday problem**
  - Even with far fewer keys than slots, collisions come quickly.
  - In a group of 23 people, the chance that two share a birthday is more than half.

$$
P(\text{collision}) = 1 - \frac{M}{M} \cdot \frac{M-1}{M} \cdots \frac{M-N+1}{M}
$$

</Slide>

<Slide class="compact">

#### How quickly they come
::sub[The last block of `01_hash_function/`]

- Run

```console
chance of at least one collision
  N =  3, M =  16:  18.0%
  N =  5, M =  16:  50.0%
  N = 10, M =  16:  97.4%
  N = 23, M = 365:  50.7%
```

Just **5 keys** in 16 slots and the chance of a collision is one half. With 10, it is nearly certain.  
A hash table must have a way to **handle** collisions, not avoid them.

</Slide>

<Slide>

#### Two ways to resolve collisions
::sub[Collision Resolution]

1. **Separate chaining**
   - Keep a linked list in each slot and hang the colliding keys on it.
2. **Linear probing**
   - On a collision, go find the next empty slot in the array.

</Slide>

<Slide>

## 1) Separate chaining
::sub[Separate Chaining]

</Slide>

<Slide>

#### A linked list per slot
::sub[Items with the same hash value are stored in one list]

- Each slot of an array of size $$M$$ holds a **linked list**.
- Colliding items are kept in a **separate list** for each slot.
- Finding a key is a **two-step search**.
  1. **Hash search**: pick the slot with the hash function.
  2. **List search**: search that slot's list sequentially.
- The lists must be short, so $$M$$ is chosen large enough.

</Slide>

<Slide>

### One step at a time: insertion
::sub[Hash to the slot and walk the list. Same key: change only the value; otherwise attach at the front]

<ChainingDemo slide />

</Slide>

<Slide class="compact">

#### The insertion procedure
::sub[`02_hash_table_sc/hashTableSC.pseudo`]

```plaintext
ALGORITHM Put(T, key, value)            // T: array of size M, a linked list per slot
    i <- Hash(key, M)
    for node x in T[i] do               // step 1: find the slot by hashing
        if x.key = key then             // step 2: search that slot's list in order
            x.value <- value            // same key found: only change the value
            return
    T[i] <- new node(key, value, next = T[i])  // not found: attach at the front
    N <- N + 1
```

- It walks to the end anyway to check for the same key.
- Attaching at the front means no need to go find the end of the list.

</Slide>

<Slide class="compact">

#### In code
::sub[`02_hash_table_sc/hashTableSC.c`]

```c
int put(ChainingTable *t, char key, int value, int *compares) {
    int i = hashOf(key, t->m);
    *compares = 0;
    for (Node *x = t->heads[i]; x != NULL; x = x->next) {
        (*compares)++;
        if (x->key == key) {
            x->value = value;
            return 0;
        }
    }
    Node *node = malloc(sizeof(Node));
    node->key = key;  node->value = value;
    node->next = t->heads[i];   /* attach at the front */
    t->heads[i] = node;  t->n++;
    return 1;
}
```

</Slide>

#### The cost of separate chaining
::sub[The average list length is N/M: this is the load factor α]

| Operation | Average | Worst (every key in one slot) |
| --- | --- | --- |
| Search, insert, delete | $$O(1 + N/M)$$ | $$O(N)$$ |

<br/>

- Choose $$M$$ proportional to $$N$$ and it is $$O(1)$$ on average.
- **If $$M$$ is too large**, there are many empty lists, and memory is wasted.
- **If $$M$$ is too small**, the lists grow long, and searching slows down.

</Slide>

## 2) Linear probing
::sub[Linear Probing]

</Slide>

<Slide>

#### Open addressing
::sub[Open Addressing]

- If the array is larger than the number of keys ($$M > N$$), there is always an empty slot left.
- A collision is resolved by putting the key into **an empty slot that is already there**.
- The memory that list links would take goes into a bigger array.

<br/>

**Linear probing** is its simplest form.  
On a collision, look at the **next slot** of the table and move right until an empty slot turns up.  
On reaching the end of the array, wrap around to 0.

</Slide>

<Slide>

### One step at a time: insertion
::sub[A key starts at its hash slot and slides. The orange bar marks a run of full slots]

<ProbingDemo slide />

</Slide>

<Slide>

#### Three scenes worth watching
::sub[The large floating number is how many slots were probed]

- **`H` (hash 4) takes 4 probes**
  - It bumps into `A` at 4, `C` at 5, and `S` at 6, and goes into 7.
- **`P` (hash 14) goes to slot 0**
  - It passes `R` at 14 and `X` at 15 and goes past the end of the array.
- **`L` (hash 6) also bumps into slot 7, held by `H`.**
  - `H` was at 7 because of the collision at slot 4.
  - Collisions breed collisions.

</Slide>

<Slide class="compact">

#### The insertion and search procedures
::sub[`03_hash_table_lp/hashTableLP.pseudo`]

```plaintext
ALGORITHM Put(T, key, value)
    i <- Hash(key, M)
    while T.keys[i] ≠ EMPTY do          // move right until an empty slot
        if T.keys[i] = key then
            T.values[i] <- value        // same key found: only change the value
            return
        i <- (i + 1) mod M              // past the end, wrap around to slot 0
    T.keys[i] <- key, T.values[i] <- value

ALGORITHM Get(T, key)
    i <- Hash(key, M)
    while T.keys[i] ≠ EMPTY do
        if T.keys[i] = key then return T.values[i]
        i <- (i + 1) mod M
    return none                         // an empty slot means the key is not there
```

</Slide>

<Slide>

### One step at a time: search

#### Why it is safe to stop at an empty slot

- Had the key been there, it would have gone into **that empty slot** at the latest.
- So **an empty slot means "nothing beyond here."**

<br/>

The missing key `Y` took 2 comparisons in chaining, but 6 probes in linear probing.  
That is because of the **cluster** running from 4 to 8.

</Slide>

#### The deletion procedure
::sub[`03_hash_table_lp/hashTableLP.pseudo`]

```plaintext
ALGORITHM Delete(T, key)
    i <- Hash(key, M)
    while T.keys[i] ≠ key do            // find the key first
        if T.keys[i] = EMPTY then return fail
        i <- (i + 1) mod M
    T.keys[i] <- EMPTY, N <- N - 1
    i <- (i + 1) mod M
    while T.keys[i] ≠ EMPTY do          // the keys that followed in the same cluster
        k, v <- T.keys[i], T.values[i]
        T.keys[i] <- EMPTY, N <- N - 1
        Put(T, k, v)                    // take out and put back in
        i <- (i + 1) mod M
    if 0 < N ≤ M/8 then Resize(T, M/2)  // too empty: halve it
```

The keys put back amount to one cluster, so when clusters are short, deletion is cheap too.

</Slide>

<Slide>

#### Another way: tombstones
::sub[Tombstone, lazy deletion]

- Leave only a **marker** in the erased slot and do not actually empty it.
  - `get` passes a marker **as if the slot were full**.
  - `put` reuses a marker **as if the slot were empty**.
- **`put` must not insert into the first marked slot right away.**
  - A trap implementations often fall into.
  - The same key may still be alive further along.
  - Go on to an empty slot, confirm the key is not there, then insert into the first marked slot.
- **Markers pile up.**
  - When there are many, rebuild the table to clean it.

</Slide>

<Slide class="compact">

#### Resizing
::sub[Grow and shrink by the load factor. Hash values change, so every key goes in again]

- **On insert**: double it when at least a certain fraction full (it differs by implementation; this example uses 0.7)
- **On delete**: halve it when $$0 < N \le M/8$$

## Clusters and the load factor
::sub[Clustering and Load Factor]

</Slide>

<Slide>

#### Clusters grow on their own
::sub[A run of full slots with no empty slot in between]

- In the example, slots 4 to 8 (`A C S H L`) form a cluster of length 5.
- **Wherever** a new key's hash lands inside a cluster, it goes into the slot just past the cluster's end.
  - The longer the cluster, the more likely it is to take in a key.
- Each key that goes in lengthens the cluster, and sometimes joins it to the next one.
  - When `P` went into 0, slots 14, 15, and 1 became one run.
- When a cluster is long, a search has to walk to the end of it.

</Slide>

#### What the load factor costs
::sub[Average number of slots probed when α = N/M (Knuth)]

$$
\text{success} \approx \frac{1}{2}\left(1 + \frac{1}{1-\alpha}\right) \qquad
\text{failure} \approx \frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)
$$

| Load factor $$\alpha$$ | Successful search | Failed search |
| --- | --- | --- |
| 1/2 | 1.5 | 2.5 |
| 3/4 | 2.5 | 8.5 |
| 7/8 | 4.5 | 32.5 |

It gets worse **sharply** as it nears 1. So $$\alpha$$ is kept near 1/2.

</Slide>

## Summary
::sub[Wrapping up]

</Slide>

<Slide>

#### Comparing the two methods

| | Separate chaining | Linear probing |
| --- | --- | --- |
| Where a colliding key goes | that slot's linked list | the next empty slot in the array |
| Load factor | may exceed 1 | must be below 1 (usually near 1/2) |
| Extra memory | a link per node | empty slots |
| Deletion | change just one link | put back, or tombstones |
| What hurts performance | long lists | long clusters |
| Memory access | nodes are scattered | neighboring slots in order |

</Slide>

<Slide>

#### Memory
::sub[By the Java measure of Sedgewick's textbook, with keys and values as reference types]

| Method | Space for $$N$$ keys |
| --- | --- |
| Separate chaining | about $$48N + 32M$$ bytes |
| Linear probing | between about $$32N$$ and $$128N$$ bytes |
| Binary search tree | about $$56N$$ bytes |

<br/>

- Chaining spends memory on links; linear probing spends it on empty slots.
- The range for linear probing is because the array is between 1/8 and 1/2 full.

</Slide>

<Slide>

#### Where hash tables fit
::sub[When you want fast search and do not care about the sorted order of the records]

| | Binary search tree (balanced) | Hash table |
| --- | --- | --- |
| Search, insert, delete | $$O(\log N)$$ | $$O(1)$$ on average |
| Worst case | $$O(\log N)$$ | $$O(N)$$ (bad hash) |
| Minimum, range search | yes | no |
| What keys need | comparison | a hash function and an equality test |

</Slide>

<Slide>

#### Hashing is no cure-all

- Every key type needs a **good hash function**.
- The performance guarantee depends on the **quality** of the hash function.
- Computing the hash function can be hard and take many operations.
- **Order-related operations** are not easy.
  - The smallest key, the next key, range search

<br/>

If you need order, use a binary search tree; if you only want speed, use a hash table.

</Slide>

## What to keep

1. **Hashing computes an index from the key and finds it without comparisons.**
   - A good hash function stays in range, is easy to compute, and spreads keys evenly.
2. **Collisions are unavoidable.**
   - The pigeonhole principle and the birthday problem
3. **Separate chaining keeps a list per slot.**
   - $$O(1 + N/M)$$ on average, and deletion is easy.
4. **Linear probing moves to the next slot.**
   - Just erasing cuts the path, so the following keys are put back in.
5. **As the load factor nears 1, clusters grow and it slows down sharply.**
   - Resizing keeps it near 1/2.
