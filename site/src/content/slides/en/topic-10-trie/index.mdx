## Split the key to store it
::sub[Topic 07 was the binary search tree, Topic 08 the hash table]

- **Binary search tree**: walks down comparing whole keys.
- **Hash table**: hashes the whole key.
- **Trie**: **splits a string key into characters** and stores it as a path in a tree.

<br/>

Lookup time depends not on how many keys there are but on **how many characters the key has**.  
Finding every key with a given prefix comes for free.

</Slide>

<Slide>

#### A little more efficient
::sub[Properties that hold even for a very large table]

- **On a search hit**
  - The time is proportional to the length of the key.
- **On a search miss**
  - Only a few characters are examined.

</Slide>

<Slide class="center">

## Tries
::sub[Trie · prefix tree, digital tree]

</Slide>

<Slide>

#### The trie
::sub[The name comes from retrieval]

- A tree built for string search.
  - Also called a prefix tree or a digital tree.
- A structure designed for storing and searching a set of strings.
- Each node stands for one character.
  - The path from the root to a node spells out a string.
- The value goes in the node for the key's last character.

</Slide>

<Slide>

#### The node
::sub[TrieNode]

- **children[26]**: an array of links to the next nodes
  - The character is used directly as an index: `b` is slot 1, `s` is slot 18
- **hasValue**: whether some key ends at this node
- **value**: that key's value

<TrieFigure kind="node" chars="bst" caption="Root of the trie with six keys: only b, s and t of the 26 slots are used" slide />

</Slide>

<Slide class="compact">

#### The node in code
::sub[`01_trie/trie.c`]

```c
#define ALPHABET_SIZE 26 /* R: alphabet size (a-z) */

typedef struct TrieNode {
    struct TrieNode *children[ALPHABET_SIZE]; /* links a-z, NULL if absent */
    bool hasValue;                            /* does a key end here? */
    int value;                                /* that key's value */
} TrieNode;
```

A missing link is NULL; a new node starts with all 26 slots set to NULL.

</Slide>

#### Reading the picture
::sub[A node's letter is the character of its incoming link]

- The node does not store a letter.
  - Which slot of the parent it hangs from is the letter.
- The blue number next to a node is its value.
  - The last character `e` of `she` holds 0.
- Below the `s` link lie **all keys that start with s**.
  - Below `sh` lie all keys that start with sh.

</Slide>

<Slide>

#### Characteristics
::sub[What it shares and what it wastes]

- **Shared common prefixes**
  - `sea` and `sells` share `se`; `she` and `shells` share `she`.
- **Fast search**: $$O(m)$$ for key length $$m$$
- **Key-value storage**: each word carries its value.
- **Memory-hungry**
  - 26 links per node; only 16 of the 442 are in use.

</Slide>

## Example 1. Trie insertion
::sub[Insert]

</Slide>

<Slide>

#### Insertion
::sub[Walk down from the root, guided by the key's characters]

- **A NULL link before the last character**
  - Create a new node and hang it there.
- **Reaching the last character's node**
  - Store the value in that node.
  - If it already had a value, replace it.

</Slide>

<Slide>

### Step by step: six keys
::sub[Nodes passed are blue, newly created nodes green]

<TrieDemo slide />

</Slide>

<Slide class="compact">

#### Insertion in code
::sub[`01_trie/trie.pseudo`]

```plaintext
ALGORITHM Insert(root, word, value)
    current <- root
    for i <- 0 to length(word)-1 do
        index <- word[i] - 'a'          // character to array index (a=0, b=1, ...)
        if current.children[index] = NULL then
            current.children[index] <- CreateTrieNode()   // no link: new node
        current <- current.children[index]
    current.hasValue <- true            // value goes in the last character's node
    current.value <- value
```

## Trie search
::sub[Search]

</Slide>

<Slide>

#### Search
::sub[Start at the root and follow the key's characters in turn]

- Repeat until a NULL link or the last character.
- **Hit**: the last character's node holds a value.
- **Miss**, in two forms
  - No link to go down.
  - Reached the end, but that node has no value.

</Slide>

<Slide>

### Step by step: four gets
::sub[shells · shell · she · shore]

<TrieDemo mode="search" slide />

<Slide>

#### The four results
::sub[Misses come in two shapes too]

- **get("shells")**: the last `s` holds 3, a hit
- **get("shell")**: we reach the last `l`, but there is no value.
  - `shell` is only a prefix of `shells`, not a key.
- **get("she")**: an inner node is fine if it holds a value; a hit, 0
- **get("shore")**: no `o` link after `sh`.
  - A miss after just three nodes.

</Slide>

<Slide class="compact">

#### Search in code
::sub[`01_trie/trie.pseudo` · the practice code returns -1 on a miss]

```plaintext
ALGORITHM Search(root, word)
    current <- root
    for i <- 0 to length(word)-1 do
        index <- word[i] - 'a'
        if current.children[index] = NULL then
            return -1                   // no link: miss
        current <- current.children[index]
    if current.hasValue then
        return current.value
    return -1                           // node exists but has no value: miss
```

::sub[Type sh into a search box and she, shells, shore appear]

::sub[`01_trie/trie.pseudo` · check the value first, then go down to the children]

```plaintext
ALGORITHM GetAllWordsHelper(node, prefix, results)
    if node = NULL then return
    if node.hasValue then
        append (prefix, node.value) to results
    for i <- 0 to 25 do                 // a to z, so results are alphabetical
        if node.children[i] != NULL then
            GetAllWordsHelper(node.children[i], prefix + ('a' + i), results)
```

`GetWordsWithPrefix` walks down to the prefix's node and then calls this.

## Trie deletion
::sub[Delete]

</Slide>

<Slide>

#### Deletion
::sub[Remove the value, then detach useless nodes from the bottom up]

1. **Search for the key's node and set its value to NULL**
2. **Clean up on the way back**
   - If any child link is non-NULL, delete nothing.
   - If there is no value and all child links are NULL, delete the node.
   - If that leaves all of the parent's child links NULL, delete the parent too.

</Slide>

<Slide>

### Step by step: delete("shells")
::sub[Nodes to delete get a red dashed outline; the node where it stops gets a green ring]

<TrieDemo mode="delete" slide />

</Slide>

<Slide class="compact">

#### Deletion in code
::sub[`01_trie/trie.pseudo` · the root is never deleted]

```plaintext
ALGORITHM DeleteHelper(node, word, index)
    if index = length(word) then        // reached the key's last node
        if not node.hasValue then return false    // no such key
        node.hasValue <- false
        return node has no children at all
    child <- node.children[word[index] - 'a']
    if child = NULL then return false   // no such key
    if DeleteHelper(child, word, index + 1) then
        free child and set that link to NULL
        return (not node.hasValue) and node has no children at all
    return false
```

</Slide>

## Analyzing tries
::sub[Shape, time, space]

</Slide>

<Slide>

#### The key set decides the shape
::sub[The link structure does not depend on insertion or deletion order]

- **Trie**: once the key set is fixed, the shape is fixed.
  - The six keys give the same picture in any order.
- **Binary search tree**: the shape depends on insertion order.
  - Inserted in sorted order, it becomes a single line: the worst case from Topic 07.

</Slide>

<Slide>

#### A binary search tree follows the order
::sub[The tree built by inserting 5, 3, 9, 4, 7, 12, 6, 8, 20]

<TreeFigure tree={{ v: "5", l: { v: "3", r: { v: "4" } }, r: { v: "9", l: { v: "7", l: { v: "6" }, r: { v: "8" } }, r: { v: "12", r: { v: "20" } } } }} slide />

Insert the same numbers as 3, 4, 5, …, 20 and you get a single line leaning right.

</Slide>

<Slide>

#### Worst case for search and insertion
::sub[Nodes passed when searching for or inserting a key]

- At most **the key length plus 1**, root included.
  - One link per character; stop at the end of the key.
  - Written recursively, the depth starts at 0 and stops at the key length.
- $$O(m)$$ for key length $$m$$
  - **No matter how many keys there are.**

<br/>

From the output: `shells` (6 letters) gives `visited 7`

</Slide>

<Slide>

#### Expected cost of a search miss
::sub[A trie built from N random keys over an alphabet of size R]

- A search miss examines about $$\log_R N$$ nodes on average.
- **The time for a search miss does not depend on the key length.**
  - Look up `xmcwkeicowalcoeks` in an English dictionary and three or four letters tell you it is not there.
- In a trie holding a million random keys
  - 7-character plates or 20-digit account numbers alike, a miss ends after four or five nodes.

</Slide>

<Slide class="compact">

#### Experiment: random 7-letter keys
::sub[`01_trie/` · average nodes passed (root included) over 1000 random searches]

Each tenfold increase in keys adds about 0.6\~0.7 nodes.  
$$\log_{26} 10 \approx 0.71$$, so it grows like $$\log_R N$$.

</Slide>

<Slide>

#### Space
::sub[N keys over an alphabet of size R, average key length w]

- Every node has $$R$$ links.
- The number of links is **between $$RN$$ and $$RNw$$**.
  - The root's $$R$$ links are counted separately.
- **Short keys, or many shared prefixes**: close to $$RN$$.
- **Long keys that differ from each other**: close to $$RNw$$.
- Reducing $$R$$ can save a great deal of space.

</Slide>

#### Removing one-way branches
::sub[Compressed trie (radix tree, Patricia trie)]

- Merge each node with no value and a single child into the node below.
  - Only the branching points remain, and nodes carry string fragments.
- We do not implement it in this topic.

<br/>

Instead we move on to the TST, which **cuts the number of links itself**.

## TST
::sub[Ternary Search Tree]

</Slide>

<Slide>

#### Overview
::sub[A memory-efficient variant of the trie]

- Each node has **only 3** child links.
  - It avoids the trie's excessive space consumption.
- It stores characters in a structure similar to a binary search tree.
  - In a trie, the position of a link was the character.
  - In a TST, **the node holds the character itself**.

</Slide>

<Slide>

#### Three links
::sub[One trie node becomes a small binary search tree]

- **left**: a smaller character at the same position
- **middle**: the character at the next position, once this one matches
- **right**: a larger character at the same position

<br/>

Left and right stay at **the same position**; only the middle moves to **the next position**.

</Slide>

<Slide>

#### The same six keys as a TST
::sub[The first-position b, s, t form a binary search tree · small dots are empty links]

<TrieFigure kind="tst" words={[["by", 4], ["sea", 2], ["sells", 1], ["she", 0], ["shells", 3], ["the", 5]]} counts slide />

</Slide>

<Slide class="compact">

#### The node in code
::sub[`02_tst/tst.c` · the trie had 17 nodes and 442 links]

```c
typedef struct TSTNode {
    char data;               /* the character this node stands for */
    bool hasValue;           /* does a key end here? */
    int value;               /* that key's value */
    struct TSTNode *left;    /* smaller than data (same position) */
    struct TSTNode *middle;  /* character at the next position */
    struct TSTNode *right;   /* larger than data (same position) */
} TSTNode;
```

The same six keys take 16 nodes and 48 links.

</Slide>

## Example 2. TST insertion
::sub[apple · application · apply · applaud · applet · appliance · applicable]

</Slide>

<Slide>

#### TST insertion
::sub[Compare the current character with the node's character]

- **If there is nothing**, create a new node.
- **Smaller goes left, larger goes right**
  - Keep looking for the character at the same position.
- **Equal goes down the middle**
  - Only here do we move on to the next character.
  - If it was the last character, store the value in that node.

</Slide>

#### Inserting appliance
::sub[One comparison at a time]

- To place `i`, `e` is already there and `e < i`
  - Go right.
- To place `i`, `i` is already there and `i == i`
  - Move on to the next character here.
- To place `a`, `c` is already there and `a < c`
  - Go left.
- That spot is empty, so fill it with new nodes `a n c e`.

</Slide>

<Slide class="compact">

#### Insertion in code
::sub[`02_tst/tst.pseudo` · left and right keep index; only the middle uses index+1]

```plaintext
ALGORITHM Insert(root, word, value, index)
    c <- word[index]
    if root = NULL then
        root <- CreateTSTNode(c)        // nothing here: new node
    if c < root.data then
        root.left <- Insert(root.left, word, value, index)        // same position
    else if c > root.data then
        root.right <- Insert(root.right, word, value, index)      // same position
    else if index < length(word)-1 then
        root.middle <- Insert(root.middle, word, value, index+1)  // next position
    else
        root.hasValue <- true           // last character: store the value
        root.value <- value
    return root
```

#### TST prefix search
::sub[Say we search with the prefix app]

1. **Come to the node for p, the last letter of app.**
   - If that node holds a value, the prefix itself is a key.
2. **Collect only below that node's middle link.**
   - Left and right are other characters at the same position, so skip them.
3. **Visit left, self, middle, right.**
   - This is an in-order traversal of a binary search tree, so the results are alphabetical.

</Slide>

#### Collecting in code
::sub[`02_tst/tst.pseudo` · left and right pass the prefix unchanged; only the middle appends a character]

```plaintext
ALGORITHM GetAllWordsHelper(node, prefix, results)
    if node = NULL then return
    GetAllWordsHelper(node.left, prefix, results)            // same position, smaller
    if node.hasValue then
        append (prefix + node.data, node.value) to results
    GetAllWordsHelper(node.middle, prefix + node.data, results)   // next position
    GetAllWordsHelper(node.right, prefix, results)           // same position, larger
```

`GetWordsWithPrefix` finds the prefix's node and calls this on its `middle`.

## Tries and TSTs
::sub[Trie vs. TST]

</Slide>

<Slide>

#### Side by side
::sub[Links counted with the same 7 keys (apple..) · n is the number of keys, m the key length]

| Property | Trie | TST |
| --- | --- | --- |
| Links per node | $$R$$ (26 for lowercase English) | 3 |
| Links for the same 7 keys | 650 | 72 |
| Finding the next node | direct array index | binary search at the same position |
| Search hit | $$m + 1$$ nodes | $$m$$ middle steps + a few sideways |
| Search miss | about $$\log_R n$$ on average | about $$\ln n$$ compares on average |
| Shape | independent of insertion order | depends on insertion order |
| Implementation | simple | moderate |

</Slide>

<Slide>

#### TST search time
::sub[The usual bound is generous]

- It is often written as $$O(m \log n)$$, but the real cost is far smaller.
- Looking up `cat`
  - **Trie**: one array slot per character, three $$O(1)$$ accesses
  - **TST**: a small binary search tree per position; $$O(\log k)$$ for $$k$$ distinct characters
- The sideways steps are **not paid for every character**.
  - Once keys diverge in the first few positions, few characters remain at each position.
  - Sedgewick: for random keys a search hit takes about $$m + \ln n$$ compares on average
- From the output: `applaud` (7 letters) 8 nodes, `application` (11 letters) 12 nodes

</Slide>

<Slide>

#### Trade-off
::sub[What you save and what you give up]

- **Trie**: fast search, $$O(m)$$, at the price of a lot of memory
- **TST**: little memory, at the price of slightly slower search

<br/>

Cache efficiency is left out of the table.  
A trie node is large and mostly empty; a TST node is small but the search follows more pointers.  
Which one wins depends on the implementation.

</Slide>

<Slide>

#### Side by side as symbol tables
::sub[With Topics 07 and 08 · n is the number of keys, m the key length]

| | Binary search tree | Hash table | Trie | TST |
| --- | --- | --- | --- | --- |
| Unit of key handling | compares whole keys | hashes the whole key | one character at a time | one character at a time |
| Search (average) | $$O(\log n)$$ comparisons | $$O(m)$$ | $$O(m)$$ | about $$m + \ln n$$ compares |
| Keys in sorted order | in-order traversal | no | a-to-z traversal | in-order traversal |
| All keys with a prefix | via a range search | no | natural | natural |
| Space | $$n$$ nodes | table + collision handling | $$R$$ per node | 3 per node |

</Slide>

## What to keep

1. **A trie stores a key one character at a time along a path.**
   - $$R$$ links per node; the value goes in the last character's node.
2. **Search and insertion grow with the key length, not the number of keys.**
   - A search miss ends after about $$\log_R n$$ nodes on average.
3. **Every key with a prefix lies below the prefix's node.**
   - Deletion removes the value and detaches empty nodes from the bottom up.
4. **Most of a trie's links are NULL.**
   - The link count lies between $$RN$$ and $$RNw$$.
5. **A TST cuts the links down to 3.**
   - Smaller goes left, larger goes right, equal goes down the middle to the next character.

</Slide>
