# 개인프로젝트

무엇이든 비교하기

*고급알고리즘*

</Slide>

<Slide>

## 하는 일은 하나입니다
::sub[주제는 자유, 하는 일은 고정]

- 관심 있는 문제를 하나 고릅니다.
- 그 문제를 이미 푸는 **기존 방식 셋 이상**을 찾습니다.
- 셋을 **같은 조건**에서 직접 돌립니다.
- 어디서 빠르고 어디서 무너지는지, 왜 그런지를 설명합니다.
- 장단점을 정리하고 발전 방향을 적습니다.

</Slide>

<Slide>

### 과제1과 같은 틀입니다
::sub[바뀌는 것은 비교 대상뿐입니다]

| | 과제1 | 개인프로젝트 |
| --- | --- | --- |
| 주제 | 정렬로 정해져 있음 | 자유롭게 고름 |
| 비교 대상 | 정렬 알고리즘 셋 | 고른 주제를 푸는 방식 셋 |
| 제출 | 한 번 | 두 번 (중간 · 최종) |

<br/>

정렬 셋을 골라 재고 비교했던 그 절차를,  
이번에는 **본인이 고른 문제**에 그대로 적용합니다.

</Slide>

<Slide>

## 제출은 두 번입니다

| 단계 | 내는 것 | 마감 |
| --- | --- | --- |
| 중간 제출 | 슬라이드 10장 (PDF) | 10월 18일 23:59 |
| 최종 제출 | 보고서 (PDF) · 코드 (URL + ZIP) | 12월 13일 23:59 |

<br/>

중간 제출은 **계획**을 봅니다. 결과가 없어도 됩니다.  
최종 제출은 **실제로 돌린 결과**를 봅니다.

</Slide>

<Slide>

## 주제의 조건은 셋입니다
::sub[이 셋만 지키면 무엇이든 됩니다]

| 조건 | 뜻 |
| --- | --- |
| 코드로 돌아갈 것 | 결과가 나오고, 시간이나 횟수를 잴 수 있어야 함 |
| 방식이 여럿일 것 | 같은 문제를 푸는 방법이 이미 셋 이상 있어야 함 |
| 공개할 수 있을 것 | 공개 저장소에 올릴 수 없는 데이터는 쓰지 않음 |

</Slide>

### 주제 예시 ①
::sub[데이터와 코드 쪽]

| 분야 | 비교해 볼 만한 것 |
| --- | --- |
| 문자열 | 부분 문자열 검색 (단순 비교 · KMP · 보이어-무어 · 라빈-카프) |
| 압축 | 파일 압축 (허프만 · RLE · LZ77) |
| 경로 | 지도 위 최단 경로 (BFS · 다익스트라 · A\*) |
| 자료구조 | 자동완성 (정렬 배열 이진 탐색 · 트라이 · 해시) |
| 생성 | 미로 생성 (재귀 백트래킹 · 프림 · 크루스칼) |
| 데이터 | 중복 제거 (해시 · 정렬 후 스캔 · 블룸 필터) |

</Slide>

### 주제 예시 ②
::sub[컴퓨터 분야에 한정되지 않습니다]

| 분야 | 비교해 볼 만한 것 |
| --- | --- |
| 통신 | 오류 정정 부호 (해밍 · CRC · 리드-솔로몬) |
| 신호 · 회로 | 신호에서 주파수 찾기 (DFT 직접 계산 · FFT · 자기상관) |
| 나노 · 재료 | 격자 위 확산 시뮬레이션 (오일러 · 룽게-쿠타 · 몬테카를로) |
| 생물 | DNA 서열 정렬 (니들만-분쉬 · 스미스-워터만 · BLAST식 휴리스틱) |
| 추천 | 영화나 음악 추천 (인기순 · 협업 필터링 · 콘텐츠 기반) |
| 이미지 | 이미지 축소 (최근접 이웃 · 이중선형 보간 · seam carving) |

## 비교 기준을 먼저 정합니다
::sub["무엇이 더 좋은가"는 기준 없이 답할 수 없습니다]

- **속도**: 실행 시간, 또는 비교 횟수나 연산 횟수
- **메모리**: 추가로 쓰는 공간
- **결과의 품질**: 정확도, 압축률, 적중률
- **입력에 따른 변화**: 크기를 키울 때, 치우친 입력을 줄 때
- **구현 난이도**: 코드 길이, 붙잡고 있던 시간

<br/>

기준은 **둘 이상** 정합니다.  
이것 이외에도 수치로 나타낼 수 있는 항목이면 됩니다.

</Slide>

### 표에 적힌 차수와 잰 숫자를 맞춰 봅니다
::sub[어긋나는 자리가 보고서의 핵심입니다]

- $$O(n \log n)$$으로 적힌 방식이 작은 입력에서 더 느린 일은 흔합니다.
- 상수와 캐시, 구현의 차이가 거기서 드러납니다.
- [[time-complexity|시간 복잡도]]를 표에 적고 끝내지 않습니다.
  - 실제로 잰 숫자와 맞는지 확인합니다.
  - 어긋나면 **왜 어긋나는지**를 설명합니다.

</Slide>

## 평가에서 보는 다섯 가지

- **돌아가는 코드**: 셋이 실제로 실행되고 같은 조건에서 비교되었는가
- **측정**: 기준이 분명하고 숫자를 다시 얻을 수 있는가
- **해석**: 결과를 이론과 이어서 설명했는가
- **정리**: 장단점과 발전 방향이 본인의 판단인가
- **문서**: 남이 읽고 그대로 돌려 볼 수 있는가

<br/>

주제가 얼마나 어려운지는 점수에 넣지 않습니다.  
쉬운 주제를 끝까지 파고든 쪽이 높습니다.

</Slide>

## 지켜야 할 것

- **AI를 써도 됩니다.**
  - 모르는 방식을 이해하는 데 쓰는 것은 오히려 권합니다.
  - 무엇을 묻고 무엇을 받았는지 보고서에 적습니다.
- **남의 코드를 가져다 써도 됩니다.**
  - 출처를 적고 어디를 고쳤는지 밝힙니다.
  - 출처 없이 옮긴 코드는 점수를 받지 못합니다.
- 보고서와 코드는 **한국어 또는 영어**로 씁니다.
- 저장소는 공개됩니다. 개인정보가 든 데이터는 쓰지 않습니다.
