## 不比较也能找到
::sub[主题 07 的二叉搜索树是一边比较一边找]

- **二叉搜索树**：一边比较键一边往下走。即使平衡也要 $$O(\log n)$$
- **哈希表**：从键**直接算出位置**。平均 $$O(1)$$

<br/>

这个计算就是哈希函数。  
不同的键指向同一个位置叫作冲突，如何解决冲突就是剩下的全部内容。

</Slide>

<Slide class="center">

## 把键当作数组下标
::sub[Key as an Index]

</Slide>

<Slide class="compact">

#### 如果键就是地址
::sub[把键为 i 的项放在数组的 i 号格]

```plaintext
格    1   2   3   4   5   6   7   8
     [ ] [ ] [3] [ ] [5] [ ] [ ] [8]

find 3?  -> 看 A[3]。有。
find 5?  -> 看 A[5]。有。
find 7?  -> 看 A[7]。是空的，所以没有。
```

一次比较都不做。  
无论哪个键，访问一次内存，$$O(1)$$ 就结束。

</Slide>

<Slide>

#### 哈希
::sub[把这种方法推广到不是小整数的键上]

- 像居民登记号、姓名、学号、字符串这样，对**很大或不是整数的键**也想做同样的事。
- 为此需要两样东西。
  - **哈希函数**：把键变成数组下标的计算
  - **冲突解决**：不同的键变成同一个下标时的处理

</Slide>

<Slide>

#### 在时间与内存之间
::sub[哈希在两个极端之间找到平衡点]

| 内存 | 能做的事 | 代价 |
| --- | --- | --- |
| 无限时 | 给每个键各分一格 | 内存（$$10^{13}$$ 格） |
| 极少时 | 全放进一个数组，顺序查找 | 时间（$$O(n)$$） |
| 适中时 | **哈希**：分散存放，只处理重叠的部分 | 两者各付一点 |

</Slide>

## 哈希函数
::sub[Hash Function]

</Slide>

#### 好的哈希函数
::sub[把键变成数组的下标值]

1. **结果总是落在整数 $$[0, M-1]$$ 之内**。
2. **容易计算**。
3. **把键均匀地散布到整个数组**。

<br/>

- **居民登记号**：是数字就直接用这个数字。
- **姓名**：是字符串就变成数字再用。
- **自定义的数据类型**：要亲自写哈希函数。

</Slide>

<Slide>

#### 取模哈希
::sub[对整数做哈希时最常用的方法]

<div class="aas-split">
<div>

$$
h(k) = k \bmod M
$$

- 键除以数组大小 $$M$$ 的**余数**
- 余数总在 $$[0, M-1]$$ 之内
- 只做一次除法，计算容易。

</div>
<div>

| 键 | 编码 | 哈希 ($$M = 8$$) |
| --- | --- | --- |
| A | 65 | 1 |
| B | 66 | 2 |
| C | 67 | 3 |
| K | 75 | 3 |

</div>

#### 为什么是素数
::sub[有助于让下标变换的结果分布均匀]

- $$M = 8$$ 时，八格中只用到 **2 格**。
  - 因为键和 $$M$$ 有公约数 4。
- $$M = 7$$ 时，键散布到全部 **7 格**。
  - 素数与不是它倍数的任何键都没有公约数。
- 不过它也不是万能的。
  - 如果键全是 7 的倍数，$$M = 7$$ 也只用到一格。

#### 字符串哈希
::sub[字符串要先变成数字]

- **把字符编码加起来**
  - `stop`、`pots`、`tops`、`spot`、`opts`、`post` 全是同一个值。
  - 因为不看字符的顺序。
- **霍纳法**（Horner's method）
  - 把前面的值乘以 $$R$$（通常是 31），再加上下一个字符。
  - 每次取除以 $$M$$ 的余数，值不会变大。

$$
h \leftarrow (R \cdot h + \text{code}(c)) \bmod M
$$

</Slide>

```c
int hornerHash(const char *s, int m) {
    const int R = 31;
    int h = 0;
    for (int i = 0; s[i] != '\0'; i++) {
        h = (R * h + (unsigned char)s[i]) % m;
    }
    return h;
}
```

## 冲突必然发生
::sub[Collisions Are Unavoidable]

</Slide>

<Slide>

#### 无法避免的两个原因

- **鸽巢原理**
  - 键比格子多（$$N > M$$）时，某一格里会有两个以上。
  - 可能成为键的值总是远多于数组大小。
- **生日问题**
  - 即使键远少于格子，冲突也很快就会发生。
  - 23 个人聚在一起，有两人生日相同的概率就超过一半。

$$
P(\text{冲突}) = 1 - \frac{M}{M} \cdot \frac{M-1}{M} \cdots \frac{M-N+1}{M}
$$

</Slide>

<Slide>

### 多少个键就会冲突
::sub[拖动 N 看概率，再随机放一放。两个键落进同一格就会变红]

<BirthdayDemo slide />

</Slide>

<Slide class="compact">

#### 多快就会发生
::sub[`01_hash_function/` 的最后一段]

- 运行


16 格里只放 **5 个**键，冲突概率就是一半。10 个几乎必然冲突。  
哈希表不是要避开冲突，而是必须有**处理**冲突的办法。

</Slide>

<Slide>

#### 解决冲突的两种方式
::sub[Collision Resolution]

1. **拉链法**（separate chaining）
   - 每格放一个链表，把冲突的键挂在上面。
2. **线性探测**（linear probing）
   - 冲突时去找数组里的下一个空位。

</Slide>

<Slide>

## 1) 拉链法
::sub[Separate Chaining]

</Slide>

<Slide>

#### 每格一个链表
::sub[把哈希值相同的项存进同一个链表]

- 在大小为 $$M$$ 的数组的每一格各放一个**链表**。
- 冲突的项按格分别用**各自的链表**管理。
- 查找是**两步查找**。
  1. **哈希查找**：用哈希函数选出格子。
  2. **链表查找**：顺序查找那一格的链表。
- 链表要短，所以 $$M$$ 要取得足够大。

</Slide>

<Slide>

### 一步一步：插入
::sub[用哈希找到格子再扫链表。相同的键只改值，没有就接到最前面]

<ChainingDemo slide />

</Slide>

<Slide class="compact">

#### 插入的步骤
::sub[`02_hash_table_sc/hashTableSC.pseudo`]

```plaintext
ALGORITHM Put(T, key, value)            // T：大小为 M 的数组，每格一个链表
    i <- Hash(key, M)
    for 节点 x in T[i] do               // 第 1 步：用哈希找到格子
        if x.key = key then             // 第 2 步：顺序查找那一格的链表
            x.value <- value            // 有相同的键就只改值
            return
    T[i] <- 新节点(key, value, next = T[i])    // 没有就接到最前面
    N <- N + 1
```

- 为了确认有没有相同的键，反正要扫到末尾。
- 接在最前面就不必一路找到链表末尾。

</Slide>

<Slide class="compact">

#### 写成代码
::sub[`02_hash_table_sc/hashTableSC.c`]

```c
int put(ChainingTable *t, char key, int value, int *compares) {
    int i = hashOf(key, t->m);
    *compares = 0;
    for (Node *x = t->heads[i]; x != NULL; x = x->next) {
        (*compares)++;
        if (x->key == key) {
            x->value = value;
            return 0;
        }
    }
    Node *node = malloc(sizeof(Node));
    node->key = key;  node->value = value;
    node->next = t->heads[i];   /* 接到最前面 */
    t->heads[i] = node;  t->n++;
    return 1;
}
```

</Slide>

#### 拉链法的代价
::sub[链表长度的平均值是 N/M，这就是装载因子 α]

| 操作 | 平均 | 最坏（所有键在同一格） |
| --- | --- | --- |
| 查找·插入·删除 | $$O(1 + N/M)$$ | $$O(N)$$ |

<br/>

- 让 $$M$$ 与 $$N$$ 成正比，平均就是 $$O(1)$$。
- **$$M$$ 太大时**，空链表变多，浪费内存。
- **$$M$$ 太小时**，链表变长，查找变慢。

</Slide>

## 2) 线性探测
::sub[Linear Probing]

</Slide>

<Slide>

#### 开放寻址
::sub[Open Addressing]

- 数组比键多（$$M > N$$）时，总会剩下空位。
- 冲突时放进**已有的空位**来解决。
- 把用在链表链接上的内存拿去把数组变大。

<br/>

**线性探测**是其中最简单的形式。  
冲突时看表的**下一格**，向右走，直到出现空位。  
到了数组末尾就回到 0 号。

</Slide>

<Slide>

### 一步一步：插入
::sub[键从哈希格出发向右滑。橙色条是被占格子连成的一片]

<ProbingDemo slide />

</Slide>

<Slide>

#### 值得留意的三个场景
::sub[放大显示的数字是查看的格数]

- **`H`（哈希 4）要 4 格**
  - 撞上 4 号 `A`、5 号 `C`、6 号 `S`，进入 7 号。
- **`P`（哈希 14）进入 0 号格**
  - 经过 14 号 `R`、15 号 `X`，越过数组末尾。
- **`L`（哈希 6）还撞上被 `H` 占着的 7 号**。
  - `H` 是因为 4 号位置的冲突才来到 7 号的。
  - 冲突引来冲突。

</Slide>

<Slide class="compact">

#### 插入与查找的步骤
::sub[`03_hash_table_lp/hashTableLP.pseudo`]

```plaintext
ALGORITHM Put(T, key, value)
    i <- Hash(key, M)
    while T.keys[i] ≠ 空 do             // 向右走，直到遇到空位
        if T.keys[i] = key then
            T.values[i] <- value        // 有相同的键就只改值
            return
        i <- (i + 1) mod M              // 到了末尾就回到 0 号格
    T.keys[i] <- key, T.values[i] <- value

ALGORITHM Get(T, key)
    i <- Hash(key, M)
    while T.keys[i] ≠ 空 do
        if T.keys[i] = key then return T.values[i]
        i <- (i + 1) mod M
    return 无                           // 遇到空位，就说明那个键不存在
```

</Slide>

#### 可以在空位停下的原因

- 那个键如果存在，最晚也会被放进**那个空位**。
- 所以**空位的意思是"从这里往后都没有"**。

<br/>

不存在的键 `Y` 在拉链法里比较 2 次，在线性探测里要 6 格。  
原因是从 4 号连到 8 号的**簇**。

</Slide>

#### 路断了
::sub[不能直接删除]

### 删除，再把跟在后面的键重新插入

#### 删除的步骤
::sub[`03_hash_table_lp/hashTableLP.pseudo`]

```plaintext
ALGORITHM Delete(T, key)
    i <- Hash(key, M)
    while T.keys[i] ≠ key do            // 先找到这个键
        if T.keys[i] = 空 then return 失败
        i <- (i + 1) mod M
    T.keys[i] <- 空, N <- N - 1
    i <- (i + 1) mod M
    while T.keys[i] ≠ 空 do             // 同一簇中跟在后面的键
        k, v <- T.keys[i], T.values[i]
        T.keys[i] <- 空, N <- N - 1
        Put(T, k, v)                    // 取出再重新插入
        i <- (i + 1) mod M
    if 0 < N ≤ M/8 then Resize(T, M/2)  // 太空就缩小一半
```

重新插入的键只有一个簇那么多，所以簇短的话，删除也很便宜。

#### 删除标记的规则
::sub[Tombstone（墓碑），惰性删除（lazy deletion）]

- 只在被删的格子里留下**标记**，实际上不清空。
  - `get` 把标记**当作被占的格子**走过去。
  - `put` 把标记**当作空位**重新使用。
- **`put` 不能直接放进第一个标记格**。
  - 这是实现时常掉进去的陷阱。
  - 相同的键可能还活在后面。
  - 走到空位确认没有之后，再放进第一个标记格。
- **标记会越积越多**。
  - 多了就新建一张表来清理。

</Slide>

## 簇与装载因子
::sub[Clustering and Load Factor]

#### 簇会自己长大
::sub[被占的格子中间没有空位、连成一片的一段]

- 示例中 4 号到 8 号（`A C S H L`）是长度为 5 的簇。
- 新键的哈希无论落在簇里的**哪里**，都会进入簇末端之后的那一格。
  - 簇越长，接收新键的概率越大。
- 进来的键让簇变长，有时还会和旁边的簇接起来。
  - `P` 一进入 0 号，14·15 号和 1 号就连成了一片。
- 簇一长，查找也得走到簇的末尾。

</Slide>

### 提高装载因子
::sub[拖动 α 比较两种方式的平均查找代价。实验值是真的插入键再数出来的]

<LoadCostDemo slide />

#### 装载因子决定的代价
::sub[α = N/M 时查看格数的平均值（Knuth）]

$$
\text{成功} \approx \frac{1}{2}\left(1 + \frac{1}{1-\alpha}\right) \qquad
\text{失败} \approx \frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)
$$

| 装载因子 $$\alpha$$ | 成功查找 | 失败查找 |
| --- | --- | --- |
| 1/2 | 1.5 | 2.5 |
| 3/4 | 2.5 | 8.5 |
| 7/8 | 4.5 | 32.5 |

越接近 1 就**急剧**变差。所以要把 $$\alpha$$ 保持在 1/2 附近。

</Slide>

::sub[Summary]

#### 两种方式的比较

| | 拉链法 | 线性探测 |
| --- | --- | --- |
| 冲突的键放在哪里 | 那一格的链表 | 数组的下一个空位 |
| 装载因子 | 可以超过 1 | 必须小于 1（通常在 1/2 附近） |
| 额外内存 | 每个节点的链接 | 空位 |
| 删除 | 只改一个链接 | 重新插入或用删除标记 |
| 损害性能的因素 | 长链表 | 长簇 |
| 内存访问 | 节点分散各处 | 依次查看相邻的格子 |

</Slide>

### 哈希表游乐场
::sub[插入、查找、删除字母。两种方式并排执行同一个操作]

<HashPlayDemo slide />

</Slide>

#### 内存
::sub[按 Sedgewick 教材的 Java 标准，键和值是引用类型时]

| 方法 | $$N$$ 个键的空间 |
| --- | --- |
| 拉链法 | 约 $$48N + 32M$$ 字节 |
| 线性探测 | 约 $$32N$$ 到 $$128N$$ 字节之间 |
| 二叉搜索树 | 约 $$56N$$ 字节 |

<br/>

- 拉链法把内存花在链接上，线性探测把内存花在空位上。
- 线性探测的范围宽，是因为数组的装满程度在 1/8 到 1/2 之间。

</Slide>

<Slide>

#### 哈希表的位置
::sub[希望查找快，并且不考虑记录的排列顺序]

| | 二叉搜索树（平衡） | 哈希表 |
| --- | --- | --- |
| 查找·插入·删除 | $$O(\log N)$$ | 平均 $$O(1)$$ |
| 最坏 | $$O(\log N)$$ | $$O(N)$$（差的哈希） |
| 最小值、范围查找 | 可以 | 不行 |
| 对键的要求 | 比较 | 哈希函数与相等判断 |

</Slide>

<Slide>

#### 哈希不是万灵药

- 每种键类型都要有**好的哈希函数**。
- 性能保证取决于哈希函数的**质量**。
- 哈希函数的计算可能很难，也可能需要大量运算。
- **与顺序有关的操作**不容易做。
  - 最小的键、下一个键、范围查找

<br/>

需要顺序就用二叉搜索树，只要快就用哈希表。

</Slide>

## 要带走的

1. **哈希从键算出下标，不经比较就能找到**。
   - 好的哈希函数：结果在范围内、计算容易、散布均匀。
2. **冲突必然发生**。
   - 鸽巢原理与生日问题
3. **拉链法每格放一个链表**。
   - 平均 $$O(1 + N/M)$$，删除容易。
4. **线性探测去下一格**。
   - 直接清空会断路，所以要把后面的键重新插入。
5. **装载因子接近 1 时簇会长大，急剧变慢**。
   - 调整大小，把它保持在 1/2 附近。
