## Binary trees \{#binary-tree}

A tree is a structure of nodes and the links that connect them. A binary
tree has two properties.

- **Property 1**: from the root to every other node there is **exactly one**
  (unique) path. If two nodes point to the same child, or a link loops back
  up, it is not a tree.
- **Property 2**: each node has **at most two** children: a left child and a
  right child.

<TreeFigure tree={{ l: { l: { v: "A", filled: true }, r: { v: "B", filled: true } }, r: { l: { v: "C", filled: true }, r: { v: "D", filled: true } } }} />

### Vocabulary \{#terms}

| Term | Meaning |
| --- | --- |
| node | one circle holding a value |
| link | the line connecting two nodes. Also called an edge |
| root | the topmost node. The only node without a parent |
| parent·child | the nodes directly above and below each other along a link |
| leaf | a node with no children |
| subtree | a node and everything below it. A tree in its own right |
| level | how many links down from the root. The root is level 0 |
| height | the number of levels. A root alone has height 1 |
| full tree | every non-leaf node has two children and all leaves are on the same level |

The figure above is a full tree. A, B, C and D are leaves, all on level 2.
Remove D and it is no longer a full tree.

In this course, height is counted as the **number of levels**. Some
textbooks count the **number of links** from the root to the deepest leaf,
which is one less than ours. That is the only adjustment needed when
comparing with other material.

### Height and node count \{#height}

Level $$l$$ holds at most $$2^l$$ nodes: 1 on level 0, 2 on level 1, 4 on
level 2. A full tree of height $$h$$ has every level filled, so its node
count $$N$$ is

$$
N = 2^0 + 2^1 + \cdots + 2^{h-1} = 2^h - 1
$$

Solving backwards, the height is the logarithm of the node count.

$$
2^h = N + 1 \quad\Rightarrow\quad h = \log_2(N + 1) = O(\log N)
$$

What does the tallest tree look like? If every node has only one child, the
tree lines up in a single row and its height is $$N$$. It has the same shape
as a linked list.

<TreeFigure tree={{ v: "A", r: { v: "B", l: { v: "C", r: { v: "D" } } } }} />

| Nodes $$N$$ | Lowest height | Highest height |
| --- | --- | --- |
| 7 | 3 | 7 |
| 1,023 | 10 | 1,023 |
| about 1 million | 20 | about 1 million |

With the same number of nodes, the height ranges from $$\log_2 N$$ to $$N$$.
Every operation in this topic ends up proportional to this height, so this
table is worth remembering.

### Searching a binary tree \{#binary-tree-search}

Being a binary tree alone does not make search faster. Suppose we look for
11 in the tree below.

<TreeFigure tree={{ v: "2", l: { v: "7", l: { v: "2" }, r: { v: "6", l: { v: "5" }, r: { v: "11" } } }, r: { v: "5", r: { v: "9", l: { v: "4" } } } }} />

The values sit anywhere, so we start at the root and sweep level by level
until we find the value or reach the leaves. In the worst case we look at
every node: $$O(N)$$, no better than a linked list. To go faster we need a
rule that tells us **where we do not have to look**.

## Binary search trees \{#bst}

### Definition \{#bst-definition}

A [[bst|binary search tree]] (BST) is a binary tree in which every node
follows these rules.

- **Every key in the left subtree** is smaller than the node's key.
- **Every key in the right subtree** is larger than the node's key.
- The left and right subtrees are binary search trees as well.

We assume all keys are distinct. Inserting a value that is already there
does nothing.

It is tempting to check only parent–child pairs: "larger than the left
**child** and smaller than the right **child**." That is not enough. The tree
below satisfies that rule for every parent–child pair and is still not a BST.

<TreeFigure tree={{ v: "5", l: { v: "3", r: { v: "7", tone: "focus" } }, r: { v: "8" } }} caption="3 < 7 satisfies the child rule, but 7 sits in the left subtree of 5" />

7 is larger than 5 yet sits in 5's left subtree. A search for 7 goes right
(to 8) at 5 and never finds it. The rule has to cover the **whole subtree**,
not just one child. For the same reason the 2·7·5 tree of the previous
section is not a BST.

Here is a tree that follows the rule. Inserting the keys `7 4 14 1 6 16 2 5 15`
in order produces this shape.

<TreeFigure tree={{ v: "7", l: { v: "4", l: { v: "1", tone: "eval", r: { v: "2" } }, r: { v: "6", l: { v: "5" } } }, r: { v: "14", r: { v: "16", tone: "focus", l: { v: "15" } } } }} caption="green: smallest value · orange: largest value" />

- The **smallest value** is where you end up going only left (1).
- The **largest value** is where you end up going only right (16).
- Read left to right, it is `1 2 4 5 6 7 14 15 16`, in sorted order.

### Search \{#bst-search}

With the rule in place, every comparison lets us discard one side entirely.
Let's find 6. The orange circle is the value we are looking for; it stands
next to the node just compared, on the side it will go next.

<BstDemo keys={[7, 4, 14, 1, 6, 16, 2, 5, 15]} find={6} />

6 is smaller than 7, so the right subtree `14 15 16` never needs a look. It
is larger than 4, so `1 2` goes too. Found in 3 comparisons. A missing value
is just as quick to detect. Searching for 13, the left of 14 is empty, so we
answer "not there" after 2 comparisons.

<BstDemo keys={[7, 4, 14, 1, 6, 16, 2, 5, 15]} find={13} />

The dashed circle is where 13 would go. Keep in mind that **the spot where a
search fails is exactly the spot to insert**. Example 1 uses this directly.

It is the same idea as [[binary-search|binary search]] in Topic 01. Binary
search compared against the middle value each time and discarded half. A
binary search tree places that "middle" at the root in advance, and each
subtree carries its own pivot value too. The difference is that it is held
together by links instead of an array, which makes inserting and deleting
easy.

```plaintext
ALGORITHM Search(root, key)
    node <- root
    while node != NULL do
        if key = node.key then
            return node                 // found it
        if key < node.key then
            node <- node.left           // smaller: only the left subtree matters
        else
            node <- node.right          // larger: only the right subtree matters
    return NULL                         // reached an empty spot: not there
```

It goes down a single path from the root toward the leaves, so the number
of comparisons is at most the height $$h$$. Search is $$O(h)$$.

3 comparisons. In the ideal case the search range halves with every
comparison.

### Representing it with links \{#structure}

A linked-list node held one value and the address of the next node. A
binary search tree node holds two addresses.

```plaintext
linked-list node    [ value | next address ]

tree node        [ left address | value | right address ]
                        |                     |
                        v                     v
          [ left | value | right ]  [ left | value | right ]
```

In C that is one struct and one function that creates a node. A new node has
no children, so both addresses start as `NULL`.

```c
typedef struct TreeNode {
    int key;
    struct TreeNode *left;   /* address of the left child */
    struct TreeNode *right;  /* address of the right child */
} TreeNode;

TreeNode *createNode(int key) {
    TreeNode *node = (TreeNode *)malloc(sizeof(TreeNode));
    node->key = key;
    node->left = NULL;
    node->right = NULL;
    return node;
}
```

## Example 1. Search and insert \{#insert}

Insertion is **a failed search plus hanging the node there**. Go down as if
searching for the value, and when you reach an empty child spot, attach a
new node there. Let's insert `5 9 7 3 8 12 6 4 20` in that order. The top row is the insertion order, and the orange
circle is the value being inserted.

<BstDemo />

Watch the step where 8 goes in. Larger than 5, so right; smaller than 9, so
left; larger than 7, so right, but the right of 7 is empty. 8 settles
there. Not a single existing node moves. Unlike inserting into an array,
nothing behind it has to shift.

The nodes in the demo appear in their final places from the start, because
their horizontal position is **their rank in sorted order**. Drop every
node to the floor into one row and `3 4 5 6 7 8 9 12 20` lines up sorted
from the left. That is exactly what the BST rule says.

```plaintext
ALGORITHM Insert(root, key)
    if root = NULL then
        return new node(key)            // exactly where the search failed
    if key < root.key then
        root.left <- Insert(root.left, key)
    else if key > root.key then
        root.right <- Insert(root.right, key)
    // if equal, do nothing (each key goes in only once)
    return root
```

Written recursively, it is short. Each call keeps one promise: "insert key
into this subtree and return its root." Inserting into an empty subtree
makes the new node that subtree's root, and the parent writes the returned
address back into `left` or `right`.

- C implementation

```c
TreeNode *insert(TreeNode *root, int key) {
    if (root == NULL) {
        return createNode(key);
    }
    if (key < root->key) {
        root->left = insert(root->left, key);
    } else if (key > root->key) {
        root->right = insert(root->right, key);
    }
    return root;
}
```

The caller always replaces its root with the one returned. The first insert
into an empty tree changes the root from `NULL` to the new node.

```c
TreeNode *root = NULL;
root = insert(root, 5);
root = insert(root, 9);
```

### The insertion order decides the shape \{#insert-order}

The last group is the most important result of this topic. The same keys A
through G were inserted in three different orders.

- `D B F A C E G`

<TreeFigure tree={{ v: "D", l: { v: "B", l: { v: "A" }, r: { v: "C" } }, r: { v: "F", l: { v: "E" }, r: { v: "G" } } }} />

- `B A D C G F E`

<TreeFigure tree={{ v: "B", l: { v: "A" }, r: { v: "D", l: { v: "C" }, r: { v: "G", l: { v: "F", l: { v: "E" } } } } }} />

- `A B C D E F G`

<TreeFigure tree={{ v: "A", r: { v: "B", r: { v: "C", r: { v: "D", r: { v: "E", r: { v: "F", r: { v: "G" } } } } } } }} />

Inserted in sorted order, each new value is larger than every value so far,
so it always lands at the far right. Insert them yourself and the tree grows
in one direction only.

<BstDemo keys={['A', 'B', 'C', 'D', 'E', 'F', 'G']} />

| Insertion order | Height | Comparisons to build |
| --- | --- | --- |
| `D B F A C E G` | 3 | 10 |
| `B A D C G F E` | 5 | 13 |
| `A B C D E F G` | 7 | 21 |

- A tree leaning to one side **is a linked list.** Search falls back to
  $$O(n)$$.
- Inserting $$n$$ sorted keys takes $$0 + 1 + \cdots + (n-1) = \dfrac{n(n-1)}{2}$$
  comparisons, so building the tree alone costs $$O(n^2)$$. With 7 keys that
  is 21.
- An unbalanced tree makes search slow, which is undesirable. Balanced trees
  such as the **red-black tree** and the AVL tree reshape themselves on every
  insert and delete to keep the height at $$O(\log n)$$. They are beyond
  this course, but they are what real libraries use for sorted maps
  (C++ `std::map`, Java `TreeMap`).

Data arriving already sorted is not rare: logs in date order, student IDs in
number order. That is why a BST that ignores balance can be risky in
practice.

## Example 2. Delete \{#delete}

Deletion has two steps. **Find** the value, then **delete** that node.
There is one condition: after the deletion the BST property, **left is
smaller and right is larger**, must still hold. There are three cases,
depending on how many children the node to delete has.

| Case | Node to delete | What to do |
| --- | --- | --- |
| 1 | 0 children (leaf) | just detach it |
| 2 | 1 child | link that child directly to the parent |
| 3 | 2 children | copy the successor into its place, then delete the original successor |

Let's use the tree built by inserting `B A D C G F E`. Each of the three demos starts afresh from this tree.

### Case 1: 0 children \{#delete-leaf}

E is a leaf. Detaching it does not change how the other nodes relate to each
other.

<BstDeleteDemo del="E" />

### Case 2: 1 child \{#delete-one}

F has only a left child, E. Delete F and link E directly to F's parent, G. E
was in G's left subtree to begin with, so it is smaller than G and the left
of G is still the right place for it. Even if the child has a subtree hanging
from it, the whole thing simply moves up.

<BstDeleteDemo del="F" />

### Case 3: 2 children \{#delete-two}

D has two children, C and G. D's parent B has only one child slot, so it
cannot link both. Instead of removing D, we look for **another value to put
in D's place**. That value must be larger than everything to D's left and
smaller than everything to its right. There are two candidates.

- **Successor**: the smallest value in the right subtree. Go right once, then
  all the way left. It is the value right after D in inorder.
- **Predecessor**: the largest value in the left subtree. It is the value
  right before D in inorder.

The practice code uses the successor.

<BstDeleteDemo del="D" />

Copying the successor E into D's place leaves E in two places for a moment.
Now delete the original E. The successor is "the far left", so it **has no
left child**. That is why deleting the original successor always ends in case
1 or case 2, and case 3 never comes up again.

Let's delete Q from the tree built by inserting `J B Q L R K N Z M P`. Q's right child R has no left child, so R itself is the successor.
Copy R, delete the original R, and R's right child Z moves up.

<BstDeleteDemo keys="JBQLRKNZMP" del="Q" />

Deleting the root works the same way. To find J's successor, go right once
(Q), then all the way left (L, K).

<BstDeleteDemo keys="JBQLRKNZMP" del="J" />

### The predecessor works too \{#predecessor}

If case 3 uses the predecessor instead of the successor, deleting D brings
the largest value of its left subtree, C, into its place; deleting Q brings P.

- Delete D using predecessor C

<TreeFigure tree={{ v: "B", l: { v: "A" }, r: { v: "C", tone: "eval", r: { v: "G", l: { v: "F", l: { v: "E" } } } } }} />

- Delete Q using predecessor P

<TreeFigure tree={{ v: "J", l: { v: "B" }, r: { v: "P", tone: "eval", l: { v: "L", l: { v: "K" }, r: { v: "N", l: { v: "M" } } }, r: { v: "R", r: { v: "Z" } } } }} />

The shapes differ from the successor results, but both are BSTs with the
same inorder sequence. Using the predecessor is a correct deletion too. The
practice code and demos in this course use the successor.

### Procedure and code \{#delete-code}

Deletion is clean when you think of it recursively.

- **Problem size**: the number of nodes in the tree
- **Base case**: the key to delete has been found. Handle it with one of the
  three cases.
- **General case**: pick the left or right subtree and delete within it.

```plaintext
ALGORITHM Delete(root, key)
    if root = NULL then
        return NULL                         // nothing to delete
    if key < root.key then
        root.left <- Delete(root.left, key)
    else if key > root.key then
        root.right <- Delete(root.right, key)
    else                                    // root is the node to delete
        if root.left = NULL then            // cases 1·2: no child, or only a right one
            return root.right
        if root.right = NULL then           // case 2: only a left child
            return root.left
        succ <- FindMin(root.right)         // case 3: the successor
        root.key <- succ.key                // copy the successor's key here
        root.right <- Delete(root.right, succ.key)   // and delete the original successor
    return root
```

Notice that case 1 and case 2 (only a right child) merge into one line. If
the left is empty we return the right, and when there are no children at all
the right is `NULL` too, which is exactly "detach it".

- C implementation

```c
TreeNode *findMin(TreeNode *node) {
    while (node->left != NULL) {
        node = node->left;
    }
    return node;
}

TreeNode *deleteNode(TreeNode *root, char key) {
    if (root == NULL) {
        return NULL;
    }
    if (key < root->key) {
        root->left = deleteNode(root->left, key);
    } else if (key > root->key) {
        root->right = deleteNode(root->right, key);
    } else {
        /* cases 1·2: zero children or one */
        if (root->left == NULL) {
            TreeNode *temp = root->right;
            free(root);
            return temp;
        }
        if (root->right == NULL) {
            TreeNode *temp = root->left;
            free(root);
            return temp;
        }
        /* case 3: two children. Copy the successor, then delete the original. */
        TreeNode *succ = findMin(root->right);
        root->key = succ->key;
        root->right = deleteNode(root->right, succ->key);
    }
    return root;
}
```

In C, the memory of a detached node goes back with `free`. Before that, the
address of the child to keep must be saved in `temp`; after `free`,
`root->right` can no longer be read.

`tree` writes the shape on one line: `key(left,right)`, with `-` for an

The cost is going down to find the node and, in case 3, going further down
to find the successor. Together they are still a single path from the root
toward a leaf, so deletion is $$O(h)$$.

## Example 3. Traversal \{#traversal}

Visiting every node of a tree once is called a traversal. An array can just
be read from the front, but a tree forces a choice at every fork: which side
first? There are three recursive traversals, and the only difference is
**when the current node is printed**.

| Traversal | Order | Result for the `D B F A C E G` tree |
| --- | --- | --- |
| inorder | [left] [current] [right] | `A B C D E F G` |
| preorder | [current] [left] [right] | `D B A C F E G` |
| postorder | [left] [right] [current] | `A C B E G F D` |

Switch tabs and step through each one. Orange is the current node, an orange
outline marks calls not yet finished (the call stack), and every printed node
gets a number showing when it came out.

<TraversalDemo />

- **Inorder** prints each node after its whole left side, so on a BST it
  **always gives sorted order**, regardless of the insertion order.
- **Preorder** puts the root first. A parent always comes before its
  children.
- **Postorder** puts the root last. Children always come before their parent.

Besides these three there is **level order**: level by level from the root,
left to right within a level. It uses a queue instead of recursion. Take a
node off the front, print it, add its children to the back, and repeat until
the queue is empty. This is exactly [[bfs|BFS]], which in Topic 12 sweeps a
graph from the nearest vertices outward.

Let's also run it on the tree built by inserting `P F B H G S R Y T W Z`. With
eleven nodes the differences between the orders show more clearly.

<TraversalDemo keys="PFBHGSRYTWZ" order="pre" />

```plaintext
ALGORITHM Inorder(node)                 // inorder: [left] [current] [right]
    if node != NULL then
        Inorder(node.left)
        print node.key
        Inorder(node.right)

ALGORITHM Preorder(node)                // preorder: [current] [left] [right]
    if node != NULL then
        print node.key
        Preorder(node.left)
        Preorder(node.right)

ALGORITHM Postorder(node)               // postorder: [left] [right] [current]
    if node != NULL then
        Postorder(node.left)
        Postorder(node.right)
        print node.key

ALGORITHM LevelOrder(root)              // level order: top level first, left to right
    queue <- [root]
    while queue is not empty do
        node <- take the front of queue
        print node.key
        if node.left != NULL then add node.left to the back of queue
        if node.right != NULL then add node.right to the back of queue
```

- C implementation (inorder and level order)

```c
void inorderTraversal(TreeNode *root) {
    if (root != NULL) {
        inorderTraversal(root->left);
        printf(" %c", root->key);
        inorderTraversal(root->right);
    }
}

void levelorderTraversal(TreeNode *root) {
    TreeNode *queue[MAX_NODES];
    int head = 0;
    int tail = 0;
    if (root != NULL) {
        queue[tail++] = root;
    }
    while (head < tail) {
        TreeNode *node = queue[head++];
        printf(" %c", node->key);
        if (node->left != NULL) {
            queue[tail++] = node->left;
        }
        if (node->right != NULL) {
            queue[tail++] = node->right;
        }
    }
}
```

Preorder and postorder are the inorder function with the one `printf` line
moved.

```console
  levelorder = D B F A C E G

insert PFBHGSRYTWZ
  tree       = P(F(B,H(G,-)),S(R,Y(T(-,W),Z)))
  inorder    = B F G H P R S T W Y Z
  preorder   = P F B H G S R Y T W Z
  postorder  = B G H F R W T Z Y S P
  levelorder = P F S B H R Y G T Z W
```

All four print each node exactly once, so they are $$O(n)$$. Extra space
differs. A recursive traversal stacks the path from the root to the current
node on the call stack, $$O(h)$$; level order can hold a whole level in the
queue, up to $$O(n)$$.

## Example 4. Print, free, copy \{#print-free-copy}

Anything that handles a whole tree comes down to a single traversal. Which
one to use is decided by **whether the parent or the children must be handled
first**.

| Task | Traversal | Why |
| --- | --- | --- |
| print in sorted order | inorder | a BST's inorder is ascending |
| print the shape | preorder | the parent must be written before its children can be indented under it |
| free | postorder | freeing the parent first loses the addresses of its children |
| copy | preorder | the parent must exist before children can be hung on it |

### Print \{#print}

Sorted printing is just the inorder traversal we have already seen. To print
the tree's **shape** as text, write the node first and then its children
below it, indented one step. The current node comes first, so it is
preorder. Printing a tree makes one think of inorder, but this function
prints the node first and then goes down to the children, so it is preorder. Sorted printing (inorder) and shape printing (preorder)
are different jobs.

```c
void printTree(TreeNode *root, const char *prefix, int isLast) {
    printf("%s%s", prefix, isLast ? "└── " : "├── ");
    if (root == NULL) {
        printf("-\n");
        return;
    }
    printf("%c\n", root->key);                       /* current first */

    if (root->left != NULL || root->right != NULL) {
        char next[256];
        snprintf(next, sizeof(next), "%s%s", prefix, isLast ? "    " : "│   ");
        printTree(root->left, next, 0);              /* then left */
        printTree(root->right, next, 1);             /* then right */
    }
}
```

### Free \{#free}

In C, nodes made with `malloc` must be handed back with `free` when done. Once
the parent is freed, the child addresses stored inside it can no longer be
read, so **postorder**, children first, is right. Step the demo below to the
end and the output row is the order of freeing: leaves first, the root P
last.

<TraversalDemo keys="PFBHGSRYTWZ" order="post" />

```c
TreeNode *clearTree(TreeNode *root) {
    if (root != NULL) {
        clearTree(root->left);
        clearTree(root->right);
        free(root);              /* safe: every child is already freed */
    }
    return NULL;
}
```

It returns `NULL` so that you write `root = clearTree(root);` and no freed
address is left behind.

### Copy \{#copy}

Copying is the opposite. The new parent node must exist before the copied
children can hang on it, so it is **preorder**.

```c
TreeNode *copyTree(TreeNode *root) {
    if (root == NULL) {
        return NULL;
    }
    TreeNode *copy = createNode(root->key);   /* current first */
    copy->left = copyTree(root->left);
    copy->right = copyTree(root->right);
    return copy;
}
```

### Save and rebuild \{#rebuild}

Suppose we write the tree to a file and, the next time the program runs,
read it back and insert the keys again. Which traversal should we write it
in?

- **Written in inorder**, the sorted order is saved. Inserting in that order
  grows the one-sided tree we saw earlier, and the original structure is
  lost.
- **Written in preorder**, a parent always comes before its children.
  Inserting in that order puts every key back in its original spot, giving
  **the same tree**.

## BSTs and linked lists \{#comparison}

How would the same work look with a sorted linked list? A linked list has to
be followed one node at a time from the start, so search, insertion and
deletion are all $$O(n)$$.

| Operation | BST (balanced) | BST (worst) | Sorted linked list |
| --- | --- | --- | --- |
| constructor | $$O(1)$$ | $$O(1)$$ | $$O(1)$$ |
| destructor | $$O(n)$$ | $$O(n)$$ | $$O(n)$$ |
| empty?·full? | $$O(1)$$ | $$O(1)$$ | $$O(1)$$ |
| search | $$O(\log n)$$ | $$O(n)$$ | $$O(n)$$ |
| insert | $$O(\log n)$$ | $$O(n)$$ | $$O(n)$$ |
| delete | $$O(\log n)$$ | $$O(n)$$ | $$O(n)$$ |

Calling a BST simply $$O(\log n)$$ hides the assumption
$$h = O(\log n)$$. The worst-case column shows that once that
assumption breaks, a BST is no better than a linked list. Strictly speaking,
search, insertion and deletion are all $$O(h)$$, and everything depends on
where the height $$h$$ lies between $$\log_2 n$$ and $$n$$.

Put it next to the sorted array of Topic 01 as well. An array finds a value
in $$O(\log n)$$ with binary search, but inserting and deleting cost $$O(n)$$
for shifting the elements behind. A balanced BST does all three in
$$O(\log n)$$, because inserting and deleting only change links.

## What to keep \{#takeaway}

- **Binary tree**: there is one path from the root to each node, and each
  node has at most two children. With $$N$$ nodes the height can be anything
  from $$\log_2(N+1)$$ to $$N$$.
- **Binary search tree**: at every node, the whole left subtree is smaller
  and the whole right subtree is larger. A rule that compares with one child
  only is not enough.
- **Search and insert**: smaller goes left, larger goes right. Insertion
  hangs the node where the search failed. The cost is $$O(h)$$.
- **The insertion order decides the shape.** Inserting in sorted order
  produces a linked list and every operation drops to $$O(n)$$. Balanced
  trees prevent this.
- **Delete**: with 0 children detach, with 1 link, with 2 replace with the
  successor (or predecessor) and then delete the original successor.
- **Traversals**: inorder is sorted order, preorder is parent first,
  postorder is children first, level order uses a queue. Printing, freeing
  and copying each take one fitting traversal.
