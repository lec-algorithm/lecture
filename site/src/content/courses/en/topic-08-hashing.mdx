> The binary search tree of Topic 07 found keys by **comparing** them. Even
> when it is well balanced, it needs $$O(\log n)$$ comparisons.  
> This topic does not search by comparing. **It computes the slot straight
> from the key.**  
> That computation is the hash function. Everything else in designing a hash
> table is about how to resolve collisions, where different keys point to the
> same slot.

## Keys as array indices \{#key-as-index}

Say the keys are small integers from 1 to 8. Then there is nothing to think
about. Put the item with key `i` in slot `i` of an array.

```plaintext
slot  1   2   3   4   5   6   7   8
     [ ] [ ] [3] [ ] [5] [ ] [ ] [8]

find 3?  -> look at A[3]. It is there.
find 5?  -> look at A[5]. It is there.
find 7?  -> look at A[7]. Empty, so it is not there.
```

Not a single comparison. The key is the address, so any key takes one
memory access: $$O(1)$$.

**Hashing** extends this method to keys that are not small integers. We want
to do the same thing when keys are large or not integers at all: national ID
numbers, names, student IDs, strings. That takes two things.

- **Hash function**: a computation that turns a key into an array index
- **Collision resolution**: what to do when different keys turn into the same
  index

### Between time and memory \{#time-memory}

Hashing is also a way to strike a balance between time and memory.

| If memory is | What you can do | The price |
| --- | --- | --- |
| unlimited | give every possible key its own slot and use the key itself as the index | memory: $$10^{13}$$ slots for 13-digit ID numbers |
| very scarce | gather everything in one unsorted array and search it sequentially | time: $$O(n)$$ for every search |
| moderate | **hashing**: scatter the keys over an array of moderate size and handle only the overlaps separately | a little of both |

The three rows are joined by a single number, the slot count. Put 12 keys
between 0 and 63 into slot `key mod M` and move $$M$$ from 1 to 64. Click a key
to look it up and color the keys it is compared with.

<SpaceTimeDemo />

With $$M = 1$$ everything lands in one slot, which is the same as a sequential
search, at 6.5 compares on average. With $$M = 64$$ the key is the address, so
any key is found at once, but 64 slots hold just 12 keys. In between,
$$M = 13$$ has only 13 slots and still finds a key in 1.25 compares on
average.

Picture the stamp-card rack at a café counter. The rack has a slot for each
first letter of the customer's name (A, B and C together, M, digits, …), so
to find a card you look in one slot instead of going through the whole box.
Picking the first letter is the hash function, and several cards in one slot
is a collision. There are far fewer slots than customers, so it uses little
memory, and you only go through one slot, so it takes little time.

When a customer comes in, pick the slot by the first letter and turn only the
cards in that slot, from the front. A returning customer just gets one more
stamp; a new customer gets a new card at the front of the slot. Go through it
with **Step**, or type a name into the box to get and find cards yourself.

<CouponDemo />

Compare the two big numbers. The whole box holds 9 cards, but no customer
turns more than 2. Still, slot `L` ends up with 3 cards while 20 of the 26
slots stay empty, because first letters of names are not spread evenly. This
is why a good hash function has to spread keys **evenly**. The card rack has
the same structure as separate chaining, which comes later.

## Hash functions \{#hash-function}

A [[hash-function|hash function]] turns a key into an array index. For an
array of size $$M$$, a good hash function has three properties.

1. The result is always an integer in $$[0, M-1]$$.
2. It is easy to compute.
3. It spreads the keys **evenly** over the whole array.

How you build one depends on the kind of key.

- **ID numbers**: if the key is a number, use the number as it is.
- **Names**: if the key is a string, turn the string into a number.
- **Your own data types**: you have to write the hash function yourself.

### Modular hashing \{#modular-hashing}

This is the most common way to hash integers. Use the **remainder** of a
positive integer key $$k$$ divided by the array size $$M$$ as the index.

$$
h(k) = k \bmod M
$$

The remainder is always between $$0$$ and $$M-1$$, so the first property
holds automatically, and it is a single division, so the second holds too.
Put the ASCII codes of the letters `A`, `B`, `C`, and `K` into an array of
size 8.

<HashSlotDemo />

| Key | Code | Hash ($$M = 8$$) |
| --- | --- | --- |
| A | 65 | 1 |
| B | 66 | 2 |
| C | 67 | 3 |
| K | 75 | 3 |

Something happens in the last row. `C` and `K` are different keys, yet they
point to the same slot, 3. This is called a [[collision|collision]].
Ideally, different keys go to different indices, but in practice different
keys can map to the same index.

### Make M a prime \{#prime-m}

The third property (evenly) depends on how you choose $$M$$. Suppose the keys
only ever come in as multiples of 4. With $$M = 8$$, this is what happens.

<HashSlotDemo keys={[0, 4, 8, 12, 16, 20, 24, 28]} m={8} />

Only two of the eight slots, 0 and 4, are used. That is because the keys and
$$M$$ share the common factor 4. Change $$M$$ to the prime 7, and the same
keys spread over all seven slots.

<HashSlotDemo keys={[0, 4, 8, 12, 16, 20, 24, 28]} m={7} />

So the array size $$M$$ is chosen to be a **prime number**. A prime shares no
common factor with any key that is not one of its multiples, so it is not
thrown off by patterns common in keys (only even numbers, only multiples of
10). A prime is not a cure-all, though. Had every key been a multiple of 7,
$$M = 7$$ would also use just one slot.

Change the key step and $$M$$ yourself. The keys are 16 numbers from 0 in
steps of $$d$$, and the slots used number $$M / \gcd(d, M)$$. The row of bars
below shows, for the current step, the share of slots used for each $$M$$ from
2 to 16; click a bar to switch to that $$M$$.

<PrimeModDemo />

With a step of 4, the full bars are the odd $$M$$, which share no factor with
4. A prime always fills its bar unless the step is a multiple of it. Change
the step to 7, and only the bars for $$M = 7$$ and $$M = 14$$ drop.

### Hashing strings \{#string-hashing}

A string has to be turned into a number first. The simplest idea is to add up
the character codes. But then **strings with the same characters in a
different order** all get the same value. `stop`, `pots`, `tops`, `spot`,
`opts`, and `post` all have the same sum of character codes.

To capture order, give each position a weight. Multiply the value so far by a
small number $$R$$ (usually 31) and add the next character. This is Horner's
method for evaluating a polynomial. Taking the remainder mod $$M$$ each time
keeps the value from growing.

$$
h \leftarrow (R \cdot h + \text{code}(c)) \bmod M
$$

Put the six words into an array of size 97. Each step updates $$h$$ by one
letter, and once the last letter is done the word drops into its slot on the
strip below. Switch between summing and Horner's method with the tabs.

<StringHashDemo />

- Pseudocode

```plaintext
ALGORITHM SumHash(s, M)                 // bad: ignores the order of the chars
    h <- 0
    for char c in s do
        h <- (h + code(c)) mod M
    return h

ALGORITHM HornerHash(s, M)              // good: multiplying by R per position captures order
    h <- 0
    for char c in s do
        h <- (R * h + code(c)) mod M    // the remainder each time keeps h below M
    return h
```

- C implementation

```c
int hornerHash(const char *s, int m) {
    const int R = 31;
    int h = 0;
    for (int i = 0; s[i] != '\0'; i++) {
        h = (R * h + (unsigned char)s[i]) % m;
    }
    return h;
}
```

- Result (part of `01_hash_function`, $$M = 97$$)

```console
  tops   66       3
  spot   66      49
  opts   66      58

```

In the `sum` column, which only adds, all six words pile into slot 66.
Horner's method scatters them over five slots. Even so, `spot` and `post`
meet at 49. A good hash function does not eliminate collisions. **It only
reduces them.**

## Collisions are unavoidable \{#collisions-happen}

Could we build a hash function that never collides? It is impossible, for two
reasons.

- **The pigeonhole principle**: if there are more keys than slots
  ($$N > M$$), some slot gets two or more keys. The values a key could take
  (every name, every string) always far outnumber the array size.
- **The birthday problem**: even with far fewer keys than slots, collisions
  come quickly. In a group of 23 people, the chance that two share a birthday
  is more than half.

If $$N$$ keys go into $$M$$ slots evenly at random, then for no collision at
all, the second key must avoid the first key's slot, the third key must avoid
the two before it, and so on.

$$
P(\text{at least one collision}) = 1 - \frac{M}{M} \cdot \frac{M-1}{M} \cdots \frac{M-N+1}{M}
$$

Move the key count $$N$$ to see how fast this chance climbs. The hollow dots on
the curve are the values the run below prints. Click **Throw at random** a few
times and the share of throws that collided closes in on the curve.

**handle** collisions, not **avoid** them. This topic looks at two.

1. **Separate chaining**: keep a linked list in each slot and hang the
   colliding keys on it.
2. **Linear probing**: on a collision, go find the next empty slot in the
   array.

## Separate chaining \{#separate-chaining}

Each slot of an array of size $$M$$ holds a **linked list**. Keys with the
same hash value hang together on that slot's list. The colliding items are
strung on a separate chain for each slot, hence the name separate chaining.

Finding a key is a **two-step search**.

1. **Hash search**: pick the slot with the hash function. $$O(1)$$
2. **List search**: search that slot's list sequentially from the front.

If the lists are short, the second step finishes quickly too. That is why
$$M$$ has to be large enough. The café stamp-card rack is exactly this
structure.

### Insertion \{#sc-insert}

`put(key, value)` finds the slot by hashing and walks that slot's list. If the
same key is there, it **only changes the value**; if it reaches the end
without finding it, it attaches a new node at the **front** of the list.
Attaching at the front means there is no need to go find the end of the list.
It has already walked to the end anyway to check for the same key, so
attaching at the back would take the same number of comparisons.

The large floating number is how many key comparisons this `put` made.

<ChainingDemo />

Inserting `H` took two comparisons, since slot 4 already held `C` and `R`,
and inserting `M` took three. The second `E` (value 6) passed `A` in slot 0,
met `E`, and only changed its value from 1 to 6.

- Pseudocode

```plaintext
ALGORITHM Put(T, key, value)            // T: array of size M, a linked list per slot
    i <- Hash(key, M)
    for node x in T[i] do               // step 1: find the slot by hashing
        if x.key = key then             // step 2: search that slot's list in order
            x.value <- value            // same key found: only change the value
            return
    T[i] <- new node(key, value, next = T[i])  // not found: attach at the front
    N <- N + 1
```

- C implementation

```c
int put(ChainingTable *t, char key, int value, int *compares) {
    int i = hashOf(key, t->m);
    *compares = 0;
    for (Node *x = t->heads[i]; x != NULL; x = x->next) {
        (*compares)++;
        if (x->key == key) {
            x->value = value;
            return 0;
        }
    }
    Node *node = malloc(sizeof(Node));
    node->key = key;
    node->value = value;
    node->next = t->heads[i]; /* attach at the front */
    t->heads[i] = node;
    t->n++;
    return 1;
}
```

Each slot of the array `heads` is a pointer to the front node of a list. At
first they are all `NULL` (empty lists).

### Search \{#sc-search}

`get(key)` is the same two steps. Search for `E`, which is present, and `Y`,
which is not.

<ChainingDemo mode="search" />

`E` is found at the second node of slot 0, after passing `A`. `Y` hashes to
2, so it looks at `X` and `S` in slot 2, reaches the end of the list, and
answers **not found**. Confirming that a key is missing also takes only that
slot's list. There is no need to look at any other slot.

```plaintext
ALGORITHM Get(T, key)
    i <- Hash(key, M)
    for node x in T[i] do
        if x.key = key then return x.value
    return none                         // reached the end of the list: not there
```

### Deletion \{#sc-delete}

`delete(key)` finds the key and then changes one link. If the node found is
at the front, the slot is made to point to the next node; if it is in the
middle or at the end, the previous node is made to skip over it.

<ChainingDemo mode="delete" />

- Pseudocode

```plaintext
ALGORITHM Delete(T, key)
    i <- Hash(key, M)
    prev <- none
    for node x in T[i] do
        if x.key = key then
            if prev = none then T[i] <- x.next      // front node
            else prev.next <- x.next                // middle or last node
            N <- N - 1
            return success
        prev <- x
    return fail
```

- C implementation

```c
int delete(ChainingTable *t, char key, int *compares) {
    int i = hashOf(key, t->m);
    *compares = 0;
    Node *prev = NULL;
    for (Node *x = t->heads[i]; x != NULL; prev = x, x = x->next) {
        (*compares)++;
        if (x->key == key) {
            if (prev == NULL) {
                t->heads[i] = x->next; /* front node */
            } else {
                prev->next = x->next; /* middle or last node */
            }
            free(x);
            t->n--;
            return 1;
        }
    }
    return 0;
}
```

Deletion in chaining has no effect on any other slot. This is a big
difference from linear probing, which comes next.

### Analysis \{#sc-analysis}

Spread $$N$$ keys evenly over $$M$$ slots, and the average list length is
$$N/M$$. This value is called the **load factor** $$\alpha$$. In the example
$$\alpha = 10/5 = 2$$, and both searches finished in two comparisons.

| Operation | Average | Worst (every key in one slot) |
| --- | --- | --- |
| Search | $$O(1 + N/M)$$ | $$O(N)$$ |
| Insert | $$O(1 + N/M)$$ | $$O(N)$$ |
| Delete | $$O(1 + N/M)$$ | $$O(N)$$ |

If $$M$$ is chosen proportional to $$N$$, then $$N/M$$ is a constant, so all
three operations are $$O(1)$$ on average. The 1 is the hash computation, and
$$N/M$$ is the list search. The worst case is when a bad hash function piles
every key into one slot, and then the hash table becomes a single linked
list.

Choosing $$M$$ is a trade-off.

- **If $$M$$ is too large**, there are many empty slots (empty lists), and
  memory is wasted.
- **If $$M$$ is too small**, the lists grow long, and searching slows down.

Keep the same 10 keys and change only $$M$$, from 1 to 20. On the right, the
compares, the empty slots and the memory estimate change together.

<ChainSizeDemo />

With $$M = 1$$ the 10 keys line up in a single list, the same as a sequential
search. With $$M = 20$$ a successful search drops to 1.2 compares on average,
but 12 of the 20 slots are empty. Separate chaining picks $$M$$ so that
$$N/M$$ stays a small constant.

## Linear probing \{#linear-probing}

Chaining spends memory on a link for every list node. What if we spent that
memory on a bigger array instead? If the array is larger than the number of
keys ($$M > N$$), there is always an empty slot left, so on a collision we
can go find **an empty slot that is already there** and use it. This approach
is called **open addressing** hashing. It means a key can live in a slot
other than the one its hash points to.

The simplest of these is **linear probing**. On a collision, look at the
**next slot** of the table; if that is full too, look at the one after. Move
right one slot at a time until an empty slot turns up. On reaching the end of
the array, wrap around to slot 0. Looking into one slot is called a probe.

The table is kept as two arrays, one for keys and one for values. The size is
16.

### Insertion \{#lp-insert}

Insert the same `SEARCHEXAMPLE`. A key floats above the slots, starts at the
slot its hash points to, and slides right if that slot is full. The large
floating number is how many slots this operation probed, and the orange bar
below marks a run of consecutive full slots.

<ProbingDemo />

There are three scenes worth watching.

- `H` (hash 4) bumps into `A` at 4, `C` at 5, and `S` at 6 in turn, and goes
  into 7. It probed **4 slots**.
- `P` (hash 14) passes `R` at 14 and `X` at 15, goes past the end of the
  array, and lands in **slot 0**.
- `L` (hash 6) also bumps into slot 7, which is not its hash slot but is held
  by `H`. `H` was at 7 because of the collision at slot 4. Collisions breed
  collisions.

- Pseudocode

```plaintext
ALGORITHM Put(T, key, value)            // T.keys, T.values: two arrays of size M
    i <- Hash(key, M)
    while T.keys[i] ≠ EMPTY do          // move right until an empty slot
        if T.keys[i] = key then
            T.values[i] <- value        // same key found: only change the value
            return
        i <- (i + 1) mod M              // past the end, wrap around to slot 0
    T.keys[i] <- key, T.values[i] <- value
    N <- N + 1
```

- C implementation

```c
int put(ProbingTable *t, char key, int value, int *probes, int *slot) {
    if (t->n * 10 > t->m * 7) { /* double when the load factor N/M exceeds 0.7 */
        resize(t, 2 * t->m);
    }
    int i = hashOf(key, t->m);
    *probes = 1;
    while (t->keys[i] != EMPTY) {
        if (t->keys[i] == key) {
            t->values[i] = value;
            *slot = i;
            return 0;
        }
        i = (i + 1) % t->m; /* past the end, back to slot 0 */
        (*probes)++;
    }
    t->keys[i] = key;
    t->values[i] = value;
    t->n++;
    *slot = i;
    return 1;
}
```

The `resize` at the top is covered later in [Resizing](#lp-resize). `% t->m`
makes the array circular: after 15 comes 0.

### Search \{#lp-search}

`get` follows the same path. It starts at the slot its hash points to and
moves right; meeting **the key it wants** is a success, and meeting **an
empty slot** is a failure. It is safe to stop at an empty slot because, had
the key been there, it would have gone into that empty slot at the latest.

<ProbingDemo mode="search" />

`H` is found in 4 probes. The missing key `Y` hashes to 4, so it walks the
whole cluster from 4 to 8 and only learns it is **not there** on seeing the
empty slot 9. That is 6 probes. Chaining did the same job in 2 comparisons.
Failed searches are expensive in linear probing because of clusters. We come
back to this in [Clusters](#clustering).

```plaintext
ALGORITHM Get(T, key)
    i <- Hash(key, M)
    while T.keys[i] ≠ EMPTY do
        if T.keys[i] = key then return T.values[i]
        i <- (i + 1) mod M
    return none                         // an empty slot means the key is not there
```

### Deletion: you cannot just erase \{#lp-delete-naive}

What if we just empty the slot the key was in, as in chaining? Delete `C` and
then search for `H`.

<ProbingDemo mode="naive" />

`H` is still sitting in slot 7, yet it is not found. The path to `H` starts at
its hash slot 4 and has to pass through 5 and 6 to reach 7, but once 5 is
empty, `get` stops there. That is because **an empty slot means "nothing
beyond here."** Deleting `C` cut the path `H` used to take.

### Deletion: put the following keys back in \{#lp-delete}

So on deletion, the **keys that follow to the right** of the erased slot are
taken out one by one, up to the next empty slot, and put back in. Each key put
back finds a spot closer to its own hash slot, given where the empty slots are
now.

<ProbingDemo mode="delete" />

- `S` (hash 6) is taken out and put back, and stays at 6.
- `H` (hash 4) is pulled into 5, the empty slot right after `A` at 4.
- `L` (hash 6) is pulled into 7, the empty slot right after `S` at 6.
- Slot 9 is empty, so it stops. Now `H` is found in 2 probes.

- Pseudocode

```plaintext
ALGORITHM Delete(T, key)
    i <- Hash(key, M)
    while T.keys[i] ≠ key do            // find the key first
        if T.keys[i] = EMPTY then return fail
        i <- (i + 1) mod M
    T.keys[i] <- EMPTY, N <- N - 1
    i <- (i + 1) mod M
    while T.keys[i] ≠ EMPTY do          // the keys that followed in the same cluster
        k, v <- T.keys[i], T.values[i]
        T.keys[i] <- EMPTY, N <- N - 1
        Put(T, k, v)                    // take out and put back in
        i <- (i + 1) mod M
    if 0 < N ≤ M/8 then Resize(T, M/2)  // too empty: halve it
```

- C implementation

```c
int delete(ProbingTable *t, char key, int *probes) {
    int i = hashOf(key, t->m);
    *probes = 1;
    while (t->keys[i] != key) {
        if (t->keys[i] == EMPTY) {
            return 0;
        }
        i = (i + 1) % t->m;
        (*probes)++;
    }
    t->keys[i] = EMPTY;
    t->n--;

    i = (i + 1) % t->m;
    while (t->keys[i] != EMPTY) { /* keys that followed in the same cluster */
        char k = t->keys[i];
        int v = t->values[i];
        int p, slot;
        t->keys[i] = EMPTY;
        t->n--;
        put(t, k, v, &p, &slot);
        printf("  reinsert %c: slot %d -> %d\n", k, i, slot);
        i = (i + 1) % t->m;
    }
    if (t->n > 0 && t->n <= t->m / 8) { /* halve when at most 1/8 full */
        resize(t, t->m / 2);
    }
    return 1;
}
```

The keys put back amount to one cluster, so when clusters are short, deletion
is cheap too.

### Another way: tombstones \{#tombstone}

Instead of putting keys back, you can leave a **deletion marker** (a
tombstone) in the erased slot. The slot is never actually emptied, so the
path is not cut. This is called lazy deletion.

Delete `C` with a tombstone, then look up `H` and put `H` and `Y`.

<ProbingDemo mode="tombstone" />

`get H` passes the marker in slot 5 like a full slot and finds `H` in slot 7.
`put H` also passes the marker and updates the `H` in slot 7. `put Y` walks all
the way to the empty slot 9 to make sure `Y` is absent, and only then goes into
the remembered marker in slot 5. The practice code does not use this method, so
the numbers in this demo come from the demo alone.

- `get` passes a marked slot **as if it were full**. It stops only at empty
  slots.
- `put` can reuse a marked slot **as if it were empty**.
- Deletion is a single marker, so it is fast.

Two things need care, though. The first is a trap implementations often
fall into.

- **`put` must not insert into the first marked slot right away.** The same
  key may still be alive further along. It has to go on to an empty slot,
  confirm the same key is not there, and then insert into the first marked
  slot it passed. Otherwise the same key ends up in two slots.
- **Markers pile up.** Repeated deletes and inserts let markers join clusters
  together, and searches get slower and slower. When markers pile up, rebuild
  the table (rehash) to clean it.

### Resizing \{#lp-resize}

With linear probing, once the array is full there is nowhere to insert. As it
fills, clusters grow and it slows down too. So the array length is not fixed;
**it grows and shrinks according to the load factor.**

- **On insert**: when the array is at least a certain fraction full, double
  it. The threshold differs from one implementation to another (many use
  half); this example uses 0.7.
- **On delete**: if $$0 < N \le M/8$$, halve it.

Resizing changes $$M$$, so every hash value changes too. The slots cannot be
moved over as they are; **every key is put into the new array again.** That
costs $$O(N)$$ at once, but since the array doubles each time, spreading the
cost over the insertions in between makes it a constant per insertion.

Move the example table into an array of size 32. Starting at slot 0 of the old
array, take each key out and insert it again with its new hash. The small
number in a corner is how many slots a search for that key looks at.

## Clusters and the load factor \{#clustering}

In linear probing, a run of full slots with no empty slot in between is called
a **cluster**. In the example, slots 4 to 8 (`A C S H L`) form a cluster of
length 5. Slots 14 through 1 (`R X P M`) are also a cluster, one that wraps
past the end of the array.

Clusters grow on their own.

- **Wherever** a new key's hash lands inside a cluster, the key goes into the
  empty slot just past the cluster's right end. The longer the cluster, the
  more likely it is to take in a key.
- Each key that goes in lengthens the cluster by one slot, and sometimes joins
  it to the neighboring cluster to make an even longer one. In the example,
  when `P` went into 0, `R X` at 14 and 15 and `M` at 1 joined into one run.
- When a cluster is long, searching for a key hashed into it, and searching
  for a missing key, both have to walk to the end of the cluster.

Count how much an empty slot right after a cluster gains. In the 16-slot table
holding the example, each empty slot has a bar for the chance that the next key
lands there. If hash values come out evenly, that chance is (length of the
cluster just before it + 1)/16.

<ClusterGrowDemo />

Slot 9 sits right after the cluster from 4 to 8, so a hash anywhere from 4 to 9
ends up in 9. That is 6/16 = 37.5%, six times slot 3 (1/16), which has no
cluster before it. Press **Insert a random key** a few times, and long clusters
grow longer and run into each other.

### What the load factor costs \{#load-factor}

Move the load factor and compare the average search cost of the two methods.
The curves are the theory from the formulas below; the small numbers in the
table are runs that actually insert keys with random hash values into an array
of size 4096 and count. The units are those of the earlier demos: slots looked
at for linear probing, nodes compared for chaining.

<LoadCostDemo />

Assuming an even hash, the average number of slots probed in a linear probing
table with load factor $$\alpha = N/M$$ follows the approximations Knuth
derived.

$$
\text{success} \approx \frac{1}{2}\left(1 + \frac{1}{1-\alpha}\right) \qquad
\text{failure} \approx \frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)
$$

| Load factor $$\alpha$$ | Successful search | Failed search |
| --- | --- | --- |
| 1/2 | 1.5 | 2.5 |
| 3/4 | 2.5 | 8.5 |
| 7/8 | 4.5 | 32.5 |

- Half full, even a failed search takes 2.5 probes on average. It does not
  have to be exactly half; set the threshold by the search cost you can
  afford.
- At 3/4 a failed search takes 8.5 probes, and at 7/8, 32.5. With
  $$(1-\alpha)^2$$ in the denominator, it gets worse **sharply** as $$\alpha$$
  nears 1.
- Use table space too thriftily and you pay for it in time. So linear probing
  resizes to keep the load factor near 1/2.

As the load factor nears 1, the runs come out a little below the approximation.
At 7/8 they give about 30 instead of 32.5. Knuth's formulas are approximations
for a very large array, and in an array of fixed size the average miss is a bit
smaller. The larger the array, the closer the runs get.

Chaining is a different story. The lists just get longer and there is nowhere
to overflow, so it works even with $$\alpha$$ above 1 (the example had 2),
and the cost grows gently, in proportion to $$\alpha$$.

## Comparing the two methods \{#comparison}

| | Separate chaining | Linear probing |
| --- | --- | --- |
| Where a colliding key goes | that slot's linked list | the next empty slot in the array |
| Load factor | may exceed 1 | must be below 1 (usually near 1/2) |
| Extra memory | a link per node | empty slots |
| Deletion | change just one link | put the following keys back, or tombstones |
| What hurts performance | long lists | long clusters |
| Memory access | nodes are scattered | neighboring slots in order |

Run the same operations on both methods side by side. Type a letter and press
**Put**, **Get** or **Delete**; the two tables, which share the hash value
(ASCII code mod $$M$$), change together, and the compares and cells looked at
for that operation show up large. Changing $$M$$ inserts the keys again in the
order they went in.

<HashPlayDemo />

Make $$M$$ small and fill it up, and the gap widens. Chaining only makes a few
lists a little longer, but in linear probing the clusters join, and finding one
missing key walks through most of the array. Linear probing needs at least one
empty slot, so it takes at most $$M - 1$$ keys.

Here is memory use by the Java measure of Sedgewick's textbook (keys and
values are reference types), side by side with the binary search tree.

| Method | Space for $$N$$ keys |
| --- | --- |
| Separate chaining | about $$48N + 32M$$ bytes |
| Linear probing | between about $$32N$$ and $$128N$$ bytes |
| Binary search tree | about $$56N$$ bytes |

The range for linear probing is wide because, under the textbook's resizing
rule, the array is between 1/8 and 1/2 full. Chaining spends memory on list
links; linear probing spends it on empty slots. Linear probing, which looks at
neighboring slots in order, works well with the CPU cache and is often faster
in practice.

## Where hash tables fit \{#where-hashing-fits}

Given a table $$T$$ and a record $$x$$ (a key and a value), a hash table
supports three operations.

- `Insert(T, x)`
- `Delete(T, x)`
- `Search(T, x)`

It is the data structure to use **when you want fast search and do not care
about the sorted order of the records**. You can generally expect to find
things in $$O(1)$$.

Hashing is no cure-all, though.

- Every key type needs a **good hash function**.
- The performance guarantee depends on the quality of the hash function. With
  a bad hash function, every operation becomes $$O(N)$$.
- Computing the hash function can be hard and expensive. For a long string,
  the work grows with the number of characters.
- **Order-related operations are not easy.** Questions like the smallest key,
  the key right after a given key, or all keys in a range cannot be answered
  from the order the hash values scattered them in.

| | Binary search tree (balanced) | Hash table |
| --- | --- | --- |
| Search, insert, delete | $$O(\log N)$$ | $$O(1)$$ on average |
| Worst case | $$O(\log N)$$ | $$O(N)$$ (bad hash) |
| Minimum, range search, listing in order | yes | no |
| What keys need | comparison | a hash function and an equality test |

If you need order, use the [[bst|binary search tree]] of Topic 07; if you do
not need order and only want speed, use a hash table.

## What to keep \{#takeaway}

- **Hashing**: compute an array index from the key and find it without
  comparisons. It is a balance point between time and memory.
- **A good hash function**: its result is in $$[0, M-1]$$, it is easy to
  compute, and it spreads keys evenly. Integers use $$k \bmod M$$ (M a prime);
  strings use Horner's method to capture order.
- **Collisions are unavoidable.** Because of the pigeonhole principle, and,
  thanks to the birthday problem, quickly even with few keys.
- **Separate chaining**: a linked list per slot. A hash search, then a list
  search. $$O(1 + N/M)$$ on average, and deletion is easy.
- **Linear probing**: on a collision, go to the next slot. A search stops at
  an empty slot, so **you cannot just erase**; put the following keys back in,
  or leave a tombstone.
- **Clusters and the load factor**: in linear probing, clusters grow on their
  own, and it slows down sharply as $$\alpha$$ nears 1. So it resizes to keep
  $$\alpha$$ near 1/2.
- A hash table **gives up order to gain speed.** If you need order, use a
  binary search tree.
