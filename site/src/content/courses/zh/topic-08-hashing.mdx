> 主题 07 的二叉搜索树是**一边比较一边**找键。即使平衡得很好，也要比较
> $$O(\log n)$$ 次。  
> 本主题不靠比较来找。**从键直接算出位置**。  
> 这个计算就是哈希函数。不同的键指向同一个位置叫作冲突，如何解决冲突，
> 就是哈希表设计剩下的全部内容。

## 把键当作数组下标 \{#key-as-index}

假设键是 1 到 8 之间的小整数。那就没什么可想的了。把键为 `i` 的项放在
数组的 `i` 号格就行。

```plaintext
格    1   2   3   4   5   6   7   8
     [ ] [ ] [3] [ ] [5] [ ] [ ] [8]

find 3?  -> 看 A[3]。有。
find 5?  -> 看 A[5]。有。
find 7?  -> 看 A[7]。是空的，所以没有。
```

一次比较都不做。键本身就是地址，所以无论哪个键，访问一次内存，
$$O(1)$$ 就结束。

**哈希**（hashing）就是把这种方法推广到不是小整数的键上。像居民登记号、
姓名、学号和字符串这样，即使键很大或者不是整数，我们也想做同样的事。
为此需要两样东西。

- **哈希函数**：把键变成数组下标的计算
- **冲突解决**：不同的键变成同一个下标时的处理

### 在时间与内存之间 \{#time-memory}

哈希也是一种在时间与内存之间取得平衡的方法。

| 内存 | 能做的事 | 代价 |
| --- | --- | --- |
| 无限时 | 给每个可能的键各分一格，直接把键当下标 | 内存。若键是 13 位的居民登记号，就要 $$10^{13}$$ 格 |
| 极少时 | 全部放进一个未排序的数组，顺序查找 | 时间。每次查找都是 $$O(n)$$ |
| 适中时 | **哈希**：把键分散到大小适中的数组里，只单独处理重叠的部分 | 两者各付一点 |

想想咖啡店收银台的集点卡格子。按顾客姓名的首字母（A、B·C、W、数字·其他、
……）各有一格，找卡时不用翻遍整个盒子，只看一格。选出首字母就是哈希函数，
一格里插着好几张卡就是冲突。格子数远少于顾客数，所以内存用得少；只要翻
一格，所以时间也用得少。

## 哈希函数 \{#hash-function}

[[hash-function|哈希函数]]把键变成数组的下标值。数组大小为 $$M$$ 时，好的
哈希函数具备三点。

1. 结果总是落在整数 $$[0, M-1]$$ 之内。
2. 容易计算。
3. 把键**均匀地**散布到整个数组。

做法随键的种类而不同。

- **居民登记号**：键是数字，就直接用这个数字。
- **姓名**：键是字符串，就把字符串变成数字再用。
- **自定义的数据类型**：要亲自为它写哈希函数。

### 取模哈希 \{#modular-hashing}

这是对整数做哈希时最常用的方法。用正整数键 $$k$$ 除以数组大小 $$M$$ 的
**余数**作为下标。

$$
h(k) = k \bmod M
$$

余数总在 $$0$$ 到 $$M-1$$ 之间，所以第一个条件自然满足；只做一次除法，第二个
条件也满足。把字母 `A`、`B`、`C`、`K` 的 ASCII 码放进大小为 8 的数组试试。

<HashSlotDemo />

| 键 | 编码 | 哈希 ($$M = 8$$) |
| --- | --- | --- |
| A | 65 | 1 |
| B | 66 | 2 |
| C | 67 | 3 |
| K | 75 | 3 |

最后一行出了状况。`C` 和 `K` 是不同的键，却指向同一个 3 号格。这叫作
[[collision|冲突]]，英文是 collision。理想情况下，不同的键应该去往不同的
下标，但实际上不同的键可能被映射到同一个下标。

### M 取素数 \{#prime-m}

第三个条件（均匀）取决于 $$M$$ 怎么选。假设进来的键都是 4 的倍数。
$$M = 8$$ 时是这样。

<HashSlotDemo keys={[0, 4, 8, 12, 16, 20, 24, 28]} m={8} />

八格中只用到 0 号和 4 号两格。因为键和 $$M$$ 有公约数 4。把 $$M$$ 换成素数 7，
同样的键就散布到全部七格。

<HashSlotDemo keys={[0, 4, 8, 12, 16, 20, 24, 28]} m={7} />

所以数组大小 $$M$$ 要选**素数**（prime number）。素数与任何键都没有公约数，
除非那个键是它的倍数，所以不会被键中常见的模式（只有偶数、只有 10 的倍数）
左右。不过素数也不是万能的。如果键全是 7 的倍数，$$M = 7$$ 也只用到一格。

### 字符串哈希 \{#string-hashing}

字符串要先变成数字。最简单的想法是把字符编码加起来。可是这样一来，
**由相同字符换个顺序组成的字符串**都会得到同一个值。`stop`、`pots`、`tops`、
`spot`、`opts`、`post` 的字符编码之和全都相同。

要反映顺序，就给每一位加上权重。把前面各字符算出的值乘以一个小数
$$R$$（通常是 31），再加上下一个字符。这是计算多项式的霍纳法
（Horner's method）。每次都取除以 $$M$$ 的余数，值就不会变大。

$$
h \leftarrow (R \cdot h + \text{code}(c)) \bmod M
$$

- 伪代码

```plaintext
ALGORITHM SumHash(s, M)                 // 坏例子：不看字符顺序
    h <- 0
    for 字符 c in s do
        h <- (h + code(c)) mod M
    return h

ALGORITHM HornerHash(s, M)              // 好例子：每一位乘以 R，反映顺序
    h <- 0
    for 字符 c in s do
        h <- (R * h + code(c)) mod M    // 每次取余数，h 不会超过 M
    return h
```

- C 实现

```c
int hornerHash(const char *s, int m) {
    const int R = 31;
    int h = 0;
    for (int i = 0; s[i] != '\0'; i++) {
        h = (R * h + (unsigned char)s[i]) % m;
    }
    return h;
}
```

- 结果（`01_hash_function` 的一部分，$$M = 97$$）

```console
string keys, M = 97
  key   sum  horner
  stop   66       9
  pots   66      79
  tops   66       3
  spot   66      49
  opts   66      58
  post   66      49
```

只做加法的 `sum` 列，六个单词全部挤在 66 号格。霍纳法把它们分散到五格。
即便如此，`spot` 和 `post` 还是在 49 号相遇。好的哈希函数也无法消除冲突，
**只能减少冲突**。

## 冲突必然发生 \{#collisions-happen}

能不能做出一个不会发生冲突的哈希函数呢？出于两个原因，做不到。

- **鸽巢原理**：键比格子多（$$N > M$$）时，某一格里一定会有两个以上的键。
  可能成为键的值（所有姓名、所有字符串）总是远多于数组大小。
- **生日问题**：即使键远少于格子，冲突也很快就会发生。23 个人聚在一起，
  有两人生日相同的概率就超过一半。

把 $$N$$ 个键均匀随机地放进 $$M$$ 格时，要一次都不冲突，第二个键必须避开
第一个键的格，第三个键必须避开前两格。

$$
P(\text{至少冲突一次}) = 1 - \frac{M}{M} \cdot \frac{M-1}{M} \cdots \frac{M-N+1}{M}
$$

- 运行

```sh
cd src/topic-08-hashing/01_hash_function
make -f /work/Makefile hashFunction.out && ./hashFunction.out
```

- 结果（最后一段）

```console
chance of at least one collision
  N =  3, M =  16:  18.0%
  N =  5, M =  16:  50.0%
  N = 10, M =  16:  97.4%
  N = 23, M = 365:  50.7%
```

在 16 格的数组里只放五个键，发生冲突的概率就是一半。十个键几乎必然冲突。
所以哈希表不是要**避开**冲突，而是必须有**处理**冲突的办法。本主题看两种。

1. **拉链法**（separate chaining）：每格放一个链表，把冲突的键挂在上面。
2. **线性探测**（linear probing）：冲突时去找数组里的下一个空位。

## 本主题的示例数据 \{#example-data}

两种方式都用同一组数据来看。键是 `S E A R C H E X A M P L E` 这十三个字母，
值是出现的顺序（0 到 12）。`E` 出现三次，`A` 出现两次，所以后面的值覆盖前面的值。
不同的键有 10 个。

给每个字母定一个整数哈希码，用这个编码除以 $$M$$ 的余数作为哈希值。这些编码是
特意挑的，为的是让结果与原课程插图（Sedgewick 教材的例子）中的哈希值完全一致。
在真实的程序里，这个位置由前面的字符串哈希函数负责。

| 键 | A | C | E | H | L | M | P | R | S | X | Y |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 编码 | 20 | 69 | 10 | 4 | 38 | 49 | 78 | 14 | 22 | 47 | 52 |
| mod 5 (拉链法) | 0 | 4 | 0 | 4 | 3 | 4 | 3 | 4 | 2 | 2 | 2 |
| mod 16 (线性探测) | 4 | 5 | 10 | 4 | 6 | 1 | 14 | 14 | 6 | 15 | 4 |

`Y` 是不插入的键。查找不存在的键时用它。

## 拉链法 \{#separate-chaining}

在大小为 $$M$$ 的数组的每一格各放一个**链表**。哈希值相同的键一起挂在那一格的
链表上。把冲突的项按格分别串成链（chain），所以叫拉链法（separate chaining）。

查找是**两步查找**。

1. **哈希查找**：用哈希函数选出格子。$$O(1)$$
2. **链表查找**：从头开始顺序查找那一格的链表。

链表短的话，第二步也很快结束。所以 $$M$$ 要取得足够大。咖啡店的集点卡格子
正是这种结构。

### 插入 \{#sc-insert}

`put(key, value)` 用哈希找到格子，再把那一格的链表扫一遍。有相同的键就
**只改值**；扫到末尾都没有，就把新节点接到链表**最前面**。接在最前面就不必
一路找到链表末尾。反正为了确认有没有相同的键已经扫到了末尾，接在最后面比较
次数也一样。

放大显示的数字是这次 `put` 比较键的次数。

<ChainingDemo />

插入 `H` 时 4 号格里已有 `C` 和 `R`，比较了两次；插入 `M` 时比较了三次。第二个
`E`（值 6）在 0 号格经过 `A` 遇到 `E`，只把值从 1 改成 6。

- 伪代码

```plaintext
ALGORITHM Put(T, key, value)            // T：大小为 M 的数组，每格一个链表
    i <- Hash(key, M)
    for 节点 x in T[i] do               // 第 1 步：用哈希找到格子
        if x.key = key then             // 第 2 步：顺序查找那一格的链表
            x.value <- value            // 有相同的键就只改值
            return
    T[i] <- 新节点(key, value, next = T[i])    // 没有就接到最前面
    N <- N + 1
```

- C 实现

```c
int put(ChainingTable *t, char key, int value, int *compares) {
    int i = hashOf(key, t->m);
    *compares = 0;
    for (Node *x = t->heads[i]; x != NULL; x = x->next) {
        (*compares)++;
        if (x->key == key) {
            x->value = value;
            return 0;
        }
    }
    Node *node = malloc(sizeof(Node));
    node->key = key;
    node->value = value;
    node->next = t->heads[i]; /* 接到最前面 */
    t->heads[i] = node;
    t->n++;
    return 1;
}
```

数组 `heads` 的每一格是指向链表第一个节点的指针。一开始全是 `NULL`（空链表）。

### 查找 \{#sc-search}

`get(key)` 也是同样的两步。查找存在的键 `E` 和不存在的键 `Y`。

<ChainingDemo mode="search" />

`E` 在 0 号格经过 `A`，在第二个节点找到。`Y` 的哈希是 2，看过 2 号格的 `X` 和 `S`
后到达链表末尾，回答**不存在**。确认不存在也只要看那一格的链表，别的格子
不必看。

```plaintext
ALGORITHM Get(T, key)
    i <- Hash(key, M)
    for 节点 x in T[i] do
        if x.key = key then return x.value
    return 无                           // 走到链表末尾就是不存在
```

### 删除 \{#sc-delete}

`delete(key)` 找到键之后改一个链接。找到的节点在最前面，就让格子指向下一个节点；
在中间或末尾，就让前一个节点跳过它。

<ChainingDemo mode="delete" />

- 伪代码

```plaintext
ALGORITHM Delete(T, key)
    i <- Hash(key, M)
    prev <- 无
    for 节点 x in T[i] do
        if x.key = key then
            if prev = 无 then T[i] <- x.next        // 第一个节点
            else prev.next <- x.next                // 中间或末尾的节点
            N <- N - 1
            return 成功
        prev <- x
    return 失败
```

- C 实现

```c
int delete(ChainingTable *t, char key, int *compares) {
    int i = hashOf(key, t->m);
    *compares = 0;
    Node *prev = NULL;
    for (Node *x = t->heads[i]; x != NULL; prev = x, x = x->next) {
        (*compares)++;
        if (x->key == key) {
            if (prev == NULL) {
                t->heads[i] = x->next; /* 第一个节点 */
            } else {
                prev->next = x->next; /* 中间或末尾的节点 */
            }
            free(x);
            t->n--;
            return 1;
        }
    }
    return 0;
}
```

拉链法的删除对其他格子没有任何影响。这一点与后面的线性探测大不相同。

### 分析 \{#sc-analysis}

把 $$N$$ 个键均匀分散到 $$M$$ 格，链表长度的平均值是 $$N/M$$。这个值叫作
**装载因子**（load factor）$$\alpha$$。示例中 $$\alpha = 10/5 = 2$$，两次查找都在
两次比较内结束。

| 操作 | 平均 | 最坏（所有键在同一格） |
| --- | --- | --- |
| 查找 | $$O(1 + N/M)$$ | $$O(N)$$ |
| 插入 | $$O(1 + N/M)$$ | $$O(N)$$ |
| 删除 | $$O(1 + N/M)$$ | $$O(N)$$ |

让 $$M$$ 与 $$N$$ 成正比，$$N/M$$ 就是常数，三种操作平均都是
$$O(1)$$。前面的 1 是计算哈希，$$N/M$$ 是查找链表。最坏情况是哈希函数太差，
所有键都挤进一格，这时哈希表就变成了一个链表。

确定 $$M$$ 是一种权衡。

- **$$M$$ 太大时**，空着的格子（空链表）变多，浪费内存。
- **$$M$$ 太小时**，链表变长，查找变慢。

## 线性探测 \{#linear-probing}

拉链法要为链表的每个链接花内存。不如把这些内存拿去把数组变大，会怎样？数组比
键多（$$M > N$$）时总会剩下空位，冲突时去找**已有的空位**来用就行。这种方式叫作
**开放寻址**（open addressing）哈希。意思是，键也可以住在哈希指向的格子以外的
其他格子里。

其中最简单的就是**线性探测**。冲突时看表的**下一格**，还被占着就再看下一格。
一格一格向右走，直到遇到空位。到了数组末尾就回到 0 号格。查看一个格子叫作
探测（probe）。

数组用存键和存值的两个数组来表示。大小是 16。

### 插入 \{#lp-insert}

插入同样的 `SEARCHEXAMPLE`。键浮在格子上方，从哈希指向的格子出发，被占着就
向右滑。放大显示的数字是这次操作查看的格数，下方的橙色条是被占格子连成的一片。

<ProbingDemo />

有三个场景值得留意。

- `H`（哈希 4）依次撞上 4 号 `A`、5 号 `C`、6 号 `S`，进入 7 号。看了
  **4 格**。
- `P`（哈希 14）经过 14 号 `R`、15 号 `X`，越过数组末尾进入 **0 号格**。
- `L`（哈希 6）不只撞上自己的哈希格，还撞上被 `H` 占着的 7 号。`H` 是因为 4 号
  位置的冲突才来到 7 号的。冲突引来冲突。

- 伪代码

```plaintext
ALGORITHM Put(T, key, value)            // T.keys, T.values：两个大小为 M 的数组
    i <- Hash(key, M)
    while T.keys[i] ≠ 空 do             // 向右走，直到遇到空位
        if T.keys[i] = key then
            T.values[i] <- value        // 有相同的键就只改值
            return
        i <- (i + 1) mod M              // 到了末尾就回到 0 号格
    T.keys[i] <- key, T.values[i] <- value
    N <- N + 1
```

- C 实现

```c
int put(ProbingTable *t, char key, int value, int *probes, int *slot) {
    if (t->n * 10 > t->m * 7) { /* 装载因子 N/M 超过 0.7 就扩大一倍 */
        resize(t, 2 * t->m);
    }
    int i = hashOf(key, t->m);
    *probes = 1;
    while (t->keys[i] != EMPTY) {
        if (t->keys[i] == key) {
            t->values[i] = value;
            *slot = i;
            return 0;
        }
        i = (i + 1) % t->m; /* 到了末尾就回到 0 号格 */
        (*probes)++;
    }
    t->keys[i] = key;
    t->values[i] = value;
    t->n++;
    *slot = i;
    return 1;
}
```

开头的 `resize` 在后面的[调整大小](#lp-resize)里看。`% t->m` 让数组成为
环形。15 号的下一格是 0 号。

### 查找 \{#lp-search}

`get` 也走同一条路。从哈希指向的格子出发向右走，遇到**要找的键**就成功，遇到
**空位**就失败。可以在空位停下，是因为那个键如果存在，最晚也会被放进那个空位。

<ProbingDemo mode="search" />

`H` 用 4 格找到。不存在的键 `Y` 哈希是 4，要从 4 号到 8 号把簇走完，看到 9 号的
空位，才知道它**不存在**。共 6 格。同样的事在拉链法里只要比较 2 次。线性探测里
查找失败代价高，是因为簇。这一点在后面的[簇](#clustering)里再看。

```plaintext
ALGORITHM Get(T, key)
    i <- Hash(key, M)
    while T.keys[i] ≠ 空 do
        if T.keys[i] = key then return T.values[i]
        i <- (i + 1) mod M
    return 无                           // 遇到空位，就说明那个键不存在
```

### 删除：不能直接清空 \{#lp-delete-naive}

如果像拉链法那样只把键所在的格子清空，会怎样？删除 `C`，再查找 `H`。

<ProbingDemo mode="naive" />

`H` 明明还在 7 号格，却找不到。找 `H` 的路要从哈希格 4 号出发，经过 5 号、6 号
到达 7 号，可是 5 号变成空位后，`get` 就停在那里。因为**空位的意思是"从这里
往后都没有"**。删除 `C` 切断了 `H` 平时走的路。

### 删除：把跟在后面的键重新插入 \{#lp-delete}

所以删除时，要把被删格子**右边连着的键**一个个取出再重新插入，直到遇到空位。
重新插入的键会按现在的空位分布，找到离自己哈希格更近的位置。

<ProbingDemo mode="delete" />

- `S`（哈希 6）取出再插入，还是 6 号。
- `H`（哈希 4）被拉进 4 号 `A` 后面空出的 5 号。
- `L`（哈希 6）被拉进 6 号 `S` 后面空出的 7 号。
- 9 号是空的，于是停下。现在 `H` 用 2 格就能找到。

- 伪代码

```plaintext
ALGORITHM Delete(T, key)
    i <- Hash(key, M)
    while T.keys[i] ≠ key do            // 先找到这个键
        if T.keys[i] = 空 then return 失败
        i <- (i + 1) mod M
    T.keys[i] <- 空, N <- N - 1
    i <- (i + 1) mod M
    while T.keys[i] ≠ 空 do             // 同一簇中跟在后面的键
        k, v <- T.keys[i], T.values[i]
        T.keys[i] <- 空, N <- N - 1
        Put(T, k, v)                    // 取出再重新插入
        i <- (i + 1) mod M
    if 0 < N ≤ M/8 then Resize(T, M/2)  // 太空就缩小一半
```

- C 实现

```c
int delete(ProbingTable *t, char key, int *probes) {
    int i = hashOf(key, t->m);
    *probes = 1;
    while (t->keys[i] != key) {
        if (t->keys[i] == EMPTY) {
            return 0;
        }
        i = (i + 1) % t->m;
        (*probes)++;
    }
    t->keys[i] = EMPTY;
    t->n--;

    i = (i + 1) % t->m;
    while (t->keys[i] != EMPTY) { /* 同一簇中跟在后面的键 */
        char k = t->keys[i];
        int v = t->values[i];
        int p, slot;
        t->keys[i] = EMPTY;
        t->n--;
        put(t, k, v, &p, &slot);
        printf("  reinsert %c: slot %d -> %d\n", k, i, slot);
        i = (i + 1) % t->m;
    }
    if (t->n > 0 && t->n <= t->m / 8) { /* 空到八分之一以下就缩小一半 */
        resize(t, t->m / 2);
    }
    return 1;
}
```

重新插入的键只有一个簇那么多，所以簇短的话，删除也很便宜。

### 另一种方法：删除标记 \{#tombstone}

也可以不重新插入键，而是在被删的格子里留下**删除标记**（tombstone，墓碑）。
格子实际上没有清空，所以路不会断。这叫作惰性删除（lazy deletion）。

- `get` 把有标记的格子**当作被占的格子**走过去。只在空位停下。
- `put` 可以把有标记的格子**当作空位**重新使用。
- 删除只要留一个标记就结束，所以很快。

不过有两点要小心。

- **`put` 不能直接放进第一个标记格**。因为相同的键可能还活在它后面。要走到
  空位、确认没有相同的键之后，再放进途中经过的第一个标记格。否则同一个键会
  出现在两个格子里。
- **标记会越积越多**。反复删除和插入，标记会把簇连起来，查找越来越慢。标记多了
  就新建一张表（重新哈希）来清理。

### 调整大小 \{#lp-resize}

线性探测在数组满了之后就没地方放了。越满簇越长，也会变慢。所以数组长度不固定，
而是**看装载因子来扩大和缩小**。

- **插入时**：数组满到一定比例以上就扩大一倍。通常以一半为界，实践代码用 0.7。
  界限随设定而不同。
- **删除时**：$$0 < N \le M/8$$ 时缩小一半。

大小一变，$$M$$ 就变了，哈希值也全都变了。所以不能原样搬格子，而要**把所有键
重新插入新数组**。一次要花 $$O(N)$$，但因为每次扩大一倍，把这个代价分摊到此前的
各次插入上，每次插入是常数。

实践代码把示例的表重新插入大小为 32 的数组来比较。下面是运行结果中的
`resize` 部分。

## 簇与装载因子 \{#clustering}

在线性探测中，被占的格子中间没有空位、连成一片的一段叫作**簇**（cluster）。
示例中 4 号到 8 号（`A C S H L`）是长度为 5 的簇。14 号到 1 号（`R X P M`）
也是越过数组末尾连起来的簇。

簇会自己长大。

- 新键的哈希无论落在簇里的**哪里**，这个键都会进入簇右端之后的那个空位。
  簇越长，接收新键的概率越大。
- 进来的键让簇长一格，有时还会和旁边的簇接起来，形成更长的簇。示例中 `P` 一进入
  0 号，14·15 号的 `R X` 和 1 号的 `M` 就连成了一片。
- 簇一长，哈希到簇里的键的查找、不存在的键的查找，都得走到簇的末尾。

用同样的随机哈希值，把 256 个和 128 个键放进大小为 512 的数组。左边是
线性探测，右边作为对照，是冲突时随便重新挑一个空位的情形。

<ClusterFigure />

装载因子为 1/2 时，线性探测一侧经常出现橙色的长簇。把装载因子降到 1/4，
簇就变短了。簇越短，性能越好。

### 装载因子决定的代价 \{#load-factor}

假设哈希是均匀的，在装载因子 $$\alpha = N/M$$ 的线性探测表中，查看格数的平均值
服从高德纳（Knuth）求出的近似值。

$$
\text{成功} \approx \frac{1}{2}\left(1 + \frac{1}{1-\alpha}\right) \qquad
\text{失败} \approx \frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)
$$

| 装载因子 $$\alpha$$ | 成功查找 | 失败查找 |
| --- | --- | --- |
| 1/2 | 1.5 | 2.5 |
| 3/4 | 2.5 | 8.5 |
| 7/8 | 4.5 | 32.5 |

- 只装一半时，失败查找平均也只要 2.5 格。不一定非得是一半，看能承受的查找
  代价来定界限就行。
- 3/4 时失败查找要 8.5 格，7/8 时要 32.5 格。分母里有 $$(1-\alpha)^2$$，
  所以越接近 1 就**急剧**变差。
- 把表的空间用得太省，就要在时间上付出代价。所以线性探测通过调整大小，
  把装载因子保持在 1/2 附近。

拉链法情况不同。链表只是变长，没有溢出的地方，所以 $$\alpha$$ 超过 1 也能工作
（示例是 2），代价也随 $$\alpha$$ 成比例地平缓增长。

## 两种方式的比较 \{#comparison}

| | 拉链法 | 线性探测 |
| --- | --- | --- |
| 冲突的键放在哪里 | 那一格的链表 | 数组的下一个空位 |
| 装载因子 | 可以超过 1 | 必须小于 1（通常在 1/2 附近） |
| 额外内存 | 每个节点的链接 | 空位 |
| 删除 | 只改一个链接 | 重新插入后面的键，或用删除标记 |
| 损害性能的因素 | 长链表 | 长簇 |
| 内存访问 | 节点分散各处 | 依次查看相邻的格子 |

按 Sedgewick 教材的 Java 标准（键和值是引用类型）来看内存用量是这样的。
与二叉搜索树并列放在一起。

| 方法 | $$N$$ 个键的空间 |
| --- | --- |
| 拉链法 | 约 $$48N + 32M$$ 字节 |
| 线性探测 | 约 $$32N$$ 到 $$128N$$ 字节之间 |
| 二叉搜索树 | 约 $$56N$$ 字节 |

线性探测的范围宽，是因为按教材的调整大小规则，数组的装满程度在 1/8 到 1/2
之间。拉链法把内存花在链表的链接上，线性探测把这些内存花在空位上。依次查看
相邻格子的线性探测与 CPU 缓存很合拍，实际上往往更快。

## 哈希表的位置 \{#where-hashing-fits}

给定表 $$T$$ 和记录 $$x$$（键和值）时，哈希表支持三种操作。

- `Insert(T, x)`
- `Delete(T, x)`
- `Search(T, x)`

这是在**希望查找快、并且不考虑记录的排列顺序时**使用的数据结构。一般期望在
$$O(1)$$ 内找到。

但这并不意味着哈希是万灵药。

- 每种键类型都要有**好的哈希函数**。
- 性能保证取决于哈希函数的质量。遇到差的哈希函数，所有操作都会变成
  $$O(N)$$。
- 哈希函数的计算可能既难又贵。长字符串有多少字符就要算多少次。
- **与顺序有关的操作不容易做**。最小的键、紧跟某个键的下一个键、范围内的
  所有键这类问题，靠哈希值打乱后的顺序是答不出来的。

| | 二叉搜索树（平衡） | 哈希表 |
| --- | --- | --- |
| 查找·插入·删除 | $$O(\log N)$$ | 平均 $$O(1)$$ |
| 最坏 | $$O(\log N)$$ | $$O(N)$$（差的哈希） |
| 最小值、范围查找、按序列出 | 可以 | 不行 |
| 对键的要求 | 比较 | 哈希函数与相等判断 |

需要顺序就用主题 07 的[[bst|二叉搜索树]]，不需要顺序、只要快，就用哈希表。

## 要带走的 \{#takeaway}

- **哈希**：从键算出数组下标，不经比较就能找到。它是时间与内存之间的
  平衡点。
- **好的哈希函数**：结果落在 $$[0, M-1]$$ 之内，计算容易，把键均匀散布。整数用
  $$k \bmod M$$（M 取素数），字符串用霍纳法反映顺序。
- **冲突必然发生**。因为鸽巢原理；又因为生日问题，即使键很少也很快就会
  发生。
- **拉链法**：每格一个链表。哈希查找之后再查找链表。平均
  $$O(1 + N/M)$$，删除容易。
- **线性探测**：冲突就去下一格。查找在空位停下，所以**不能直接清空**，要把
  后面的键重新插入，或留下删除标记。
- **簇与装载因子**：线性探测的簇会自己长大，$$\alpha$$ 接近 1 时急剧变慢。
  所以要调整大小，把 $$\alpha$$ 保持在 1/2 附近。
- 哈希表**放弃顺序，换来速度**。需要顺序就用二叉搜索树。
