## What the assignment is about \{#what}

Chat and agent use the same AI, but they work in different places.

| | Chat | Agent |
| --- | --- | --- |
| Does it know my code | Only what I paste in | Reads the files in the repository itself |
| Where does the result go | I copy the answer and paste it | It creates and edits files itself |
| Does it run anything | No | Runs the tests in the terminal and reads the failures |
| Does it remember rules | Forgets when the conversation ends | Reads the rules file every time |

The more the agent can do, the clearer the human's part becomes.

- **I decide what to build.** The AI may draft the specification, but editing it and deciding is the human's job.
- **I check that it is right.** Agents are wrong in convincing ways. Tests and real runs catch it.
- **I leave points to go back to.** Committing after every step means anything the agent breaks can be undone.

You build a URL shortener on top of the hash table from [Topic 08](/course/topic-08-hashing/).
Give it a long URL and it returns a short code such as `1`, `2`, `3`; open that code and
it sends you to the original address. At the end you run the server in your Codespace
and **open the short link on your own phone.**

## Seven steps \{#steps}

Each step repeats **issue → request → check → commit → log**.

You could commit with git commands or with VS Code's Source Control view. This time
**git is the agent's job too.** At the start, ask once:

```text
Let us manage this repository with git flow.
First create a develop branch from main.
I will open one GitHub issue per step, numbered the same as the step.
For each step, branch feature/<issue-number>-<short-name> off develop and work there,
and leave progress comments on that issue as you go.
When the step is done, commit, merge it into develop and close the issue.
Write commit messages as "Step N: what was done (#issue-number)".
Push to GitHub every time you commit or merge.
```

- Each example request below starts with **the step and issue number** and ends with **"When done, commit, merge into develop and push."**
  Copy it as is and the branch and commit come along. The issue number tells the agent where to comment
  and which branch to create.
- Keep going in **the same chat** where you set up git. Do not switch chats until step 5 opens a new one.
- A commit is a point to go back to. After the agent commits, check what went in with the Source Control view or `git log`.
- Before submitting, have it merge develop into main and push. Grading and the ZIP use main on GitHub.

The first push may stop and ask, as below. Creating the branch went ahead without asking, but
sending work out to GitHub is judged risky, so it asks and gives a reason.

<Image src={assistedPush} alt="Approval box in the Copilot chat: Run in terminal: Publish the develop branch to GitHub, command git push -u origin develop, reason Publishing develop itself was not specifically authorized, buttons Allow Once, Skip, Explain" />

- **Allow Once**: allows it just this once.
- **Skip**: does not run it.
- **Explain**: explains what it is about to do first. Start here if you do not know the command.

The agent judges the scope against what you asked. This box came from its judgment that
publishing develop itself was not specifically requested.

### Step 1. Chat and agent side by side \{#step-1}

Build the same feature both ways and see the difference. The feature is base62
encoding, which turns an integer into short text: base 62 written with the 62
characters `0-9`, `a-z`, `A-Z`.

First the **chat way**. Ask the **chat AI you usually use in the browser** (ChatGPT, Gemini and so on):

```text
Write base62 encode/decode functions in Python
```

Copy the answer into `src/base62.py` and work out for yourself how to run it.

Now ask in the **Copilot chat in your Codespace**. Delete the pasted file and ask:

```text
This is step 1, issue #1.
In src/base62.py, write encode(n) and decode(s).
encode(n) turns an integer n >= 0 into a base-62 string using 0-9, a-z, A-Z in that order,
and decode(s) is its inverse.
Write unittest tests in tests/test_base62.py,
then run make test in the terminal and show me that they pass.
When done, commit, merge into develop and push.
```

The agent creates files, runs the tests in the terminal, and fixes failures. With Assisted
permissions it asks only before commands that look risky, like the push shown earlier. **You are the one who decides.**
When it asks, read and decide; for commands it ran without asking, read the record in the chat.

What to check

- What does `encode(0)` return? An empty string is a common bug.
- Did the chat answer and the agent answer use the same character order? If you do not say, the AI picks one.
- What did you do by hand in each approach? That is section 3 of `AGENT_LOG.md`.

### Step 2. The AI drafts the specification, I edit it \{#step-2}

As step 1 showed, whatever you leave out the AI decides for you. The same goes for the
specification. Get a draft from the agent, and **decide what to build by editing it yourself.**

```text
This is step 2, issue #2.
Fill in the #SPEC.md template with a draft specification of the URL shortener we are building.
Store data in a hash table we implement ourselves (linear probing, Horner hash),
and do not use dict, set or the built-in hash().
Write only the draft, no code.
We will commit after I edit it.
```

Writing `#SPEC.md` with a `#` attaches that file to the request. Check that the file shows up as a chip in the input box.

When the draft arrives, read how it answers each question below and edit anything that differs from what you want.
Delete the `TEMPLATE:` line at the top if it is still there.

- **Hash table**: how are collisions resolved? What is the hash function? When does the table grow?
- **Shortener**: does the same URL get the same code twice? Is an unknown code an error or `None`?
- **Bad input**: what happens to an address starting with `ftp://`, one with a space, a very long one?
- **Edge cases**: list everything to turn into tests. This list becomes the tests in step 4.

Decide that the hash table uses **linear probing** and the **Horner hash** from Topic 08,
and does not use Python's `dict`, `set` or built-in `hash()`. This assignment is about
building the hash table yourself. The built-in `hash()` gives strings a different value
on every run, so rerunning the step 6 experiment would give different numbers.

This step is about finding where the AI filled in blanks on its own and fixing them. Write what
you changed in the step 2 row of `AGENT_LOG.md`. When you are done editing, ask for the commit.

```text
Step 2, continued (issue #2).
I have edited SPEC.md.
Commit it, merge into develop and push.
```

### Step 3. A plan before code \{#step-3}

Do not say "build it" right away. Get a plan first and review it.

```text
This is step 3, issue #3.
Read SPEC.md, write a step-by-step implementation plan and save it to PLAN.md.
Do not write any code yet.
When done, commit, merge into develop and push.
```

You may switch the agent mode to **Plan** for this. Plan shows the plan first and runs only
after you approve. Either way, have the plan saved to `PLAN.md`, and switch back to
**Autopilot** afterwards.

Read `PLAN.md`, find where it disagrees with the specification, and fix it yourself.
These come up often:

- It plans to store URL→code in a `dict`. That breaks the specification.
- It plans to make the code a hash of the URL. Then two different URLs can get the same code.
- It plans to write the tests last. Change the order.

Fixing the plan is much cheaper than fixing the code.

### Step 4. Tests first, implementation by the agent \{#step-4}

Ask for the tests only.

```text
This is step 4, issue #4.
Turn the edge cases in section 6 of SPEC.md into unittest tests.
Put them in tests/test_hash_table.py and tests/test_shortener.py.
Do not implement anything yet.
When done, commit, merge into develop and push.
```

**Read** the tests. Check that every edge case from the specification is there and that
the expected values are right. Add whatever is missing yourself and commit. `make test`
fails at this point, which is expected: there is no implementation yet.

Then ask for the implementation.

```text
Step 4, continued (issue #4).
Implement src/hash_table.py and src/shortener.py in the order of PLAN.md,
and keep fixing them until make test passes.
Do not change the tests.
When done, commit, merge into develop and push.
```

**"Do not change the tests" matters.** Without it the agent sometimes quietly edits a
test it cannot pass. When it finishes, open the changed files, read the diff and commit.

### Step 5. Give the rules as a file \{#step-5}

Check in the terminal whether the agent followed the specification.

```sh
grep -n "dict\|set(\|hash(" src/*.py
```

A rule in the specification does nothing if the agent never reads `SPEC.md`. The agent
reads only the files that look relevant at the moment. **`.github/copilot-instructions.md`,
on the other hand, is read with every request.** Create this file yourself and write the
repository's rules in it.

- `.github/copilot-instructions.md` (part of an example)

```md
# To the agent working in this repository

- Read SPEC.md before writing code.
- Do not use dict, set or the built-in hash() inside src/. Use the hash table we built.
- After changing code, run make test and show the result.
- If a test fails, fix the code, not the test.
- For each issue, work on feature/<issue-number>-<name> off develop and post progress as issue comments.
- When done, commit, merge into develop, push and close the issue.
- I am a first-year student. Summarize what you changed in at most three lines.
```

The two git rules are what you asked in the chat at the start. A new chat does not
know the earlier conversation, so move anything that must keep applying into the rules file.

Open a new chat and ask it to check. If anything broke the rules, have it fixed.

```text
This is step 5, issue #5.
Check whether the code in src/ follows this repository's rules,
and fix anything that breaks them.
When done, commit, merge into develop and push.
```

A rules file is a habit that outlives this assignment. Put one in your project repository too.

### Step 6. Verify the result yourself \{#step-6}

Passing tests do not make a hash table a **good** one. As Topic 08 showed, linear probing
slows down sharply as the load factor approaches 1. Measure whether your table does.

```text
This is step 6, issue #6.
Create experiments/probe_experiment.py.
Fill a HashTable(max_load=None) of fixed size 4093 with random URLs.
For load factors from 0.1 to 0.9,
measure the average number of slots probed for successful and unsuccessful searches.
Compare them in a table with Knuth's approximations from Topic 08.
hit ≈ (1 + 1/(1-α))/2, miss ≈ (1 + 1/(1-α)²)/2
Save experiments/results.csv and an SVG chart.
Do not use external libraries.
When done, commit, merge into develop and push.
```

Run `make experiment` and **judge the numbers yourself.**

- At load factor 1/2, are hits near 1.5 and misses near 2.5?
- If they are far from theory, find out why. Check whether the first slot was counted as 0, or whether the hash function differs from the specification.
- Can you read the axis labels and the legend?

### Step 7. Serve it \{#step-7}

Finally, add a web server.

```text
This is step 7, issue #7.
Create src/server.py as described in section 5 of SPEC.md.
Use only the standard http.server module,
and make it start on port 8000 with make serve.
When done, commit, merge into develop and push.
```

Start it with `make serve` and open it on your phone.

1. In the bottom panel, find port 8000 on the **Ports** tab.
2. Right-click the row → **Port Visibility** → **Public**
3. Open the **Forwarded Address** on your phone.
4. Enter a long URL, get a short link, and tap it to see that it goes to the original address.

If the short link shows `localhost:8000`, the agent did not know about the proxy.
Codespaces passes the requested address in the `X-Forwarded-Host` header. Things like this
are the "places the agent was wrong" for section 2 of `AGENT_LOG.md`.

**Anyone on the internet can open a public port.** When you are done, stop the server with
`Ctrl+C` and switch the port back to **Private**. Restarting the Codespace also makes it private again.

## Catching up on a missed step \{#catchup}

If you miss a step in class you can still go on. Commit what you have, then give the

`AGENT_LOG.md`. Write "caught up" in the log for that step. Catching up costs no points,
but you cannot use that step for "places the agent was wrong."

## Grading \{#grading}

We look at **what you decided and what you caught**, not at how well the agent did.
Agent output differs from person to person, so grading only the finished product would
let luck decide the score.

| Item | Points | What we look at |
| --- | --- | --- |
| Specification and tests | 1 | You recorded what you changed in the AI's draft, and the tests check every edge case |
| Rules file | 1 | The rules are concrete and actually had an effect |
| Hash table and experiment | 1 | Works without `dict`, and measured values are compared with theory and explained |
| Work log | 1.5 | Concretely describes how you noticed and fixed mistakes |
| Service | 0.5 | Starts with `make serve` and the short link redirects |
