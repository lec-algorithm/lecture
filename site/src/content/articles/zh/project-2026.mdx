## 这是一个什么样的项目 \{#what}

作业1 中你选了三种排序进行比较。个人项目沿用同样的框架，只是比较的对象不再是
排序，而是**你自己选定的主题**。

- 选一个你感兴趣的问题。
- 找出已经在解决这个问题的**三种以上**现有方法。
- 亲手实现或运行这三种方法，并在相同条件下执行。
- 说明什么在哪里更快、什么在哪里崩掉，以及为什么。
- 整理各自的优缺点，并写出还可以往哪个方向发展。

## 选择主题 \{#topic}

主题自由，但要守住三个条件。

| 条件 | 含义 |
| --- | --- |
| 能以代码运行 | 必须能产生结果，并且可以测量时间或次数 |
| 存在多种方法 | 解决同一问题的方法必须已经有三种以上 |
| 可以公开 | 不使用无法放进公开仓库的数据或代码 |

主题不限于计算机领域。通信、电路与信号、纳米与材料、生物等等，
从自己的专业或兴趣里选也可以。只要能用代码跑起来并加以比较就行。

下面是一些例子。可以直接采用，也可以只当作提示。

| 领域 | 值得比较的内容 |
| --- | --- |
| 字符串 | 子串查找 (朴素比较 · KMP · Boyer-Moore · Rabin-Karp) |
| 压缩 | 文件压缩 (哈夫曼 · RLE · LZ77) |
| 路径 | 地图上的最短路径 (BFS · Dijkstra · A\*) |
| 推荐 | 电影或音乐推荐 (按热度 · 协同过滤 · 基于内容) |
| 图像 | 图像缩小 (最近邻 · 双线性插值 · seam carving) |
| 数据结构 | 自动补全 (有序数组二分查找 · 字典树 · 哈希) |
| 生成 | 迷宫生成 (递归回溯 · Prim · Kruskal) |
| 数据 | 去重 (哈希 · 排序后扫描 · 布隆过滤器) |
| 通信 | 纠错码 (汉明码 · CRC · 里德-所罗门码) |
| 信号 · 电路 | 从信号中找出频率 (直接计算 DFT · FFT · 自相关) |
| 纳米 · 材料 | 晶格上的扩散模拟 (欧拉法 · 龙格-库塔法 · 蒙特卡罗) |
| 生物 | DNA 序列比对 (Needleman-Wunsch · Smith-Waterman · BLAST 式启发式) |

不需要事先获得审批。主题在中期提交时确定下来。

## 先定下比较标准 \{#criteria}

“哪一个更好”，没有标准就无法回答。
先定下**两个以上**标准，再用这些标准在相同条件下测量三种方法。

- **速度**：运行时间，或者比较次数、运算次数这类可以计数的值
- **内存**：额外占用的空间
- **结果的质量**：准确率、压缩率、推荐命中率等随主题而异的值
- **随输入的变化**：规模变大时、输入有偏时会怎样变化
- **实现成本**：代码长度、自己花掉的时间，如实写出来即可

不要把[[time-complexity]]写进表格就算完事，要和实际测到的数字对照。标着
$$O(n \log n)$$ 的方法在小输入上更慢是常见的事。找出并解释这种偏差，才是一份
好报告。

## 中期提交（10 月 18 日）\{#interim}

用**大约 10 页幻灯片**说明你要做什么、打算怎么比较。
此时还没有实验结果也没关系。这是看计划的环节。

| 页 | 内容 |
| --- | --- |
| 1 | 标题、学号、姓名 |
| 2 | 选定的主题和选它的理由 |
| 3 | 用一句话写出要解决的问题 |
| 4\~6 | 要比较的三种方法，每种一页 |
| 7 | 比较标准与测量方法 |
| 8 | 实验设计（输入数据、规模、重复次数） |

- 上面这八页必须有，剩下的页数自由使用。
- 格式为 **PDF**。用什么工具制作都可以。
- 10 页是基准，8\~12 页都可以。

## 最终提交（12 月 13 日）\{#final}

### 报告 \{#report}

- 以 **PDF** 文件提交。篇幅最少 5 页，最多 20 页
- 在第一页写上 GitHub 仓库 URL。
- 实验结果要用**截图和图表**呈现。只罗列数字的报告很难读。

目录这样安排就够用了。

1. 主题与动机
2. 三种方法的说明（原理、伪代码或核心代码）
3. 比较标准与实验设计
4. 实验结果（表 · 图表 · 运行画面截图）
5. 解读：为什么会出现这样的结果
6. 优缺点整理
7. 发展方向：如果继续做会做什么
8. 参考资料与 AI 使用记录

报告用 Markdown 写、用 Word 或 Hangul 写都可以。
**提交的是 PDF**。

### 代码 \{#code}

- 必须提交 GitHub 仓库 **URL**。写进报告里。
- 同时提交在仓库 **Code > Download ZIP** 下载到的 zip 文件。
- 把运行方法写进 `README.md`。别人要能照着做下来。
- 实验用的输入数据也一并上传。数据太大时，上传生成数据的脚本。

仓库怎么建都可以。从
[`algorithm-env`](https://github.com/lec-algorithm/algorithm-env) 用
**Use this template** 创建，实验环境会一并带过来；不用它、自己建的仓库同样可以。
模板的用法参见[实验环境准备](/article/setup-guide/)

作业1 的示例展示了它的样子。主题不同，但仓库和报告的形态是一样的。

- 代码：[hw1-sample-2026](https://github.com/lec-algorithm/hw1-sample-2026)
- 报告：[REPORT.md](https://github.com/lec-algorithm/hw1-sample-2026/blob/main/report/REPORT.md)

## 评分 \{#grading}

考察的是下面五点。

- **能跑起来的代码**：三种方法确实都能运行，并在相同条件下比较
- **测量**：标准明确，数字可以再次得到
- **解读**：把结果与理论联系起来加以说明
- **结论**：优缺点与发展方向出自你自己的判断
- **文档**：别人读了就能照着运行

主题有多难不计入分数。把简单的主题做到底的报告，会高于把难主题只擦了个表面的
报告。

## 必须遵守的事 \{#rules}

- **可以使用 AI**。用它来理解课堂上没讲过的方法，甚至是推荐的做法。
  但要在报告里写清楚你问了什么、得到了什么。
- **可以使用别人的代码**。写明出处，并说明自己改了哪里。
  没有出处而照搬的代码不给分。
- 报告和代码用**韩语或英语**撰写。
- 仓库是公开的。不要使用包含个人信息的数据。

## 常见问题 \{#faq}

- **可以用和作业1 相同的主题吗？** 原样再交一次排序比较是不行的。
  以作业1 为起点扩大范围则没有问题。
- **三种都必须自己实现吗？** 不必。可以使用库。
  只要写清楚哪部分是自己的代码、哪部分是库即可。
- **语言有规定吗？** 没有。C 和 Python 会最顺手，用别的语言也可以。
  关键是三种方法要在**相同语言、相同环境**下比较。
- **是一个人做吗？** 是。这是个人项目。
- **中途可以换主题吗？** 可以。换了之后请发邮件告知。
