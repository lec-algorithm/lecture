## 这是什么样的作业 \{#what}

聊天和智能体用的是同一个 AI，但干活的地方不同。

| | 聊天 | 智能体 |
| --- | --- | --- |
| 它了解我的代码吗 | 只知道我贴进去的部分 | 直接读取仓库里的文件 |
| 结果放在哪里 | 我复制答案再粘贴 | 它自己创建和修改文件 |
| 会运行吗 | 不运行 | 在终端里跑测试，查看失败信息 |
| 记得规则吗 | 对话结束就忘了 | 每次都读规则文件 |

智能体能做的越多，人该做的事就越清楚。

- **做什么由我决定。** 规格说明可以由 AI 起草，但修改和决定是人的工作。
- **对不对由我检查。** 智能体会错得很像对的。用测试和运行结果抓出来。
- **留好可以回退的点。** 每一步都提交，智能体弄坏的东西随时可以撤回。

要做的是建立在[主题 08](/course/topic-08-hashing/) 哈希表之上的短网址服务（课上用拉链法，作业再加上线性探测进行比较）。输入长 URL，
它给出 `1`、`2`、`3` 这样的短代码；访问这个代码，就会跳回原来的地址。最后在 Codespace
里启动服务器，**用自己的手机打开短链接**。

## 课前准备 \{#prepare}

请在上课前做好下面三件事。在课上做的话，光等待就要花十分钟。

1. 一台能**登录 GitHub** 的笔记本电脑。也带上手机。
2. **开启 Copilot Free**：在 [github.com/settings/copilot](https://github.com/settings/copilot) 开启 Copilot Free。免费，不需要付款信息。
3. **先打开一次 Codespace**：按照[准备实习环境](/article/setup-guide/)在 `algorithm-code` 上打开 Codespace。第一次需要几分钟。

### 免费额度 \{#quota}

Copilot Free 对聊天和智能体的使用量有限制。代码补全单独计算，每月 2,000 次。这次作业
设计为**大约 20 次智能体请求**就能完成。节省的办法如下。

- 一次只让它做一件事，并且说清楚要什么。含糊的请求会浪费一次在反问上。
- 把失败信息原样贴进去。比说"不行"更能一次修好。
- 小改动自己做。不要为改个变量名浪费一次请求。

通过认证的学生可以经由 GitHub Education 获得 Copilot Student 方案。申请情况时常变化，
请到 [GitHub Education](https://education.github.com/) 确认。**没有它也能完成作业。**

## 开始 \{#start}

1. 在 [hw2-starter-2026](https://github.com/lec-algorithm/hw2-starter-2026) 顶部点击 **Use this template** → **Create a new repository**
2. 仓库名取 `algorithms-hw2` 之类，设为 **Public**。
3. 在新建好的**自己的仓库**里点击 **Code** → **Codespaces** → **Create codespace on main**
4. 用侧边栏或标题栏的 Copilot 图标打开聊天窗口。
5. 按照[智能体设置](#agent-settings)调整输入框下方的菜单。

起始仓库里没有答案。智能体会读取工作区的文件，如果答案就在旁边，它会照抄过来，
练习就没有意义了。

| 文件 | 作用 |
| --- | --- |
| `SPEC.md` | 规格说明模板。智能体起草，你来修改 |
| `src/` · `tests/` · `experiments/` | 空的 |
| `tools/catchup.sh` | 追上漏掉的步骤 |
| `Makefile` | `make test` · `make serve` · `make experiment` |

### 智能体设置 \{#agent-settings}

在输入框下方的菜单里设置三项。

| 菜单 | 选择 | 含义 |
| --- | --- | --- |
| Agent mode | **Autopilot** | 在权限范围内自己一直做到底 |
| Permissions | **Assisted permissions** | 先评估风险，只对看起来危险的命令询问 |
| 模型 | **Copilot Fusion**（Standard） | 根据任务挑选或组合模型 |

**检查靠结果，而不是许可按钮。**

- Assisted 对大部分命令不询问就直接运行。弹出询问时，读一读它要做什么再决定。
- Autopilot 有时会做你没说的事。所以每个请求都要写清范围。
  "现在还不要实现"、"不要修改测试"这样的句子就是起这个作用的。
- 智能体做了什么，用测试、diff 和提交来确认。

想一步一步看着它做，就把 Agent mode 改为 **Interactive**；想亲自批准所有命令，就把
Permissions 改为 **Manual**。Agent mode 的 **Plan** 可以在第 3 步使用。免费方案不能选择模型，
会自动决定，保持原样即可。

## 七个步骤 \{#steps}

每一步都重复**issue → 请求 → 检查 → 提交 → 记录**。

### 第 0 步：issue 与 git 准备 \{#step-0}

第 1 步之前准备两件事：建好 8 个 issue（7 个步骤和 1 个作业），并把 git 管理交给智能体。

#### 建好 8 个 issue \{#issues}

先在 GitHub 上自己的仓库里一次建好 8 个 issue：7 个步骤和 1 个作业。一个 issue 对应一个步骤、一个 feature 分支。
智能体工作时会在这个 issue 里用评论记录进展，完成后关闭它。

1. 在仓库上方的 **Issues** 标签页点击 **New issue**。

<Image src={issueList} alt="GitHub 仓库 algorithms-hw2 的 Issues 标签页，没有打开的 issue，右上角有 New issue 按钮" />

2. 在下面的 issue 列表里选第 1 步，复制标题和内容粘贴进去，然后创建。按顺序重复到作业标签页。

<Image src={issueNew} alt="Create new issue 页面，标题是步骤名称，描述是一行要做的事" />

<IssueTabs />

- 从第 1 步开始按顺序创建，issue 编号就和步骤编号相同。请求示例也是这样假设的。
- 编号不同的话，把请求示例里的 issue 编号换成自己的。

#### 把 git 管理交给智能体 \{#git}

提交可以用 git 命令，也可以用 VS Code 的源代码管理界面。这次**连 git 也交给智能体**。
开始时请求一次：

```text
这个仓库用 git flow 管理。
先从 main 创建 develop 分支。
每一步的 GitHub issue 我已经建好了，issue 编号和步骤编号相同。
每一步都从 develop 拉出 feature/<issue编号>-<简短名称> 分支来做，
做的过程中在那个 issue 里用评论记录进展。
这一步完成后提交、合并到 develop，并关闭 issue。
提交信息按 "Step N: 做了什么 (#issue编号)" 的格式写。
每次提交或合并后都 push 到 GitHub。
```

- 下面的请求示例第一行写着**第几步、哪个 issue**，最后一行是"**完成后提交、合并到 develop 并 push**。"
  直接复制，分支和提交就一起完成。有了 issue 编号，智能体才知道在哪里评论、创建哪个分支。
- 在设置 git 的**同一个聊天**里继续。到第 5 步打开新聊天之前不要换聊天。
- 提交就是可以回退的点。智能体提交后，用源代码管理界面或 `git log` 确认放进了什么。
- 提交作业前，让它把 develop 合并到 main 并 push。评分以 GitHub 仓库的 main 为准。

第一次 push 时可能会像下面这样停下来询问。创建分支时没有询问，但发到 GitHub 被判断为有风险，
所以它会附上理由来询问。

<Image src={assistedPush} alt="Copilot 聊天中弹出的确认框：Run in terminal: Publish the develop branch to GitHub，命令 git push -u origin develop，理由 Publishing develop itself was not specifically authorized，按钮 Allow Once、Skip、Explain" />

- **Allow Once**：只允许这一次。
- **Skip**：不运行。
- **Explain**：先听它说明要做什么。不认识的命令先点这个。

智能体以你的请求为准判断范围。这个确认框也是因为它判断"没有特别说明要发布 develop"才弹出的。

检查了什么、智能体错在哪里，都**亲自用评论**留在那一步的 issue 里。智能体的进展评论和你的评论集中在同一个 issue，
写报告时可以直接用。下面的请求示例可以直接用，也可以改写。

### 第 1 步：聊天与智能体并排比较 \{#step-1}

用两种方式做同一个功能，看看区别。要做的是 base62 编码，把整数变成短字符串：
用 `0-9`、`a-z`、`A-Z` 这 62 个字符表示的 62 进制。

先用**聊天方式**。向平时用的**浏览器里的聊天 AI**（ChatGPT、Gemini 等）提问：

```text
用 Python 写 base62 的 encode/decode 函数
```

把答案复制到 `src/base62.py`，自己想办法运行它。

然后在 **Codespace 的 Copilot 聊天窗口**里请求。删掉粘贴的文件，再请求：

```text
这是第 1 步，对应 issue #1。
在 src/base62.py 中写 encode(n) 和 decode(s)。
encode(n) 把 0 以上的整数按 0-9、a-z、A-Z 的顺序转换成 62 进制字符串，
decode(s) 是它的逆变换。
在 tests/test_base62.py 中用 unittest 写测试，
然后在终端运行 make test，给我看是否通过。
完成后提交、合并到 develop 并 push。
```

智能体会创建文件，在终端里跑测试，失败了就修改。Permissions 为 Assisted，只有像前面 push 那样看起来危险的命令
才会在运行前询问。**做决定的人是你。** 弹出询问时读过再决定；没有询问就运行的命令，也要读一读聊天里的记录。

要检查的地方

- `encode(0)` 返回什么？返回空字符串的实现很常见。
- 聊天的答案和智能体的答案，字符顺序一样吗？如果你不说，AI 会自己决定。
- 两种方式里，你各自亲手做了什么？在 issue #1 里用评论记下来，报告里会用到。

### 第 2 步：规格说明由 AI 起草，我来修改 \{#step-2}

正如第 1 步看到的，没写下来的东西 AI 会自己决定。规格说明也一样。
草稿交给智能体，**做什么由我修改后决定**。

```text
这是第 2 步，对应 issue #2。
请填写 #SPEC.md 模板，写出我们要做的短网址服务的规格说明草稿。
数据用我们自己实现的哈希表（拉链法、霍纳哈希）保存，
不要使用 dict、set 和内置 hash()。
只写草稿，不要写代码。
等我修改后再提交。
```

像 `#SPEC.md` 这样加上 `#`，这个文件就会附到请求里。确认输入框里出现了文件标签。

草稿出来后，逐个看它对下面问题的回答，和自己的想法不同就亲手修改。
最上面的 `TEMPLATE:` 那一行如果还在，就删掉。

- **哈希表**：冲突怎么解决？哈希函数是什么？什么时候扩容？
- **短网址**：同一个 URL 放两次，代码相同吗？查询不存在的代码，是报错还是返回 `None`？
- **错误输入**：以 `ftp://` 开头的地址、含空格的地址、非常长的地址怎么处理？
- **网页**：有没有在浏览器里输入 URL、拿到短链接的页面？只有 API 的话，第 7 步就没法在手机上用。
- **边界情况**：把要变成测试的情况列成清单。这个清单就是第 4 步的测试。

规定哈希表使用**拉链法**（每格一个链表）和主题 08 的**霍纳哈希**，不使用 Python 的 `dict`、`set`
和内置 `hash()`。目的是亲手实现哈希表。**线性探测**放在课后的[作业](#homework)里另外实现并比较。内置 `hash()` 每次运行时字符串的
哈希值都会变，第 6 步的实验重跑一次就会得到不同的数字。

找出 AI 自作主张填上的地方并改正，就是这一步要做的事。改了什么，
用评论留在 issue #2 里。改完后让它提交。

```text
继续第 2 步（issue #2）。
SPEC.md 我已经改好了。
请提交、合并到 develop 并 push。
```

### 第 3 步：先要计划，再写代码 \{#step-3}

不要一上来就说"帮我做"。先拿到计划并审查。

```text
这是第 3 步，对应 issue #3。
读 SPEC.md，制定分步骤的实现计划并保存到 PLAN.md。
现在还不要写代码。
完成后提交、合并到 develop 并 push。
```

也可以把 Agent mode 切换为 **Plan** 再请求。Plan 会先给出计划，批准后才执行。
无论哪种方式，都让它把计划保存到 `PLAN.md`，结束后切回 **Autopilot**。

阅读 `PLAN.md`，找出与规格说明不一致的地方，亲手修改。常见的有这些。

- 打算用 `dict` 保存 URL→代码。这违反了规格说明。
- 打算用 URL 的哈希值作为代码。这样不同的 URL 可能得到相同的代码。
- 打算最后才写测试。调换顺序。

在计划里修改，比在代码里修改便宜得多。

### 第 4 步：先写测试，实现交给智能体 \{#step-4}

先只让它写测试。

```text
这是第 4 步，对应 issue #4。
把 SPEC.md 第 6 节的边界情况用 unittest 写成测试。
文件是 tests/test_hash_table.py 和 tests/test_shortener.py。
现在还不要实现。
完成后提交、合并到 develop 并 push。
```

**阅读**测试。检查规格说明里的边界情况是否全部包含，期望值是否正确。缺的自己补上
并提交。这时 `make test` 失败是正常的，因为还没有实现。

然后让它实现。

```text
继续第 4 步（issue #4）。
按照 PLAN.md 的顺序实现 src/hash_table.py 和 src/shortener.py，
一直修改到 make test 全部通过为止。
不要修改测试。
完成后提交、合并到 develop 并 push。
```

**"不要修改测试"很重要。** 没有这句话，智能体有时会悄悄改掉它通过不了的测试。
完成后打开改动过的文件，阅读 diff，再提交。

### 第 5 步：用文件给出规则 \{#step-5}

在终端里检查智能体是否遵守了规格说明。

```sh
grep -n "dict\|set(\|hash(" src/*.py
```

规格说明里写了，智能体不读 `SPEC.md` 也没用。智能体只读当下看起来相关的文件。
而 **`.github/copilot-instructions.md` 每次请求都会读取。** 亲手创建这个文件，
写下仓库的规则。

- `.github/copilot-instructions.md`（示例的一部分）

```md
# 致在本仓库工作的智能体

- 写代码之前先读 SPEC.md。
- src/ 里不要使用 dict、set 和内置 hash()。使用我们自己实现的哈希表。
- 改完代码后运行 make test 并展示结果。
- 测试失败时修改代码，而不是测试。
- 每个 issue 从 develop 拉 feature/<issue编号>-<名称> 分支来做，进展用 issue 评论记录。
- 完成后提交、合并到 develop 并 push，然后关闭 issue。
- 我是一年级学生。用三行以内总结你改了什么。
```

这两行 git 规则，是一开始在聊天里交代的。新的聊天不知道之前的对话，
所以需要一直遵守的内容要移到规则文件里。

打开一个新的聊天，让它检查。如果有违规，让它修正。

```text
这是第 5 步，对应 issue #5。
检查 src/ 里的代码是否遵守本仓库的规则，
有违反的地方就修正。
完成后提交、合并到 develop 并 push。
```

规则文件是作业结束后也会留下的习惯。在个人项目的仓库里也放一个吧。

### 第 6 步：结果由自己验证 \{#step-6}

测试通过，不代表哈希表就是**好的**哈希表。正如主题 08 所示，拉链法的查找代价随链表长度，也就是装载因子 α
成比例增加。测一测你的表是不是这样。

```text
这是第 6 步，对应 issue #6。
创建 experiments/probe_experiment.py。
往格数固定为 4093 的 HashTable(max_load=None) 里放入随机 URL。
装载因子从 0.25 到 4，
测量成功查找和失败查找平均比较的节点数。
用表格与主题 08 的理论值比较。
成功 ≈ 1 + α/2，失败 ≈ α
结果保存为 experiments/results.csv 和 SVG 图表。
不要使用外部库。
完成后提交、合并到 develop 并 push。
```

用 `make experiment` 运行，**自己判断这些数字**。

- 装载因子为 1 时，成功查找在 1.5 左右、失败查找在 1 左右吗？
- 拉链法在装载因子超过 1 时也能工作。到 4 时还和理论吻合吗？
- 如果与理论相差很大，找出原因。看看是不是把在空格里查找算成了 1，或者哈希函数与规格说明不同。
- 图表的坐标轴名称和图例看得清吗？

这个实验脚本在[作业](#homework)里与线性探测比较时还会用到。

### 第 7 步：作为服务运行 \{#step-7}

最后加上 Web 服务器。

```text
这是第 7 步，对应 issue #7。
在 src/server.py 里做短网址 Web 服务。
在浏览器里打开 / 时显示输入 URL 的表单，
点击缩短后显示带短链接的页面。
打开短链接时跳转到原来的地址。
只使用标准模块 http.server，
并让 make serve 在 8000 端口启动。
完成后提交、合并到 develop 并 push。
```

用 `make serve` 启动，然后用手机打开。

1. 在下方面板的**端口**标签页找到 8000。
2. 右键点击该行 → **Port Visibility** → **Public**
3. 用手机打开 **Forwarded Address** 的地址。
4. 输入一个长 URL，拿到短链接后点开，看是否跳转到原地址。

如果短链接显示为 `localhost:8000`，说明智能体不知道有代理。Codespaces 通过
`X-Forwarded-Host` 头传递请求的地址。像这样的情况，就是
报告里要写的"智能体出错的地方"。用评论留在 issue #7 里。

**Public 端口互联网上的任何人都能打开。** 确认完毕后用 `Ctrl+C` 停止服务器，

## 作业：线性探测实现与比较 \{#homework}

课上用**拉链法**做了短网址服务。作业是在同一个仓库里加上**线性探测**哈希表，并在相同条件下比较两种方法，
也就是亲手实现并测量主题 08 的两种方法。

<ShortenerDemo mode="probe" />

用 issue 列表的**作业**标签页建好 issue #8，像课上一样用 issue 和 feature 分支来做。
要做的事有四件。

1. **线性探测表**：和 `HashTable` 用同样的接口（`put`、`get`、`find`、`len`、`in`、`load_factor`）。
   不使用 `dict`、`set` 和内置 `hash()`，哈希函数沿用霍纳方法。
2. **测试**：哈希表的测试也在线性探测上运行。还要检查从最后一格绕回 0 号格的情况和满表的情况。
3. **换到短网址里**：让短网址可以选用两种表之一，短网址的测试在两种表上都通过。
4. **比较实验**：把相同的键放进大小相同的两个表，测量装载因子 0.1 到 0.9 的成功、失败查找代价。
   拉链法数比较的节点数，线性探测数探查的格子数。和理论值一起画成图。

| 方法 | 成功查找 | 失败查找 |
| --- | --- | --- |
| 拉链法 | 约 1 + α/2 | 约 α |
| 线性探测 | 约 (1 + 1/(1-α))/2 | 约 (1 + 1/(1-α)²)/2 |

请求由你自己写。像课上学的那样，写清步骤和 issue 编号、范围，以及"不要修改测试"。
卡住时可以参考[示例仓库](https://github.com/lec-algorithm/hw2-sample-2026)的 `homework` 标签。

## 提交 \{#submit}

| 提交内容 | 方法 |
| --- | --- |
| 仓库 URL | 写在报告第一页 |
| 报告 | PDF，不超过 2 页，上传到 LearnUs 作业提交栏 |

仓库里必须包含以下内容。

- `SPEC.md`：AI 起草、自己修改的规格说明
- `src/`、`tests/`：自己实现的哈希表、短网址、服务器及其测试
- `experiments/`：实验脚本、`results.csv` 和图表
- 作业：线性探测表及其测试、两种方法的比较实验
- 每一步的提交历史（提交作业前把 develop 合并到 main 并 push）
- 每一步的 issue 和评论

报告是 PDF，**不超过 2 页**。第一页最上方写仓库 URL。

- 两种方法是怎么实现的（简短）
- 实验条件和结果：按装载因子的成功、失败查找代价，两种方法和理论值画在一张图上
- 解释：线性探测在装载因子接近 1 时为什么急剧变差，与拉链法有什么不同
- 一两处智能体出错的地方，以及你如何发现并修正

**没有 push 的内容不算提交。** 在 Codespace 里做的提交，push 之前不会出现在 GitHub 上。
提交作业前，打开 GitHub 上自己的仓库页面，确认文件和提交都在。

仓库保持 Public。截止后的提交不予查看。

这次作业本身就是要用 AI。但仍有一些部分必须由你完成。
