같은 AI라도 **저장소 안에서 일하게 하면** 할 수 있는 일이 달라집니다.
URL 단축기 하나를 만들면서 그 방법을 익힙니다.

## 무엇을 하는 과제인가 \{#what}

채팅과 에이전트는 같은 AI를 쓰지만 일하는 자리가 다릅니다.

| | 채팅 | 에이전트 |
| --- | --- | --- |
| 내 코드를 아는가 | 내가 붙여 넣은 만큼만 | 저장소의 파일을 직접 읽습니다 |
| 결과를 어디에 두나 | 답을 복사해 내가 붙여 넣습니다 | 파일을 직접 만들고 고칩니다 |
| 돌려 보는가 | 돌려 보지 않습니다 | 터미널에서 테스트를 돌리고 실패를 봅니다 |
| 규칙을 기억하나 | 대화가 끝나면 잊습니다 | 규칙 파일을 매번 읽습니다 |

할 수 있는 일이 많아지는 만큼, 사람이 맡을 일도 분명해집니다.

- **무엇을 만들지는 내가 정합니다.** 명세를 쓰는 것은 사람의 몫입니다.
- **맞는지는 내가 확인합니다.** 에이전트는 그럴듯하게 틀립니다. 테스트와 실행 결과로 잡습니다.
- **되돌릴 자리를 만들어 둡니다.** 단계마다 커밋하면 에이전트가 망친 것을 언제든 되돌릴 수 있습니다.

만드는 것은 [주제 08](/course/topic-08-hashing/)의 해시 테이블 위에 올린 URL
단축기입니다. 긴 URL을 넣으면 `1`, `2`, `3` 같은 짧은 코드를 주고, 그 코드로
접속하면 원래 주소로 보내 줍니다. 마지막에는 Codespace에서 서버를 띄워 **내
휴대폰으로 짧은 링크를 열어 봅니다.**

Copilot Free는 채팅과 에이전트에 쓸 수 있는 양이 정해져 있습니다. 자동완성은

인증된 학생은 GitHub Education으로 Copilot Student 플랜을 받을 수 있습니다. 신청

## 시작하기 \{#start}

1. [hw2-starter-2026](https://github.com/lec-algorithm/hw2-starter-2026) 상단의 **Use this template** → **Create a new repository**
2. 저장소 이름은 `algorithms-hw2`처럼 정하고, **Public**으로 만듭니다.
3. 만들어진 **내 저장소**에서 **Code** → **Codespaces** → **Create codespace on main**
4. 왼쪽 막대나 상단의 Copilot 아이콘으로 채팅 창을 엽니다.
5. 입력창 아래의 메뉴를 [에이전트 설정](#agent-settings)대로 맞춥니다.

시작 저장소에는 정답이 없습니다. 에이전트는 작업 공간의 파일을 읽으므로, 정답이
옆에 있으면 그것을 베껴 와서 연습이 되지 않습니다.

| 파일 | 하는 일 |
| --- | --- |
| `SPEC.md` | 명세 틀. 본인이 채웁니다 |
| `AGENT_LOG.md` | 제출용 작업 기록 틀 |
| `src/` · `tests/` · `experiments/` | 비어 있습니다 |
| `tools/catchup.sh` | 놓친 단계 따라잡기 |
| `Makefile` | `make test` · `make serve` · `make experiment` |

### 에이전트 설정 \{#agent-settings}

입력창 아래의 메뉴에서 셋을 맞춥니다.

| 메뉴 | 고를 것 | 뜻 |
| --- | --- | --- |
| Agent mode | **Autopilot** | 권한 안에서 알아서 끝까지 진행합니다 |
| Permissions | **Assisted permissions** | 위험을 따져 보고, 위험해 보이는 명령만 묻습니다 |
| 모델 | **Copilot Fusion** (Standard) | 작업에 맞는 모델을 고르거나 섞어 씁니다 |

**확인은 허락 버튼이 아니라 결과로 합니다.**

- Assisted는 대부분의 명령을 묻지 않고 실행합니다. 묻는 창이 뜨면 무엇을 하려는지 읽고 정합니다.
- Autopilot은 말하지 않은 일까지 진행하기도 합니다. 그래서 요청마다 범위를 분명히 적습니다.
  "구현은 아직 하지 마", "테스트는 고치지 마" 같은 문장이 그 일을 합니다.
- 에이전트가 무엇을 했는지는 테스트, diff, 커밋으로 확인합니다.

과정을 한 단계씩 지켜보고 싶으면 Agent mode를 **Interactive**로, 모든 명령을 직접 허락하고
싶으면 Permissions를 **Manual**로 바꿔도 됩니다. Agent mode의 **Plan**은 3단계에서 쓸 수
있습니다. 무료 플랜은 모델을 고를 수 없고 자동으로 정해지므로 그대로 두면 됩니다.

## 일곱 단계 \{#steps}

단계마다 **요청 → 확인 → 커밋 → 기록**을 반복합니다.

커밋은 git 명령어로도, VS Code의 소스 제어 화면으로도 할 수 있습니다. 이번에는 **git도
에이전트에게 맡깁니다.** 시작할 때 한 번 이렇게 시킵니다.

```text
이 저장소는 git flow로 관리하자. 먼저 main에서 develop 브랜치를 만들어 줘.
앞으로 단계마다 develop에서 feature/step-N 브랜치를 따서 작업하고, 단계가 끝나면
커밋한 뒤 develop에 머지해 줘. 커밋 메시지는 "Step N: 한 일" 형식으로 써 줘.
```

- 단계 요청 끝에 "끝나면 커밋하고 develop에 머지해 줘"를 붙이면 요청 수가 늘지 않습니다.
- 커밋은 되돌릴 자리입니다. 에이전트가 커밋한 뒤 소스 제어 화면이나 `git log`로 무엇이 들어갔는지 확인합니다.
- 제출 전에는 develop을 main에 머지하게 합니다. 채점과 ZIP은 main 기준입니다.

`AGENT_LOG.md`에는 실제로 쓴 요청 문장과, 무엇을 확인했는지를 단계마다 한 줄씩
적습니다. 아래의 요청 예시는 그대로 써도 되고 고쳐 써도 됩니다.

### 1단계. 채팅과 에이전트를 나란히 \{#step-1}

같은 기능을 두 방식으로 만들어 차이를 봅니다. 만들 것은 정수를 짧은 글자로
바꾸는 base62 인코딩입니다. `0-9`, `a-z`, `A-Z` 62글자를 숫자로 쓰는 62진법입니다.

먼저 **채팅 방식**입니다. 평소 쓰던 **브라우저의 채팅 AI**(ChatGPT, Gemini 등)에 묻습니다.

```text
Python으로 base62 encode/decode 함수 만들어 줘
```

답을 복사해 `src/base62.py`에 붙여 넣고, 돌려 볼 방법을 직접 찾아봅니다.

이번에는 **Codespace의 Copilot 채팅 창**에서 시킵니다. 붙여 넣은 파일은 지우고 시킵니다.

```text
src/base62.py에 0 이상의 정수를 0-9, a-z, A-Z 순서의 62진법 문자열로 바꾸는
encode(n)과 그 역변환 decode(s)를 만들어 줘. tests/test_base62.py에 unittest로
테스트를 만들고, 터미널에서 make test로 돌려서 통과하는지 보여 줘.
```

에이전트가 파일을 만들고, 터미널에서 테스트를 돌리고, 실패하면 고칩니다. Assisted
permissions라 위험해 보이는 명령만 실행 전에 묻습니다. **결정하는 사람은 나입니다.**
묻는 창이 뜨면 읽고 정하고, 묻지 않고 실행한 명령도 채팅에 남은 기록을 읽어 봅니다.

확인할 것

- `encode(0)`은 무엇을 돌려주나요? 빈 문자열이 나오는 구현이 흔합니다.
- 채팅의 답과 에이전트의 답이 글자 순서를 같게 잡았나요? 순서를 말하지 않으면 AI가 마음대로 정합니다.
- 두 방식에서 내가 손으로 한 일은 각각 무엇이었나요? 이것이 `AGENT_LOG.md` 3절의 내용입니다.

### 2단계. 명세는 내가 쓴다 \{#step-2}

1단계에서 본 것처럼, 적지 않은 것은 AI가 마음대로 정합니다. 그래서 만들기 전에
`SPEC.md`를 **직접** 씁니다. 이 단계에서는 에이전트에게 요청하지 않습니다.

맨 위의 `TEMPLATE:` 줄을 지우고, 절마다 아래 질문에 답합니다.

- **해시 테이블**: 충돌은 어떻게 푸나요? 해시 함수는 무엇인가요? 언제 크기를 늘리나요?
- **단축기**: 같은 URL을 두 번 넣으면 같은 코드인가요? 없는 코드를 물으면 오류인가요, `None`인가요?
- **잘못된 입력**: `ftp://`로 시작하는 주소, 공백이 들어간 주소, 아주 긴 주소는 어떻게 하나요?
- **경계 사례**: 테스트로 옮길 것을 목록으로 적습니다. 이 목록이 4단계의 테스트가 됩니다.

해시 테이블은 **선형 탐지**와 주제 08의 **호너 해시**를 쓰고, Python의 `dict`,
`set`, 내장 `hash()`는 쓰지 않는 것으로 정합니다. 이 과제는 해시 테이블을 직접
만드는 과제입니다. 내장 `hash()`는 실행할 때마다 문자열의 해시값이 바뀌어, 6단계의
실험을 다시 돌리면 다른 숫자가 나옵니다.

### 3단계. 코드보다 계획을 먼저 \{#step-3}

바로 "만들어 줘"라고 하지 않고, 계획부터 받아 검토합니다.

```text
SPEC.md를 읽고 구현 계획을 단계별로 세워서 PLAN.md에 저장해 줘.
아직 코드는 쓰지 마.
```

Agent mode를 **Plan**으로 바꿔서 시켜도 됩니다. Plan은 계획을 먼저 보여 주고, 승인해야
실행합니다. 어느 쪽이든 계획은 `PLAN.md`로 저장하게 하고, 끝나면 **Autopilot**으로 돌아옵니다.

`PLAN.md`를 읽고 명세와 어긋나는 곳을 찾아 직접 고칩니다. 자주 나오는 것은 이렇습니다.

- URL→코드 저장에 `dict`를 쓰겠다고 합니다. 명세 위반입니다.
- 코드를 URL의 해시값으로 만들겠다고 합니다. 그러면 서로 다른 URL이 같은 코드를 받을 수 있습니다.
- 테스트를 맨 마지막에 쓰겠다고 합니다. 순서를 바꿉니다.

계획에서 고친 것은 코드에서 고치는 것보다 훨씬 쌉니다.

### 4단계. 테스트를 먼저, 구현은 에이전트가 \{#step-4}

먼저 테스트만 만들게 합니다.

```text
SPEC.md 6절의 경계 사례를 tests/test_hash_table.py와 tests/test_shortener.py에
unittest로 옮겨 줘. 구현은 아직 하지 마.
```

테스트를 **읽습니다.** 명세의 경계 사례가 빠짐없이 들어갔는지, 기대값이 맞는지
봅니다. 빠진 것은 직접 더하고 커밋합니다. 이때 `make test`가 실패하는 것은
정상입니다. 아직 구현이 없습니다.

그다음 구현을 시킵니다.

```text
PLAN.md 순서대로 src/hash_table.py와 src/shortener.py를 구현하고,
make test가 모두 통과할 때까지 고쳐 줘. 테스트는 고치지 마.
```

**"테스트는 고치지 마"가 중요합니다.** 이 말이 없으면 에이전트가 통과하지 못하는
테스트를 슬쩍 고쳐 놓기도 합니다. 끝나면 변경된 파일을 열어 diff를 읽고 커밋합니다.

### 5단계. 규칙은 파일로 준다 \{#step-5}

에이전트가 명세를 지켰는지 터미널에서 확인합니다.

```sh
grep -n "dict\|set(\|hash(" src/*.py
```

명세에 적었어도 에이전트가 `SPEC.md`를 읽지 않으면 소용이 없습니다. 에이전트는
그때그때 필요해 보이는 파일만 읽습니다. 반면 **`.github/copilot-instructions.md`는
요청할 때마다 항상 읽습니다.** 이 파일을 직접 만들어 저장소의 규칙을 적습니다.

- `.github/copilot-instructions.md` (예시의 일부)

```md
# 이 저장소에서 일하는 에이전트에게

- 코드를 쓰기 전에 SPEC.md를 읽는다.
- src/ 안에서 dict, set, 내장 hash()를 쓰지 않는다. 해시 테이블은 직접 만든 것을 쓴다.
- 코드를 고친 뒤에는 make test를 돌리고 결과를 보여 준다.
- 테스트가 실패하면 테스트가 아니라 코드를 고친다.
- 나는 1학년이다. 무엇을 바꿨는지 세 줄 이내로 요약한다.
```

새 채팅을 열고 확인을 시킵니다. 위반이 있었다면 고치게 합니다.

```text
src/ 안의 코드가 이 저장소의 규칙을 지키는지 검사하고, 어긴 곳이 있으면 고쳐 줘.
```

규칙 파일은 이번 과제가 끝나도 남는 습관입니다. 개인프로젝트 저장소에도 하나 만들어 두면 좋습니다.

### 6단계. 결과는 직접 검증한다 \{#step-6}

테스트가 통과했다고 해시 테이블이 **좋은** 해시 테이블인 것은 아닙니다. 주제 08에서
본 것처럼, 선형 탐지는 적재율이 1에 가까워질수록 탐색이 급격히 느려집니다. 내
테이블이 정말 그런지 잽니다.

```text
experiments/probe_experiment.py를 만들어 줘. 크기를 4093으로 고정한
HashTable(max_load=None)에 무작위 URL을 적재율 0.1부터 0.9까지 넣고,
성공 탐색과 실패 탐색에서 들여다본 칸 수의 평균을 재서, 주제 08의 크누스 근삿값
성공 ≈ (1 + 1/(1-α))/2, 실패 ≈ (1 + 1/(1-α)²)/2와 표로 비교해 줘.
결과는 experiments/results.csv와 SVG 그래프로 저장해 줘. 외부 라이브러리는 쓰지 마.
```

`make experiment`로 돌리고 숫자를 **직접 판단합니다.**

- 적재율 1/2에서 성공 탐색이 1.5, 실패 탐색이 2.5 근처인가요?
- 이론과 크게 어긋나면 원인을 찾습니다. 처음 들여다본 칸을 0으로 세었는지, 해시 함수가 명세와 다른지 봅니다.
- 그래프의 축 이름과 범례가 읽히나요?

### 7단계. 서비스로 띄운다 \{#step-7}

마지막으로 웹 서버를 붙입니다.

```text
SPEC.md 5절대로 src/server.py를 만들어 줘. 표준 모듈 http.server만 쓰고,
make serve로 포트 8000에서 뜨게 해 줘.
```

`make serve`로 띄우고 휴대폰으로 엽니다.

1. 아래쪽 패널의 **포트** 탭에서 8000번을 찾습니다.
2. 줄을 오른쪽 클릭 → **Port Visibility** → **Public**
3. **Forwarded Address**의 주소를 휴대폰으로 엽니다.
4. 긴 URL을 넣고 짧은 링크를 받은 뒤, 그 링크를 눌러 원래 주소로 가는지 봅니다.

짧은 링크가 `localhost:8000`으로 찍힌다면 에이전트가 프록시를 몰랐던 것입니다.
Codespaces는 요청 주소를 `X-Forwarded-Host` 헤더로 넘깁니다. 이런 것이
`AGENT_LOG.md` 2절에 적을 "에이전트가 틀린 곳"입니다.

**Public 포트는 인터넷의 누구나 열 수 있습니다.** 확인이 끝나면 `Ctrl+C`로 서버를
끄고 다시 **Private**으로 돌립니다. Codespace를 다시 시작하면 Private으로 돌아갑니다.

## 놓친 단계 따라잡기 \{#catchup}

수업 중에 한 단계를 놓쳐도 다음 단계로 갈 수 있습니다. 먼저 지금까지를 커밋하고,
따라잡을 단계 번호를 줍니다.

```sh
git add -A && git commit -m "WIP"
sh tools/catchup.sh 4
```

[샘플 저장소](https://github.com/lec-algorithm/hw2-sample-2026)의 `step-4` 태그
상태로 `src/`, `tests/`, `experiments/` 등을 맞춥니다. `AGENT_LOG.md`는 건드리지
않습니다. 따라잡은 단계는 기록에 "따라잡음"이라고 적습니다. 따라잡은 단계가 있어도
감점하지 않지만, 그 단계의 "에이전트가 틀린 곳"은 쓸 수 없습니다.

## 제출 \{#submit}

| 내는 것 | 방법 |
| --- | --- |
| 저장소 URL | LearnUs 과제 제출란에 적습니다 |
| ZIP | 저장소의 **Code** → **Download ZIP**으로 받은 파일 |

저장소에는 아래가 들어 있어야 합니다.

- `SPEC.md`: 본인이 쓴 명세
- `.github/copilot-instructions.md`: 본인이 쓴 규칙
- `src/`, `tests/`: 직접 구현한 해시 테이블, 단축기, 서버와 테스트
- `experiments/`: 실험 스크립트, `results.csv`, 그래프
- `AGENT_LOG.md`: 단계별 기록, 에이전트가 틀린 곳 둘 이상, 채팅과의 비교, 소감
- 단계별 커밋 이력 (제출 전에 develop을 main에 머지합니다)

저장소는 Public으로 둡니다. 마감 뒤에 커밋한 것은 보지 않습니다.

## 평가 \{#grading}

에이전트가 일을 잘했는지가 아니라, **내가 무엇을 정하고 무엇을 잡아냈는지**를 봅니다.
에이전트의 결과는 사람마다 다르게 나오므로, 결과물의 완성도만으로 채점하면 운이
점수를 정하게 됩니다.

| 항목 | 배점 | 보는 것 |
| --- | --- | --- |
| 명세와 테스트 | 1 | 경계 사례를 본인이 정했고, 테스트가 그것을 빠짐없이 검사하는가 |
| 규칙 파일 | 1 | 규칙이 구체적이고, 실제로 효과를 냈는가 |
| 해시 테이블과 실험 | 1 | `dict` 없이 동작하고, 실험값을 이론과 비교해 해석했는가 |
| 작업 기록 | 1.5 | 틀린 곳을 어떻게 알아채고 고쳤는지 구체적으로 적었는가 |
| 서비스 | 0.5 | `make serve`로 뜨고, 짧은 링크로 이동되는가 |

## 수업에 오지 못했다면 \{#absent}

**같은 과제를 같은 마감으로** 냅니다. 이 글의 [일곱 단계](#steps)를 순서대로
따라 하면 됩니다. 수업에서 보여 준 화면은 [슬라이드](/slides/hw2-2026/)에 있습니다.

- 혼자 하므로 단계마다 커밋을 더 꼼꼼히 남깁니다. 커밋 이력이 수업 참여를 대신합니다.
- 막히면 `tools/catchup.sh`로 다음 단계로 넘어가도 됩니다.
- 질문은 LearnUs 게시판에 올립니다.

## AI를 쓰는 원칙 \{#ai-rules}

이 과제는 AI를 쓰는 과제입니다. 그래도 사람이 맡을 몫은 정해져 있습니다.

- `SPEC.md`와 `AGENT_LOG.md`는 **본인이 씁니다.** AI가 쓴 기록은 기록이 아닙니다.
- 규칙 파일은 AI에게 초안을 받아도 되지만, 무엇을 넣을지는 본인이 정합니다.
- 다른 사람의 저장소를 복사하지 않습니다. 커밋 이력과 기록을 보면 드러납니다.
